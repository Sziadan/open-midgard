# PK45.03 — item pickup acknowledgment and inventory handoff

Date: 2026-11-04. Status: client receive layouts and success-path handoff traced. Selected-server emitter/profile, failure cleanup, item merge semantics, and replay remain open. No rows closed.

## Receive variants and payload

The current map receive profile exposes basic pickup acknowledgment 0x00A0 and extended variant 0x02D4. The client packet-size table assigns 23 and 29 bytes, and both IDs register to `HandleItemPickupAck`. The handler requires at least 23 bytes and rejects IDs outside the active profile. It reads the result byte at offset 22; nonzero result returns immediately. On success it decodes item index@2, amount@4, item ID@6, identified/damaged/refine bytes@8..10, four card slots@11..18, location@19, and item type@21. The extended trailing fields are read only when present: delete time u32@23 and `isYours` u16@27.

## Request-to-inventory path

`TryBeginGroundItemPickup` replaces the pending pickup list with the clicked ground object ID, clears attack/chase state, and either sends a take-item request immediately when in range or continues through a chase path. On successful acknowledgment, the client starts the local pickup animation for the first pending object ID if present, announces the acquired item, adds the decoded item to session inventory, clears the pending list, and resets the request tick. Ground-item disappearance also removes its object ID from the pending list and resets the tick when the list becomes empty.

## Open compatibility and failure questions

The client profiles and parsers prove supported client layouts, not that the selected 2008 server emits either variant or that the extended trailing fields are valid for that baseline. The nonzero-result branch returns before clearing pending pickup state. The later pickup continuation path throttles requests using `kPickupRetryIntervalMs` and retries the pending ground object while it remains available; disappearance removes it and clears the timer when the queue empties. No terminal failure UI or retry ceiling was established. Verify server result codes, request/ack correlation, inventory merge/quantity semantics, and retry exhaustion before changing or closing the failure path. Test basic and extended boundaries, failed pickup, disappearing item, duplicate/out-of-order acknowledgments, and local animation/inventory synchronization in the production replay. No rows are closed.

### Pickup failure follow-up

Focused inspection of the continuation path confirmed the pending ground-object request is retried after `kPickupRetryIntervalMs` while the object remains in range; object disappearance removes it and clears the timer when no pending IDs remain. The earlier evidence now captures this retry behavior. A terminal failure state/retry ceiling and server result mapping remain open.


## Additional pending-request and failure lifecycle

TryBeginGroundItemPickup clears the prior pending list, stores the clicked ground-object AID as the sole pending request, resets its request tick, and sends immediately when in range (src/gamemode/GameMode.cpp:5380-5402). The acknowledgment has no ground-object AID field: on success the handler uses the pending list's front entry for the local pickup animation, adds the decoded inventory item, then clears the list and request tick (src/gamemode/GameModePacket.cpp:2475-2527). A nonzero result returns before those success updates, preserving the pending entry; the continuation retries after kPickupRetryIntervalMs while the object still exists and remains in range, and clears pending state when the object disappears (GameMode.cpp:7363-7384). This documents a single-outstanding-request correlation model and failure retry behavior. It does not prove stale/duplicate acknowledgment handling or selected-server emitter timing; those remain replay/server-profile review items. The selected server sources are not present in this checkout, so no emitter variant is claimed.
