# PK46.02 — leave-party request 0x0100

Date: 2026-11-05. Status: request call graph and client 0x0105 removal notification handler are source-traced. The leave packet is reached from the party-window master-only disband action through the guarded helper in the bounded call-path search; non-master caller reachability is source-resolved for this client path. Server rejection/recovery and queued-removal ordering remain open. No discovery row is closed.

## Current client path

The party-window leader action sends `GameMsg_RequestPartyDisband`. `RequestDisbandParty` requires a nonempty party and local master status, sends a remove-member request for each non-self member with a nonzero account ID, then calls `RequestLeaveParty`. The leave helper itself requires only a nonempty party, builds the packet and sends it. In this call graph, the leave request follows the member-removal sends without awaiting server responses. `RequestDisbandParty` returns true if the leave send succeeds or if any preceding removal send succeeded; it can therefore report success even when leave failed and only some removal sends succeeded.

## Client layout and profile

`PACKET_CZ_REQ_LEAVE_GROUP` contains only opcode `0x0100`, at offset 0 with width 2. `ActivePartySend::kLeaveParty` resolves to the legacy party opcode. Total frame length is two bytes.

## Selected registry comparison

`PK01.02-server-registry-final.csv` maps opcode `0100` to fixed length 2 and `clif_parse_LeaveParty`. Client opcode and length agree with the selected registry.

## Caller reachability and local guards

The party window exposes its disband action only when the party list is nonempty and `m_amIPartyMaster` is true; its only `GameMsg_RequestPartyDisband` call is inside that leader-button branch (`src/ui/UIMessengerGroupWnd.cpp:355-372`). `RequestDisbandParty` repeats the nonempty-party/master guard, sends removal requests for non-self members with nonzero AIDs, then calls `RequestLeaveParty` (`src/gamemode/GameMode.cpp:6636-6650`). The focused `kLeaveParty` search finds the packet assignment only inside `RequestLeaveParty` (`src/gamemode/GameMode.cpp:6598-6611`), which checks only that the local party is nonempty. Thus the current UI/message path prevents non-masters reaching the packet, though the low-level helper itself has no master guard. No separate ordinary member-leave action was found in this bounded sender search; verify against any future/alternate caller before generalizing.

## Selected server leave path — 20080910

The selected two-byte `0x0100` parser delegates to `party_leave(*sd, true)` (`src/map/clif.cpp:13909-13916`). `party_leave` rejects party-locked maps or missing party state, can reject instance departure with a `CANT_LEAVE` withdrawal notification, cancels party-bound trade, then sends `intif_party_leave` to the character service (`src/map/party.cpp:759-797`). The actual membership-removal notification follows the character-service withdrawal path, rather than being a synchronous result of the request.

`RequestDisbandParty` sends each non-self member removal request before sending `0x0100`; its return expression is `RequestLeaveParty() || sentAny` (`src/gamemode/GameMode.cpp:6636-6650`). Therefore it always attempts leave, but reports success if any expel send succeeded even when the leave send failed. This is a source-confirmed partial-send reporting limitation.

## Client party-removal notification follow-up

The client frames `0x0105` as 31 bytes (`src/network/GronPacket.cpp:175`) and routes it to `HandlePartyMemberRemoved` (`src/gamemode/GameModePacket.cpp:8978`). The handler reads the fixed character name at offset 6 and result at offset 30. Results 2 and 3 display map-specific leave/expel refusal messages and return without changing the party cache. Other results remove the named member; if that name is the local player or result bit `0x10` is set, the client clears the party, with a disband notice for bit `0x10`, then refreshes party UI (`GameModePacket.cpp:7702-7731`). This describes cache behavior for server removal notifications, not whether the chained removal requests and following 0x0100 leave are accepted or ordered as intended. Keep that sequencing and UI reachability open for stronger review/replay.
