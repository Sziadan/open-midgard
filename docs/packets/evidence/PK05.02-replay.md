# PK05.02 — fail closed at unframed receive boundaries

Date: 2026-11-04. Status: implementation and production replay complete; PK05.03 reporting contract remains open; PK48 independent review pending.

## Change

`CRagConnection::RecvPacket` now logs and disconnects when the active receive table has no size for the leading opcode, or when a table-known variable packet declares a length outside 4–`0x7FFF`. It no longer removes two bytes and rescans the remainder. `CConnection::Disconnect` closes the socket and clears send/receive/block queues; the receive method returns no packet. Recognized fixed/variable packets keep using the active size table and preserve incomplete headers/bodies.

This fail-closed behavior is a client framing policy: absent a declared length or marker, no safe next boundary can be inferred. It does not claim a server-defined error reply. Typed failure propagation/reporting remains PK05.03. Discovery rows remain open.

## Production replay

Extended the existing local TCP replay through production `Connect` and `CRagConnection::RecvPacket`. Five records in `PK05.02-replay.jsonl` cover unknown opcode, undersized length 3, oversized length `0x8000`, a one-byte fragmented unknown header, and a three-byte fragmented invalid variable header. Each invalid stream is followed by the valid synthetic fixed frame `6c0000` (SHA-256 `a8649967f8ca13630d18e21c07eaad14b309a54534f1cd9f633b692c3b2f341f`). The fragmented cases verify no disconnect occurs until enough header bytes arrive. All five then assert no emitted frame, closed connection, and empty receive queue. Existing fixed/variable fragmentation, concatenation, EOF and reconnect cases also passed.
