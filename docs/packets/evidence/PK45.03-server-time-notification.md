# PK45.03 — server time notification

Date: 2026-11-04. Status: profile routing, fixed framing and clock/ping effects traced; timing semantics and replay remain open. No rows closed.

The active receive profile maps notify-time to 0x007F; the packet size table fixes it at 6 bytes. `HandleNotifyTime` reads the server tick as little-endian u32@2. The first notification calls `SetServerTime`, which resets the late-packet counter and anchors the local clock offset; later notifications call `UpdateServerTime`, which applies lead/tolerance logic and may ignore early outliers until the fourth late sample. The handler sets `m_receiveSyneRequestTime`, increments the notification count, samples local `timeGetTime() - m_syncRequestTime`, recalculates average ping (last three samples), and logs the server tick/count.

## Selected server tick-response contract (2026-11-04)

The pinned server emitter confirms `0x007F` contains one u32 tick value and is sent to SELF. It serializes `client_tick(time)`, which is a direct cast from the server `t_tick` to u32, not a wall-clock timestamp or Unix epoch. The corresponding request parser accepts profile variants `0x007E`/`0x0360`, reads the client tick at the registered packet offset into session state, then replies with the current `gettick()` value through `clif_notify_time`. This confirms a request/response clock-sync path and explains wraparound at the u32 boundary.

The exact timer unit and sync cadence depend on the timer implementation/callers outside this emitter; the client’s offset estimator, late-sample policy, startup/reset behavior, and stale/future replay remain open. No discovery row is closed.


Supplemental timing trace (current client sources and unpinned current timer.cpp): server clif_parse_TickSend reads the request tick and immediately calls clif_notify_time(gettick()); the emitter casts that tick to u32 and sends 0x007F to SELF.
