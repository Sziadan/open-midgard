# PK46.02 — sit/stand action request branch

Date: 2026-11-04. Status: user actions, profile packet values and selected server action branches traced; response/replay remains open. No discovery row is closed.

The in-game sit/stand toggle and `/sit`/`/stand` chat commands call the shared request path. It requires a local player, clears the local target GID, and sends a target ID of zero with action `0x02` for sit or `0x03` for stand. The toggle chooses the opposite of the player's current local sitting flag. The sender's zero-target rejection applies only to attack action values 0 and 7, so these sit/stand requests are allowed.

The request uses the same action packet profile layouts documented in `PK46.02-map-action-request.md`: PacketVer22 sends 19-byte `0x0190` with target/action at 5/18; PacketVer23 sends 7-byte `0x0437` with target/action at 2/6. The selected 20080910 server registers both layouts to `clif_parse_ActionRequest`, which forwards the registered action and target fields to its action subroutine.

In the selected parser enum, action 2 is `DMG_SIT_DOWN` and action 3 is `DMG_STAND_UP`. Sit rejects dead players, interaction-blocking statuses, insufficient Basic Skill (when configured), incompatible timers/statuses, and `PCBLOCK_SITSTAND`; accepted requests call `pc_setsit`, `skill_sit(true)`, and `clif_sitting`. Stand requires the server to consider the player sitting, applies status/block checks, and on successful `pc_setstand` calls `skill_sit(false)` and `clif_standing`. This server-authoritative state change explains why the client request itself does not locally confirm the posture. No independent bytes or production sit/stand UI replay were performed; no discovery row is closed.

## Server response and client receive path — 2026-11-04

The selected server's 20080910 `PACKETVER` uses the `PACKETVER >= 20071113` `PACKET_ZC_NOTIFY_ACT` layout in `src/map/packets.hpp`; `clif_sitting`/`clif_standing` set the `type` to `DMG_SIT_DOWN`/`DMG_STAND_UP` and send the action to `AREA` in `src/map/clif.cpp`. This branch maps the packet to `0x02E1` (33 bytes); the older 0x008A layout is not the selected wire ID. Source hashes: `defines_pre.hpp` `0A18FF8845D1E6465C6F0213A3F62AA269D0380337C79E9FCE961EC312E41CFB`, `packets.hpp` `FCF4570619DB2B46468F254B8A59F94EB6FF1C9C6705C9AFB1C3BC8825A136EF`, and `clif.cpp` `E00EDDAE72D4569F126EFC91ED645CAD0D99B4D0B6460790A441354E4B1AFA69`.

On the client, `MapSendProfile.cpp` selects `actorActionNotifyExtended=0x02E1`; `GronPacket.cpp` frames it at 33 bytes; the production router registers that ID to `HandleActorActionNotify`. The handler reads the action byte at offset 28 and forwards it through actor message 11 to `CGameActor::Am_Action`. This explains how accepted server posture changes reach actor animation. No dedicated 0x02E1 request/response replay or visible posture capture was run, so the send/reply case remains open and no discovery row is closed.
