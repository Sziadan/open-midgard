# PK46.02 — trade item or currency offer 0x00E8

Date: 2026-11-05. Status: client guards plus selected-server parser, item and currency validation, and response paths source-traced. Production client-sender replay now covers the item branch; server-valid index mapping, currency behavior, and server result handling remain open. No row closed.

`Commerce::Action` accepts `offerTrade` and `tradeZeny` only while a trade is active and the local side is not locked, awaiting lock, or waiting on another item-add acknowledgement. Item offers additionally require a nonzero amount, a present inventory item that is neither equipped nor expiring, amount at most 32767, cumulative offers no greater than inventory count, and fewer than ten local offer rows. The sender writes an 8-byte `0x00E8` frame with item index u16@2 and amount u32@4. A successful item send records `pendingTrade` and sets `tradeAddPending`; failed send leaves those pending fields unchanged.

The currency branch requires selected-character data and amount no greater than nonnegative current money; it allows zero. The default `ITEM_INFO` index is zero, so the shared frame serializes index 0 with the requested currency amount. On successful send the client updates `localZeny` immediately; the source comment states the server does not echo a currency-add acknowledgement to the sender, and this value is an editable offer rather than actual character balance.

`GronPacket.cpp` fixes the client frame at 8 bytes. Selected server `PACKET_CZ_ADD_EXCHANGE_ITEM` is `{ int16 packetType; uint16 index; int32 amount; }`, registered as fixed-size `0x00E8`. `clif_parse_TradeAddItem` sends index 0 to the currency handler; other indices pass through `server_index`, and the 32-bit amount narrows to signed `int16` before `trade_tradeadditem`.

`trade_tradeadditem` requires an active unlocked trade and a live partner; missing partner cancels the trade. Zero amount returns a success ack with index 0. Negative/out-of-range indices and negative or over-inventory amounts return silently. Non-tradable, expired, or bound-item failures send the closed result; hatched eggs and equip-switch items return silently. The server merges repeated offers from the same inventory slot and clamps a cumulative amount beyond inventory to the remaining amount. It checks recipient stack maximum, inventory-space policy, and weight; those rejection paths send distinct add-failed results. A full ten-row offer table returns silently. Accepted offers update the source's deal amount/weight/space, ack only the source, then send the added-item record to the partner.

For selected 20080910, `clif_tradeitemok` emits fixed `0x00EA` to the source, maps the returned inventory index with `client_index`, and serializes the result byte. The pre-20110705 compatibility branch clamps newer failure values to `EXITEM_ADD_FAILED_OVERWEIGHT`. `clif_tradeadditem` emits the offer item to the peer. This source trace does not establish how every rejection affects the client's optimistic local offer or lock state; replay remains required.

The parser routes `index == 0` to `trade_tradeaddzeny` without narrowing the signed 32-bit amount. That path also requires an active unlocked trade and live peer. Negative amounts, amounts greater than the sender's current zeny, and amounts that would put the recipient over `MAX_ZENY` return silently. Success replaces `sd->deal.zeny` with the requested amount and sends the zeny add-record to the peer using item index 0; it does not send an add-item acknowledgement to the source or debit the sender's actual balance at offer time. A missing peer cancels the trade. This matches the client source note that updates displayed offer zeny optimistically and expects no direct zeny-add ack, but runtime reconciliation/rejection behavior remains unverified.

The commit path revalidates the aggregate offer after both sides lock: `trade_tradecommit` waits for the peer's locked state, runs `impossible_trade_check` for each participant, then calls `trade_check`. That check simulates both inventories, rejects offered quantities exceeding the source inventory, recipient stacks exceeding `MAX_AMOUNT`, or missing recipient slots, and cancels the trade on failure. The per-add capacity checks are therefore not the only integrity gate. This source trace does not verify runtime lock races, client rollback after final cancel, or the complete transfer transaction; replay remains required.

The existing production replay covers one client item-offer frame, send failure, and duplicate-pending suppression. Still open: a server-valid inventory-index fixture, currency offers/rejection, repeated item indices, boundary counts, lock races, and server correction of `localZeny`. Primary ownership remains PK37; no row closed.
