# PK45.03 — cart metadata and clear handlers

Date: 2026-11-04. Status: client metadata/clear packet paths traced. Cart-item format and inventory/equipment synchronization in the generic commerce receiver remain for focused review. No rows closed.

## Metadata and cart clear

The client size table marks 0x0121 `ZC_UPDATE_CARTINFO` fixed at 14 bytes and 0x012B `ZC_CLEAR_CART` fixed at 2 bytes; both are registered to dedicated handlers. `HandleCartInfo` delegates first to `ro::commerce::Receive`, then requires 14 bytes and decodes count u16@2, capacity u16@4, weight u32@6, and max weight u32@10. It marks the local cart as present and applies pending local cart state. The isolated 0x0121 branch in `Commerce::Receive` checks the same 14-byte minimum and updates the commerce cart metadata.

`HandleCartOff` also delegates to the commerce receiver, then requires the 2-byte header, marks the known local cart absent, applies pending state, and invalidates cart UI. The isolated 0x012B branch clears `hasCart`, the commerce cart item map, cart/vending visibility, draft state, and vending active/pending flags.

## Selected server cart metadata/clear emission (2026-11-04)

The selected server's packed `0x0121` cart-count packet is 14 bytes: current/max item count as u16 and current/max cart weight as u32. `clif_cartcount` fills those fields from the session's cart state and sends SELF. The `0x012B` cart-off packet is the two-byte opcode only. Its server comment describes closing cart storage and removing cart items from client memory while retaining count and weight; `clif_clearcart` sends it on the requested file descriptor.

These contracts match the client's fixed packet sizes and its separate metadata and clear handlers. The server comment specifically distinguishes closing cart contents from removing the cart and preserving count/weight. Ordering relative to item-list updates, inventory/equipment synchronization, and stale metadata behavior remain unresolved pending selected-profile replay. No discovery row is closed.
