# PK45.03 — guild member status update 0x01F2

Date: 2026-11-04. Status: fixed framing, validation and member/cache effects traced; field contract and selected-profile semantics remain open. No rows closed.

Opcode 0x01F2 has fixed size 20 and routes through `HandleGuildWindowPacket`. `ReadWindowPacket` requires exactly 20 bytes, reads account ID u32@2, character ID u32@6 and status u32@10, and rejects status values greater than 1 before mutation. It then reads gender u16@14, hairstyle u16@16 and hair color u16@18. The parser finds the first member matching both account and character IDs; if found, it updates online=`status==1` and the three appearance fields, then recalculates the guild online count. Unknown members are ignored while the packet still succeeds.

The outer handler erases `m_guildPosList[accountId]` when status is zero, then performs its common local position-derived permission/title refresh. Unlike 0x016D, this branch also updates member appearance fields and uses exact-size validation plus a bounded status enum. No network reply is sent.

Open work: verify that 0x01F2 is a selected-server variant of 0x016D, confirm field meanings/online polarity and the AID/account-character identity; replay malformed status, unmatched and duplicate member records, local appearance changes and offline cache clearing. Coverage requires source verification. No independent fixture or production replay was performed for this leaf.

## Selected server status-variant follow-up (2026-11-04)

The pinned server declares two `ZC_UPDATE_CHARSTAT` layouts: without PACKETVER, legacy `0x016D` is 14 bytes; with PACKETVER defined, `0x01F2` is 20 bytes and appends gender, hair style, and hair color u16 fields after AID, GID, and status. The selected server profile is compiled with PACKETVER, so the client’s 20-byte `0x01F2` parser corresponds to the active source branch. `clif_guild_memberlogin_notice` fills those appearance fields from the online member; when no member session exists it zeroes them. It sends through guild targets, while the separate login snapshot helper deliberately emits legacy 14-byte `0x016D` records to SELF. The two opcodes therefore serve different update paths and should not be conflated.

The source comment says it does not know when the 0x016D→0x01F2 format change occurred, so historical-version compatibility remains uncertain even though the selected source branch is clear. The caller passing the online flag is in unpinned `guild.cpp`; timing, recipient semantics, and replay remain open. No discovery row is closed.
