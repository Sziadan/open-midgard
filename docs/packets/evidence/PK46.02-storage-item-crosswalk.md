# PK46.02 selected personal-storage and item requests

The lengths and registered offsets below come from the pinned MAIN 20080910 registry. Parser descriptions use the inspected local `clif.cpp` with SHA-256 `76c1c4202040daab90f2e441ffad05d9b9ce612d2a16edba55d2926c83ccbb6e`, which differs from the PK01.02 pin.

## PK46.02-PERSONAL-STORAGE-REQUESTS

- `0094` deposits an inventory item. The selected 14-byte request has a two-byte index at offset 7 and four-byte quantity at offset 10.
- `00F7` withdraws a storage item. The selected 22-byte request puts the index at offset 14 and quantity at offset 18. Both transfers zero their padding. The server interprets the deposit index relative to inventory's two-slot offset and the withdrawal index relative to storage's one-slot offset.
- `0193` is the two-byte close request. The parser dispatches closure by the open storage context. Replay checks the storage-open guard and exact request, and the transfer fixture verifies cleanup through the server close reply.

Production transfer replay checks stale item identity, quantity clamping, withdrawal rejection and retry, and ordered inventory and storage updates. [Storage transfer evidence](PK46.02-storage-transfer-requests.md)

## PK46.02-ITEM-ACTION-REQUESTS

- `0439` is the eight-byte PacketVer23 use-item request, with a two-byte inventory index at offset 2 and four-byte AID at offset 4. Replay captures the selected frame and checks use-result ownership. The registry also accepts `009F` as the 14-byte use-item layout with offsets 4 and 10, which matches the PacketVer22 builder. That variant retains its existing C2S identity and requires a dedicated production capture. The explicit Legacy profile uses a six-byte pickup under `009F` and compact item use under `00A2`. Both conflict with the selected registry and need a matching server profile.
- `00F5` is the selected eight-byte pickup request, with ground object GID at offset 4. `0116` is the ten-byte drop request, with two-byte inventory index at offset 5 and two-byte quantity at offset 8. Replay captures the requests and checks the corresponding item lifecycle.
- `00A9` sends the two-byte inventory index and requested equipment location at offsets 2 and 4. `00AB` sends just the inventory index at offset 2. Replay captures both and checks server-confirmed state changes.

The selected request identities preserve the discovery owners. Live storage and item actions, alternate profile verification, and PK48 independent review remain open. [Item action verification](PK38.04-item-action-verification.md)
