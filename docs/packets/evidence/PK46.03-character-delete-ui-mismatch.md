# PK46.03 — reachable character-delete request mismatch

PacketVer23 now uses the selected layout. [Current deletion replay](PK46.03-character-delete-selected-replay.md)

Date: 2026-11-05. Status: current UI path and selected-server layout compared; incompatible request retained as open. No discovery row is closed.

`UISelectCharWnd::ActivateDelete` resolves the selected occupied slot and sends `LoginMsg_RequestDeleteCharacter` with both slot and character index. `CLoginMode` verifies connection and that the index still maps to the requested slot, stores the character GID/slot, and enters `LoginSubMode_DeleteChar`. On that transition it rejects a missing GID/slot, shows a wait message, then serializes `PACKET_CH_DELETE_CHAR`: packet ID from the active character profile, GID, and a 40-byte key copied from the configured email address. The struct is 46 bytes total. The path sends immediately when the delete submode is entered; this observed path has no separate confirmation step. Disconnection, stale/invalid slot, missing GID, and local send failure stop the request and update status.

The current profile constant is `0x0068` and the local packet is the 46-byte older layout. The selected 20080910 character-server contract PK44.CHAR-DELETE specifies `0x01FB`, 56 bytes, GID at byte 2 and a 50-byte key at byte 6. Thus the occupied-slot UI reaches a request whose opcode, length, and key layout do not match the selected server. Do not relabel it compatible or change the shared profile based on this trace; a target-specific layout/profile plus production replay and UI-result lifecycle are still needed. This is evidence of a reachable mismatch, not a recommendation to enable immediate deletion. No discovery row is closed.


## Direct client/server packet-size recheck — 2026-11-05

`src/network/Packet.h:318-322` defines the client `PACKET_CH_DELETE_CHAR` as opcode plus GID plus `key[40]`; its static assertion at line 741 fixes size 46. `src/gamemode/LoginMode.cpp:1868-1873` sends `sizeof(pkt)` and copies the account email into that 40-byte field. `src/network/MapSendProfile.cpp:44-53` selects the `PacketVer23LoginChain` delete opcode for the character profile. The selected rAthena parser `src/char/char_clif.cpp:1356-1365` receives the selected fixed packet, copies its key into `email[40]`, and validates that email. The PK44 contract therefore expects opcode `0x01FB` and 56-byte `key[50]`, while current client sends `0x0068` and 46-byte `key[40]`; the previous contract sentence saying the client sent a 56-byte struct was incorrect and has been fixed.

Do not patch this destructive request in the broad PK46.03 trace. The fix needs a version-specific packet ID/layout and independently derived fixtures for the configured PacketVer22/PacketVer23 peers; the current `MakeCharacterProfile` takes the same PacketVer23 IDs for both profile IDs. Keep `PK44.03.006` and all discovery classifications open for focused implementation/review.
