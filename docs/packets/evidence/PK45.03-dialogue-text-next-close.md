# PK45.03 — NPC dialogue text, next, and close leaves

Date: 2026-11-04. Status: client and selected-server packet paths traced; script state observations are from unversioned npc.cpp, and replay remains open. No rows closed.

## Receive framing and handlers

The client size profile marks 0x00B4 as variable length and 0x00B5/0x00B6 as fixed 6-byte packets. The receive router maps these to `HandleNpcDialogText`, `HandleNpcDialogNext`, and `HandleNpcDialogClose` respectively. The 0x00B4 handler requires at least 8 bytes, reads NPC ID u32 at offset 4, extracts a string at offset 8, and appends it to `UISayDialogWnd`. The next and close handlers require 6 bytes and read NPC ID u32 at offset 2.

The next handler remembers the NPC conversation, hides menu/input windows, and calls `UISayDialogWnd::ShowNext` when that window exists. The close handler remembers the ID and hides menu/input windows; if a visible say window exists it calls `ShowClose` and returns, otherwise it releases the conversation lock and closes NPC dialog windows.

## Outbound handoff

The say dialog UI sends `GameMsg_RequestNpcNext` for its next action and `GameMsg_RequestNpcCloseDialog` for close. The sender serializes 0x00B9 as a fixed `PACKET_CZ_NPC_NEXT_CLICK` (6 bytes: opcode and NPC ID), and the close sender uses the corresponding fixed NPC-close structure. Both reject NPC ID 0. The close sender clears `m_isOnQuest` and `m_lastNaid` before validating the ID and attempting the send, so cleanup also occurs when the ID is invalid or send fails; whether that is intended depends on the quest/dialog lifecycle contract.
