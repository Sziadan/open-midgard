# PK45.03 — broadcast and battlefield chat notifications

Date: 2026-11-04. Status: client and selected-server prefix paths traced; extra legacy client prefixes remain reachability-unresolved. No rows closed.

## Broadcast variants

The receive profile maps 0x009A basic and 0x01C3 colored broadcast; both are variable-length framed. `HandleBroadcast` parses the active variant, ignores empty parsed text, updates `m_broadCastTick`, and records the result in the broadcast chat channel.

For 0x01C3, the parser reads RGB bytes at offsets 4–6, skips to text at offset 16, and uses the default color when the packet is shorter than 16 bytes (resulting in empty text/no record). For 0x009A, it extracts a raw string at offset 4 and heuristically recognizes legacy prefixes: `micc` embeds a 24-byte talker plus hex color and body; `tool` embeds a hex color; `blue`/`ssss` select a yellow color; another hash/colon pattern is handled later in the same parser. These branches do not have selected-server source/capture proof in this pass.

## Battlefield chat

The packet-size table marks 0x02DC variable length and registers `HandleBattlefieldChat`. It requires at least 32 bytes, reads actor AID u32@4, records the actor tick, extracts text at offset 32, and records only nonempty text in the battlefield channel with a fixed configured color.

## Review boundary

The colored broadcast's RGB byte order, skipped bytes, accepted text offset, and legacy prefix heuristics should be tied to the selected emitter before normalization changes. Battlefield sender/text offsets and color/channel semantics also need source parity. Replay each broadcast prefix, empty/short/invalid color payload, battlefield message with sender GID, and non-ASCII text. No rows are closed.

## Selected server broadcast emitters (2026-11-04)

Pinned `clif_broadcast` confirms the legacy `0x009A` payload starts with message bytes at offset 4. For `BC_BLUE` it prepends the literal `blue`; for `BC_WOE` it prepends `ssss`; otherwise it sends the message unchanged. It drops messages shorter than two bytes and uses the requested send target. This corroborates those two client legacy-prefix branches but does not explain the client’s `micc`/`tool` variants, which remain subject to stronger source/capture review.

Pinned `clif_broadcast2` confirms the `0x01C3` 16-byte prefix: packet type/length, uint32 fontColor, then font type, size, alignment and y as four int16 fields, followed by message bytes. This matches the client’s text offset 16 and color field location. The selected source confirms framing but replay is still needed to verify RGB byte order, rendering, and truncated-message behavior. No discovery row is closed.


## 0x009A selected-emitter reachability boundary (2026-11-04)

The packet inventory names `clif_broadcast` as the selected server emitter for 0x009A. In the pinned 20080910 source it rejects messages shorter than two bytes, prefixes `BC_BLUE` with `blue`, prefixes `BC_WOE` with `ssss`, and otherwise copies the original message (`src/map/clif.cpp:6711–6745`). It does not construct the client parser's `micc` or `tool` prefixes. Therefore those parser branches are not shown reachable from the selected emitter; treat them as compatibility behavior with unresolved source/capture provenance, not as selected-profile server variants. Ordinary, blue, and WoE framing are source-backed. No discovery row is closed.
