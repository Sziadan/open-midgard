# PK38.03 card composition result ownership

The selected `clif_use_card` sends `017B` with a four-byte header and two-byte equipment indices. `clif_parse_InsertCard` reads `017C` as card index then equipment index. `clif_insert_card` sends the indices in reverse order in `017D`, followed by result 0 for success or 1 for failure. All indices use the inventory namespace with a two-slot offset. `pc_insert_card` suppresses the usual deletion packet, consumes one card, writes the first empty equipment slot, and sends the result. The result owns those local inventory changes.

The client validates list length, bounds and uniqueness before replacing the chooser. A successful submit records the card and equipment IDs and the equipment's four card words. A failed submit keeps the chooser open. Only a matching result retires the request. The client checks the live rows again before applying success, so duplicate results and changed equipment do not consume another card. Map changes and game mode exit retire the request and chooser. Some server rejection branches send no result. The client retains one in-flight request to avoid confusing it with a later request for the same slots.

Production replay uses the inventory action to send `017A`, dispatches `017B`, and double-clicks the chooser row to send `017C`. It checks the exact request bytes, rejects duplicate list indices, and verifies that equipment worn after the list arrived leaves the chooser open. The resulting pending request drives the unsolicited, mismatched, unknown, duplicate and successful result checks. A separate receive fixture covers equipment replaced before the result. The client recognizes the selected server's inventory item type 6 as a card, with the item metadata table available for older rows.

The render fixture dispatches a literal `017B` through the production router, verifies the offered equipment label paints in native and Qt, and captures both presentations. A click through the native window manager's input path closes the chooser and clears the selected card.

## Recovery after a silent rejection

The selected server's map parser processes packets in TCP order. `clif_parse_InsertCard` calls `pc_insert_card` synchronously, which emits `017D` during processing when it sends a result. The selected `0089` time request is handled by `clif_parse_TickSend`, the sole caller of the `007F` time reply. The client requests a time reply after a pending `017C`. If the matching time reply arrives while composition is still pending, the server has processed the submission and the client can release it. This avoids retries based on elapsed time.

The connection tracks time requests in send order so an earlier reply cannot retire the card request. Time requests wait until the load-end acknowledgment is queued because the selected server can discard time requests before map entry. Replay checks that gate, the actual time request packets, an earlier reply that leaves the request pending, and a later reply that allows card use again without consuming anything. Live carding and map-entry timing remain to be verified against the deployed server.
