# PK45.03 — guild emblem image 0x0152

> Current disposition — 2026-11-05: Stronger security/source review found bounded inflate but incomplete pre-cache BMP validation, not a demonstrated Qt decoder exploit. Use the temporary validate/decode/commit and cache/pending-race matrix specified in the primary review. See [second review](REVIEW-2026-11-05.md).

Date: 2026-11-04. Status: variable framing, bounded inflate/BMP checks, storage and pending-request match traced; image safety and profile contract need stronger review. No rows closed.

Opcode 0x0152 uses variable-size framing and routes to `HandleGuildEmblem`. The handler requires data and packet length greater than 12, reads guild ID u32@4 and version u32@8, and rejects guild ID zero. It zlib-uncompresses bytes from offset 12 into a 65,536-byte output buffer. It rejects inflate failure, output shorter than 54 bytes, non-`BM` signature, width other than 24, or height other than +24/-24. Accepted bytes are resized to the produced output size and stored in `m_guildEmblems[guild]` with the received version. The handler then erases that guild's emblem-request tick.

A pending local emblem update is treated as confirmed only when the pending guild matches, received version differs from pending version, compressed payload length equals the pending payload length, and the received compressed bytes exactly match. On that match, pending guild/data are cleared and a system notice is shown. Otherwise the received emblem is stored without that confirmation notice. No network reply is sent in this handler.

Defer image contract and race review to a stronger agent: these checks do not validate all BMP header/stride/pixel fields, and pending confirmation depends on byte-for-byte compressed payload equality plus a changed version. Confirm selected-server field offsets, version semantics, request timeout behavior, malformed/oversized image handling and UI consumption with fixtures/replay. Coverage routing remains provisional; no independent fixture or production replay was performed.

## Selected server emblem emitter follow-up (2026-11-04)

The pinned `clif_guild_emblem` emitter confirms the variable `0x0152` header: packet length u16@2, guild ID u32@4, emblem version u32@8, then exactly `emblem_len` compressed bytes at offset 12. It sends directly to the requesting session and returns without a packet when `emblem_len <= 0`. This matches the client’s offset/length interpretation and its pending-upload byte-for-byte confirmation path. The server source establishes the wire boundary but does not establish that arbitrary compressed payloads inflate safely or form valid BMPs; those image-validation and bounds questions remain for stronger security review and malformed-input testing.

No discovery row is closed. Runtime transfer/caching/UI refresh behavior remains open.
