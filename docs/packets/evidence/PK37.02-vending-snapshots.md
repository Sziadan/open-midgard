# PK37.02 selected vending snapshots

`clif_vendinglist` and `clif_openvending` in the selected rAthena `src/map/clif.cpp` send `0133` and `0136` with an eight-byte header and 22-byte rows. The selected date precedes the extra vendor ID and random-option fields. Both rows begin with a 32-bit price. The buyer list puts quantity before cart index and the owner list reverses those two words. Each row then carries item type, item ID, identification, damage, refine, and four card words. `MAX_VENDING` is 12. The cart has 100 slots and `client_index` adds two.

The client stages all offers before replacing the buyer or owner list. It accepts zero prices and rejects invalid list size, absent owner, out-of-range and repeated cart indices, invalid quantity, and zero item ID. Repeated indices make purchase row selection ambiguous because `0134` identifies the row by cart index. An invalid replacement preserves the previous quote, including seller and stock.

Packet replay sends a buyer list with the highest valid cart index and a zero price, rejects a duplicate-index replacement and an out-of-range replacement, and checks the exact purchase frame against the retained quote. The Qt commerce detail fixture uses valid cart indices for both layouts.

## Purchase replies and seller reports

`Ref/UIItemWnd.cpp::UIMerchantItemPurchaseWnd::SendMsg` closes the buyer windows after submission. The selected `vending_purchasereq` issues `0135` on failure branches. Successful purchases send inventory and balance changes directly. `0135` has no seller field, so the client shows known failure notices in chat and leaves any open quote untouched. After a successful send the client retires the submitted quote and requires a fresh list for another purchase. Failed sends preserve the current quote.

The selected `0137` carries the seller's cart index and quantity in six bytes. The seller handler checks active vending, slot identity, and available quantity before updating the offer and its detail count. Inventory and cart mutations remain with their own packets. It announces the sale and requests shop closure on the last row, following the sold-out action in `Ref/GameModePacket.cpp::Zc_deleteitem_from_mcstore`. Replay exercises a late `0135` after a replacement quote, a report exceeding the listed amount, partial sales, and the exact sold-out close request. Live buyer and seller verification remains open.

## Opening and cancellation

`clif_parse_OpenVending` clears the server's setup state on `01B2` with flag zero before checking the title. `clif_parse_CloseVending` closes a shop that is already active. Canceling an in-flight open sends `012E` followed by the empty flag-zero `01B2` in one queue operation. The first request covers a successful open and the second clears any setup left after a rejected open. The client suppresses late owner lists after explicit close until fresh `012D` setup or map reset. Ordinary setup cancellation sends only `01B2` and ordinary active closure sends only `012E`.

The selected server sends `0136` on open and uses `0110` on several failure branches. `clif_openvending_ack` is gated to 20141022 or newer, so legacy `0138` no longer changes selected-profile state. Replay verifies the ordered cancel bytes, late `0136` suppression, a fresh setup, and a legacy acknowledgment that leaves the active shop intact. Live rejection paths that return without a skill failure still need verification.
