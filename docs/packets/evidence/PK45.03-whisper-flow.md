# PK45.03 — whisper request/message/ack flow

Date: 2026-11-04. Status: client request and receive paths traced. Server size/content limits and acknowledgment correlation remain open. No rows closed.

## Outbound request

The active legacy send profile selects whisper opcode 0x0096. `SendWhisperChatMessage` rejects empty names/messages and target names longer than 24 bytes, then builds a variable packet of 28-byte header plus message and NUL: opcode@0, total length u16@2, fixed name bytes@4..27, message@28. It permits any message length that fits the u16 packet length. After a successful send, the command path stores the target and message as the single `m_lastWhisperName`/`m_lastWhisper` pending pair.

## Incoming message and acknowledgment

The size table marks 0x0097 variable length and 0x0098 fixed at 3 bytes. The 0x0097 handler requires at least 29 bytes, reads a fixed 24-byte sender name at offset 4 (truncated at the first NUL), extracts text from offset 28, strips inline color codes, stores the latest sender/message, and displays a whisper chat line. The 0x0098 handler reads a status byte at offset 2. Status 0 echoes the stored latest outbound whisper as `(To name) text`; nonzero status displays a generic delivery-failed message.

## Open correlation and bounds

The reply carries no request ID, while client state stores only one latest outbound whisper. A second send can replace pending state before the first acknowledgment; a duplicate success acknowledgment can echo the same message again because the handler does not consume/clear the pending pair. Verify whether the server serializes whisper request acknowledgments and whether one outstanding request is an enforced invariant. Also confirm server message byte/character limits and the accepted fixed-name boundary; client only caps the name at 24 bytes and message at the u16 packet maximum. Replay overlapping sends, out-of-order/duplicate acks, non-ASCII names/messages, and maximum lengths before closure. No rows are closed.

## Selected server whisper limits and ack semantics (2026-11-04)

The pinned packet registry confirms outbound `0x0096` is variable length with length@2, fixed target name@4, and message@28. For the selected pre-20151001 profile, `clif_process_message` requires a NUL-terminated target within the 24-byte name field and a NUL-terminated message whose declared length exactly matches its string length plus terminator; it rejects messages above `CHAT_SIZE_MAX-1`. This is stricter than the client’s u16 packet-length ceiling. In particular, a name that fills all 24 bytes without a NUL is rejected server-side even if the client send helper allowed it through.

The pinned acknowledgment emitter sends `0x0098` with only a result byte to SELF: 0=sent, 1=target offline, 2=ignored by target, 3=target ignores everyone. The client’s result messages align, but the ack carries no request identifier, confirming that two outstanding whispers cannot be reliably correlated by this protocol alone. Incoming `0x0097` uses sender name[24] followed by message; the emitter includes no newer admin/character-ID fields for PACKETVER 20080910. Server processing also rejects malformed/no-message packets before recipient delivery.

These source traces resolve the selected packet shape and bounds. Exact CHAT_SIZE_MAX value/config, inter-map ordering, send-failure correlation, and replay remain open. No discovery row is closed.
