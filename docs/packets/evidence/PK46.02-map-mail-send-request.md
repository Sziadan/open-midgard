## Historical trace

Date: 2026-11-05. Status: client frame, selected legacy server parser, send guards, attachment sourcing and client result handling are source-traced. Character-service delivery ordering and boundary/retry replay remain open. No row closed.

`Commerce::Action(mail)` rejects a pending send, empty/over-23-byte recipient, empty/over-39-byte subject, or body over 254 bytes. It serializes a variable `0x0248` frame of `69 + body.size() + 1` bytes: total length u16@2, recipient in the zero-padded 24-byte field @4, subject in the zero-padded 40-byte field @28, body-length byte @68 (`body bytes + NUL`), and body @69 with a trailing zero from vector initialization. A successful send sets `mailPending` and waiting status; failed send leaves that flag unset.

The selected final registry assigns variable-length `0x0248` to `clif_parse_Mail_send` with positions `2,4,28,68,69,0` (`PK01.02-server-registry-final.csv:292`). In the selected `PACKETVER=20080910` branch, the parser requires a live char-server connection and a declared packet length of at least 69, then calls `mail_send` with recipient, title, one-byte body length and body at those registered offsets (`src/map/clif.cpp:16817-16830`). No attachment fields are serialized in 0x0248: the server sources attachment/zeny from its existing `sd->mail` draft (`src/map/mail.cpp:488-512`). The server checks mail throttle/daily quota, clamps body length to `MAIL_BODY_LENGTH`, validates attachments, and hands the message to `intif_Mail_send`; an immediate handoff failure runs `mail_deliveryfail` and refunds attached items/zeny before reporting failure (`mail.cpp:414-435,462-522`). The selected legacy result packet 0x0249 is three bytes; its result byte is `1` on failure and `0` on success (`src/map/clif.cpp:15963-15969`, `GronPacket.cpp:204`). Client receive handling clears `mailPending`, reports the result, and closes the composer only on success (`Commerce.cpp:87`). This is a source trace of the request/result contract, not proof of char-server persistence or recipient delivery; the exact asynchronous success path and message durability need separate evidence. The companion `PK46.02-map-mail-window-request.md` also records the unresolved `0x0246` draft-state behavior that precedes composition.

Replay recipient/subject/body byte boundaries, non-ASCII text, embedded NUL, send failure, server rejection, credit/attachment behavior and duplicate result before closure. Primary ownership remains PK32; no row closed.

- `src/map/mail.cpp` `mail_send` (lines 462-523) rejects trading/cooldown/daily-limit cases, constructs the attachment-bearing message, and calls `intif_Mail_send`. If the char-server link is unavailable at enqueue time, the map server immediately calls `mail_deliveryfail`, which restores offered items/zeny and reports failure. It then sets the mail flood timer.

The response parser (2600-2628) treats `msg.id == 0` as failure; otherwise it notifies the sender of success and optionally saves inventory state.
- `src/char/int_mail.cpp` `mapif_parse_Mail_send` (599-657) validates the internal frame, resolves the recipient name, applies the pre-20150513 same-account restriction, sets mail status, calls `mail_savemessage` for a valid recipient, sends the result to the map server, then attempts a recipient notification. `mapif_Mail_new` suppresses notifications when the message ID is zero.
- `mail_savemessage` (82-158) starts a SQL transaction, inserts the mail row, inserts any attached-item rows, rolls back on row/attachment errors, and returns a nonzero ID after commit. The caller assigns that return value back to `msg.id`, so a persistence failure reaches the map server as a failed result.
