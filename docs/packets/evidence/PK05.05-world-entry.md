# Same-world handoff regression found in deployed login

Date: 2026-11-10. Baseline:3db169c9. Repair subject: `packet(PK05.05): honor same-world mode handoffs`.

The user reported that the current deployment in D:/Spel/OldRO could log in but never display the world. This is a regression, not an expected limitation of the unfinished packet plan.

## Evidence and cause

The latest supplied deployment log, debug_hp_14520.log, shows accepted map entry02EB into prontera.rsw at156,184, GameMode initialization, then0091 requesting the same map/coordinates. The mode continues emitting OnRun heartbeats on the loading screen until normal shutdown. Selected diagnostic lines are retained without account/auth packet bytes. Before repair, deployed open-midgard.exe exactly matched the build artifact SHA256 BB0A0A659DF2906527E49EFC008383D626B0D6B408D0567825247BEA61333230.

The interaction is between the PK05.05 receive preamble added in d3ccc48c2 and the port mode loop. ProcessNetworkUpdate deliberately latches an old mode terminal after an explicit mode-operation generation change, preventing post-handoff world updates/tail dispatch. While the map is still loading,0091 cannot take the already-loaded-map reuse branch and requests Switch(1,"prontera.rsw"). Switch increments the generation; however CModeMgr::Run previously recreated a mode only when type or name differed. That same-world request was ignored, leaving the terminal instance alive forever. OnUpdate returned before AdvanceMapLoading every frame. Weakening the terminal receive guard would mask the ownership defect.

Primary Ref/Mode.cpp1289–1363 corroborates the required behavior: Switch505C00 ends the current mode's inner loop, and Run505AA0 calls OnExit/deletes it and constructs the next instance without coalescing identical names/types. Source excerpts and static selected-PE disassembly are retained; original executable execution was not used.

## Repair and regression

Switch now marks an explicit pending request; the frame-based Run loop consumes it even when type/name match. Consumption occurs before construction/OnInit so a new request from initialization remains pending. The existing terminal receive latch, operation generation, same-map-already-loaded reuse path and teardown ownership remain unchanged. A diagnostic log records application of the request.

The real Run loop has optional factory/loading presentation services, with normal production defaults. The regression uses that exact loop and production CRagConnection/0091 framing/router/ProcessNetworkUpdate; only mode construction and loading presentation are lightweight. It sends same-world0091 plus a queued007F tail. The old mode must stop before that tail, retire once, and the replacement must process the tail and continue on a second stable update without repeated reloads. No real map assets or live server are required. The full replay also preserves prior terminal failure/EOF/acknowledgement and map-lifetime tests. The fixture saves/restores pending WM_QUIT state from earlier shutdown cases.

Deploy-off all-target build passes. Full root157/157 in38.56s; standalone470/470 in14.60s. The dedicated production-loop replay reports PASS. The built application is at build-mingw-preset/open-midgard.exe; its SHA256 and all source/test inputs are pinned in the adjacent provenance JSON. Plan consistency passes separately.

The deployed OldRO executable was read only and retains its original hash. No live login or world rendering was retried. The repair therefore proves the reported deadlock path is removed, while actual live entry needs a retry after redeploying the new build. No broad PK48/49/deployed acceptance is claimed.
