# PK46.02 — NPC shop deal-type request 0x00C5

Date: 2026-11-05. Status: buy/sell choice action, request guards, selected server shop checks and list responses are source-traced. Invalid nonzero type bytes are source-confirmed to select the sell-list branch; production replay and lifecycle remain open. No discovery row is closed.

## User action to sender

`UIChooseSellBuyWnd` sends `GameMsg_RequestShopDealType` with type 0 for Buy or 1 for Sell. `GameMode` passes that value to `RequestNpcShopDealType`, which rejects a missing shop NPC or a type above 1, takes the NPC ID from current session state, fills the request and sends. The sender returns the transport result and does not optimistically switch shop-list state.

## Client layout and profile

`PACKET_CZ_ACK_SELECT_DEALTYPE` contains opcode `0x00C5` (offset 0, 2 bytes), shop NPC ID (offset 2, 4 bytes), and deal type (offset 6, 1 byte), for seven bytes total. The sender selects `LegacyNpcShopSend::kSelectDealType` (`0x00C5`).

## Selected registry comparison

`PK01.02-server-registry-final.csv` maps opcode `00c5` to fixed length 7 and `clif_parse_NpcBuySellSelected`. The parser silently returns while trading; otherwise it passes the requested NPC ID and type byte to `npc_buysellsel`. That routine rechecks same-map proximity, NPC visibility and dynamic-hidden state, and requires `NPCTYPE_SHOP`. It stores the accepted NPC ID as `npc_shopid`; type 0 sends the buy list, while every nonzero value sends the sell list. Unlike the client guard, the selected server does not restrict the byte to 0 or 1. Wrong shop subtype is logged and can clear the active NPC dialog ID when it matches the requested ID. There is no generic acknowledgement; the selected buy/sell list is the response.

The server does not require the selected shop ID to equal the client session's current `npc_id`; proximity and shop-state checks authorize the selection. Repeated requests can replace `npc_shopid` with another eligible nearby shop. The client sender rejects type >1, but `npc_buysellsel` validates the nearby visible shop, stores `npc_shopid`, and branches only on `type == 0`; any nonzero type, including 2 or 255, dispatches `clif_selllist` (`src/map/npc.cpp:2387-2417`; `src/map/clif.cpp:12258-12269`). Invalid values therefore open the sell-list response instead of being rejected server-side. Existing [PK45.03 deal-type evidence](PK45.03-npc-shop-deal-type.md) covers the broader server contract; this note connects the present UI action and flags the type-domain mismatch for replay.
