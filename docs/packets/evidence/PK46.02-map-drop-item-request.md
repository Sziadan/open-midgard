# PK46.02 — inventory item drop request

Date: 2026-11-05. Status: drag/action path, selected request/parser and basic/extended removal-ack effects are source-traced, including that unmatched positive removal notifications still reach inventory deletion. Stale/duplicate effects and production byte replay remain open. No discovery row is closed.

## User action and local gates

`UIWindowMgr::OnLBtnUp` recognizes an inventory-item drag released outside a window. A single item sends `GameMsg_RequestDropInventoryItem` immediately; a stack opens the numeric prompt and sends the same message with the chosen amount. `RequestDropInventoryItem` rejects zero index/amount, absent or nonpositive inventory entries, equipped items, and a second request while an item-throw acknowledgement is pending. It clamps the request to the available stack count and a 16-bit maximum. After a successful send it records the item index as pending; a matching basic inventory-removal notification clears that wait, then removes the indicated amount from the session inventory.

## Client and selected server wire contract

All configured map gameplay profiles select drop-item opcode `0x0116`. The client sends `PACKET_CZ_ITEM_THROW`, 10 bytes: opcode u16@0, three initialized padding bytes@2–4, item index u16@5, padding byte@7, and amount u16@8. The selected effective `PACKETVER=20080910` registry in the PK01.02 hash-pinned `src/map/clif_packetdb.hpp` has `0x0116`, length 10, parser `clif_parse_DropItem`, field offsets 5 and 8. Those client offsets and total length match.

The selected parser reads the wire index at offset 5 and subtracts 2 before calling `pc_dropitem`; it reads amount at offset 8. It refuses the action when the player is dead, cannot act, is in an NPC dialog, has a status that forbids dropping, or `pc_dropitem` fails. On failure it sends `clif_dropitem` for that index with amount zero. A successful `pc_dropitem` returns without that failure notice. This traces the selected server action branch without inferring its deeper inventory/ownership rules.

No independent byte fixture or production replay was run. The selected 20080910 failure result is the basic 0x00AF count-zero acknowledgement; the client now clears its matching pending request without deleting the inventory row. Successful removal/UI behavior remains source-traced but needs replay. The selected wire identity/layout and zero-count failure behavior now match at source level; no discovery row is closed pending byte replay and independent review.


## Selected failure acknowledgement follow-up (2026-11-04)

The selected `clif_delitem` branch also emits the basic 0x00AF `PACKET_ZC_ITEM_THROW_ACK` form; 0x07FA is gated to PACKETVER >= 20091117. `HandleItemRemove` now clears the matching pending throw index and returns without changing inventory when a basic 0x00AF acknowledgement has count zero. Positive counts still remove the acknowledged amount. Source behavior is traced; server/client byte replay remains open.

## Removal-ack correlation follow-up

`HandleItemRemove` reads the basic active form's item index/count at offsets 2/4, or the extended form's fields at 4/6. It clears `m_waitingItemThrowAck` only when the item index matches, then special-cases basic `0x00AF` with amount zero as a failure correction that must not remove inventory. All other forms continue to `RemoveInventoryItem` without requiring a matching pending index (`src/gamemode/GameModePacket.cpp:2659-2695`). Thus a positive unsolicited or late removal notification can mutate the inventory cache despite not matching the outstanding throw item; production stale/duplicate-ack replay remains necessary.

## PK38.02 production replay

A valid map change retires the pending drop and hides the drop amount prompt. The removal handler validates frame lengths, slot bounds, and the server stack limit. An extended `07FA` with zero count leaves inventory and pending drop state intact. Positive removals still apply to the indexed row and refresh the dependent windows. Its positive delta carries no item ID or request identifier, so the client cannot distinguish an identical duplicate from a second removal.
