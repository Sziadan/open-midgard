# PK46.02 — actor-name request 0x008C profile branch

Date: 2026-11-05. Status: selected request profiles and version-specific server response layouts are source-traced; client GID cache/timer behavior is documented. Runtime replay and visible cache acceptance remain open. No row closed.

The selected modern map-send profiles use 0x008C for actor-name requests. Hover lookup rejects GID 0 and the local GID, applies a per-GID 1000 ms cooldown, then sends `PACKET_CZ_REQNAME2`: opcode u16@0, five padding bytes @2–6, GID u32@7 (11 bytes total). `FillPacketPadding` derives four ASCII hex characters from `timeGetTime()` and leaves the last padding byte zero. Successful sends update the per-GID timer; failure does not. A proactive request path uses the same frame and cooldown after a newly received actor lacks resolved identity, but defers proactive requests when the PacketVer22 receive profile requires it.

The legacy map-send profile instead uses 0x0094 with a 6-byte opcode+GID frame; in that legacy profile 0x008C is global chat. Keep those profile meanings distinct. The selected final registry assigns 0x008C length 11 to `clif_parse_GetCharNameRequest` with GID at offset 7 (`PK01.02-server-registry-final.csv:374`), matching the modern client struct. This confirms the selected modern request branch, not the legacy 0x008C meaning.

Trace the corresponding name response correlation/cache lifecycle and replay padding/profile cases before closure. Primary ownership remains PK50; no row closed.

## 2026-11-04 — selected server response and client cache continuation

The selected server source is available at `C:\Users\sziad\source\repos\rathena-master\src\map\clif.cpp`. `clif_parse_GetCharNameRequest` reads the signed GID from the packet profile's configured offset, normalizes a negative self-ID for disguises, then resolves the block. It silently ignores a missing block and requests outside the same-map `AREA_SIZE` range; otherwise it calls `clif_name(sd, bl, SELF)`. Thus the request does not produce a not-found/error acknowledgement for stale or out-of-range IDs.

For player blocks, `clif_name` sends `PACKET_ZC_ACK_REQNAMEALL` (`HEADER_ZC_ACK_REQNAMEALL`) with the block GID and the fake name when present, otherwise the character name. Party and guild fields are filled when applicable. NPC/monster-like blocks use the separate `PACKET_ZC_ACK_REQNAMEALL_NPC` format. This confirms server response generation for a resolvable in-range block; the exact selected-profile response opcode/length still depends on the packet-version struct selection and should be checked against PK01.02 before claiming full wire equivalence.

On the client, the active receive profile registers its basic, party and full actor-name acknowledgement IDs to `HandleActorNameAck`. The handler requires at least 30 bytes, reads GID at offset 2 and a 24-byte name at offset 6, rejects zero GID or empty name, updates both name maps, and erases `m_actorNameByGIDReqTimer[gid]`. For the full response only, if length is at least 102 bytes, it also reads party/guild/title fields at offsets 30/54/78. This is per-GID timer cleanup, not a one-to-one outstanding-request token: unsolicited and late acknowledgements can populate the cache and clear a current cooldown entry. No explicit generation check is present in this handler.

### Packet-version resolution

The selected server is configured for 20080910, below the packet-struct thresholds at `src/map/packets_struct.hpp:3563` and `:3586`. Therefore its player response takes the `#else` `PACKET_ZC_ACK_REQNAMEALL`: ID 0x0195 and 102 bytes (`u16` ID, `i32` GID, then four `NAME_LENGTH` fields). Its NPC-like response takes the `#else` `PACKET_ZC_ACK_REQNAMEALL_NPC`: ID 0x0095 and 30 bytes (`u16` ID, `i32` GID, one name field). This matches the client full handler's 102-byte threshold/offsets for player names and its basic 30-byte parse for NPC names. The client also registers 0x0194 as a party acknowledgement ID, but this selected server struct does not emit that ID from `clif_name`; its presence is an accepted profile alias, not evidence of this server's player response.

This resolves the selected server response ID/length for the two `clif_name` variants at source level. The 0x0195 server's fourth name field is `position_name`; the client stores it in `guildTitle`, so this is a field-label mapping that still needs replay/visible-cache validation. The newer title-ID layout is not selected by this server version. Runtime replay and rendered cache acceptance remain open.
