# PK46.03 — account-login send selection and gates

Date: 2026-11-04. Status: current client selection/gates traced; service/profile applicability and security review remain open. No discovery row is closed.

After a successful account-server connection, `LoginMode` sends optional `0x0200` connect-info first only when `Login.SendConnectInfoChanged` is nonzero (default false). It then attempts `0x0204` executable-hash only for Korea/Indonesia service types or when a client-hash override/source is configured; an unusable hash payload suppresses that send. Finally, it either requests a password hash with `0x01DB` or sends a direct account-login variant. The hash-request gate is always true for the Login3 selection, otherwise controlled by `Login.ForcePasswordHashRequest`, falling back to `g_passwordEncrypt`.

`Login.AccountLoginPacket` can select plain/legacy `0x0064`, channel `0x02B0`, PC-bang `0x0277`, Login3 `0x01FA`, or Login4 `0x027C`. Invalid nonempty values are logged and fall back to the service default. Without an override, channel login is selected only when `Login.ForceLoginChannel` is configured nonzero or the service is Korea; otherwise the profile uses legacy login. Login3 routes through the `0x01DB` challenge first. On challenge receipt, the client computes MD5 over challenge bytes and password in an order controlled by `g_passwordEncrypt2`; Login3 then sends `0x01FA` with a byte-range-checked selected client-info index, while other hash-login modes send the profile's `0x01DD` packet. An unencodable Login3 client-info index resets the handshake, disconnects, and returns to the login submode. Client type can be overridden with a byte-range-checked `Login.ClientTypeOverride`; otherwise it uses the active account type. The source-backed layouts and current-client byte captures for these variants are cross-referenced in `PK44.LOGIN-REQUESTS.md` and the PK44.04 login-request direction evidence.

These gates establish what the current executable can attempt under local settings; they do not establish the deployed service's expected variant, credential policy, or complete challenge/result lifecycle. The `0x0825` SSO registration has no current-client sender in the reviewed path and remains unsupported/unproven; do not infer that support from server registration. The existing Login4 `macData` security question and Login3/hash security semantics need the stronger review already called out by PK44. No production UI lifecycle replay or new byte capture was performed here; no discovery row is closed.

## Pre-auth send failure control-flow recheck (2026-11-05)

The connect-account branch invokes optional `SendConnectInfoChanged`, then `SendExeHashCheck`, then the selected password-hash or direct-login path without branching on the helper results. The 0x0200 and 0x0204 helpers log and return on send failure, so those failures do not stop the subsequent auth path. `SendPasswordHashRequest` commits its waiting/timestamp flags only after a successful send; failure returns before those mutations. `LoginMode.cpp` SHA-256: `0f5a4b4279007e2aa85d39a1dd9ac6c0bb2bf191b1b77b6653c1ee1e2f8766f7 (observed by primary review 2026-11-05; historical note did not record a hash)`. Whether the deployed service requires either best-effort pre-auth packet remains open.

## Account authentication failure recovery

The selected login source registers `01DB` with `logclif_parse_reqkey`, which generates a 20-byte session salt and sends it in `01DC` (`src/login/loginclif.cpp`, `src/login/login.hpp`). Login3 requires that challenge before sending `01FA`. At the existing 1500 ms challenge deadline, Login3 closes the account connection and returns to login with a persistent status. A profile with an optional challenge sends its configured direct login once. The receiver ignores unsolicited and repeated challenges and rejects a framed challenge with no salt. Failed sends for the challenge request, direct account request, and challenge response all return to login. The optional `0200` and `0204` sends still precede authentication when enabled.

Replay exercises the configured Login3 and optional legacy challenge paths against local mock account sockets. It checks the deadline, absence of a repeated request, preservation of the account-response status, empty challenge rejection, and a failed challenge-request send. Live login on the selected deployment and character-server recovery remain open.
