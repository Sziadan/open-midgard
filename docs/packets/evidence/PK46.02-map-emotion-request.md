# PK46.02 — client emotion request 0x00BF

Date: 2026-11-05. Status: command parsing, throttle, three-byte send path, selected server gates and client 0x00C0 actor-animation/state handling are source-traced. Production timing and rendered replay remain open. No row closed.

`CGameMode` normalizes chat text to lowercase and passes it to `ResolveEmotionCommand`. Ordinary text returns `-1` and continues through the normal chat/command path; malformed explicit `/emotion` or `/emote` forms return `-2` and stop. Recognized aliases and numeric forms resolve to an ID in the supported 0–80 range. A recognized request is suppressed when a prior successful emotion send was less than 1000 ms ago. Otherwise the client sends bytes `{0xBF,0x00,u8(emotion)}` (fixed 3 bytes); only successful send updates the throttle tick and `m_isReqEmotion`.

The size table fixes 0x00BF at 3 bytes. The selected registry assignment snapshot identifies a 3-byte `clif_parse_Emotion` entry (`PK01.02-server-registry-assignments.txt:57`). The selected server parser rejects values `>= ET_MAX`, blocks `ET_CHAT_PROHIBIT`, applies basic-skill and `PCBLOCK_EMOTION` gates, and broadcasts the accepted emotion in a 7-byte 0x00C0 packet containing GID and type to the area. If dice reshuffling is enabled, IDs in the dice range are randomized before broadcast. A failed skill/action gate emits a skill-fail response rather than an emotion broadcast.

The server enum has 88 values before `ET_MAX` (valid numeric IDs 0–87), while the production client command resolver and 0x00C0 handler accept only 0–80. Current client sends stay in that supported subset, but responses with IDs 81–87 would be ignored by this client.

The server flood check uses integer seconds and rejects when `emotionlasttime + 1 >= time(nullptr)`, then updates `emotionlasttime` on that rejected attempt. Thus a send exactly one second after the prior accepted second can be rejected; by contrast, the client allows a request at exactly 1000 ms since its last successful send. This is a concrete client/server boundary mismatch to replay. Client send failure does not advance its timer; server rate-limit failure does advance its timer.

Replay ordinary chat, valid alias/numeric command, malformed explicit command, exact and just-over 1-second boundaries, send failure, server skill/action gates, and IDs 80/81/87. Verify visible client action/effect mapping before closure. No production replay was performed; primary ownership remains PK47 and no row closed.

## Client emotion-notification effect follow-up

The client registers `0x00C0` as seven bytes and routes it to `HandleEmotion` (`src/network/GronPacket.cpp:107`, `src/gamemode/GameModePacket.cpp:8968`). The handler drops missing/short frames and emotion IDs above 80, reads actor GID at offset 2 and forwards the emotion ID through actor message 21; it clears `m_isReqEmotion` only when the resolved actor is the local player (`GameModePacket.cpp:6740-6748`). `CGameActor::Am_Action` maps the emotion ID through `EmotionAction`, skips unmapped IDs, and creates the emotion sprite effect; ID 34 uses the chat-prohibition motion (`src/world/GameActor.cpp:5355-5373`, `src/world/Emotion.h:5-12`). This traces client state/effect dispatch, but not successful rendering on production assets. The server valid range 0-87 therefore exceeds this handler's accepted range 0-80, and IDs 81-87 are ignored by this client. Keep asset/rendered verification and the one-second throttle boundary replay open.
