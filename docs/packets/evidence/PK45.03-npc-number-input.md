# PK45.03 — NPC number-input prompt and reply leaf

Date: 2026-11-04. Status: client and selected-server prompt/reply paths traced. Numeric-domain compatibility and UI replay remain open; no rows closed.

## Server prompt and selected layout

PK01.02 pins effective PACKETVER=20080910. The server emits ZC_OPEN_EDITDLG 0x0142 as a packed 6-byte record: opcode@0, NPC ID u32@2. clif_scriptinput builds this packet for the number-entry prompt. The current receive router registers 0x0142 to HandleNpcDialogNumberInput, which validates at least 6 bytes, remembers the NPC conversation, clears pending dialog action/hides the menu, and opens UINpcInputWnd::OpenNumber(npcId).

## Submit reply

The number UI rejects empty input. On submit it routes SubmitAction::NpcNumber as GameMsg_RequestNpcInputNumber with the NPC ID and parsed decimal value. RequestNpcInputNumber rejects NPC ID 0 and sends 0x0143 as 10 bytes: opcode@0, NPC ID@2, value@6. The selected server PACKET_CZ_INPUT_EDITDLG is also 10 bytes with opcode 0x0143, GID@2, and signed int32 value@6. Its packet database registration routes to clif_parse_NpcAmountInput, which stores the value in sd->npc_amount and continues the NPC script with the same NPC ID.

## Cancel reply

For NPC-number prompts, CancelInput closes the NPC dialog windows and sends GameMsg_RequestNpcCloseDialog. RequestNpcCloseDialog sends 0x0146 as 6 bytes with NPC ID@2. The selected server registers this fixed packet to clif_parse_NpcCloseClicked; when an NPC script is active, that parser continues the script with the cancel flag.

## Remaining semantics

The wire widths and offsets match. The client accepts up to ten input characters and parses with `strtoul` into u32; the selected server field is signed int32 and is assigned directly to `sd->npc_amount`. Values in 0..INT32_MAX share the same numeric meaning. Values above INT32_MAX can be interpreted as negative server-side if the UI allows them. The accepted character set, intended script value domain, and overflow behavior need stronger review and replay before semantic parity can be claimed. No row is closed.


## Selected server parser trace (2026-11-04)

For PACKETVER=20080910, the selected server uses the 0x0142 six-byte `ZC_OPEN_EDITDLG` prompt (NPC ID u32@2, `SELF`) and registers 0x0143 as a fixed 10-byte `clif_parse_NpcAmountInput` request (`PK01.02-server-registry-final.csv`, line 134). The request struct is packet type u16@0, NPC ID u32@2, signed int32 value@6 (`src/map/packets.hpp:1829–1834`). The parser stores `p->value` directly in `sd->npc_amount` and continues the NPC script; it does not clamp or normalize the numeric value in this parser (`src/map/clif.cpp:13358–13371`).

On the client, Number mode caps input length at 10 characters (`src/ui/UINpcInputWnd.cpp:358`); submit uses `std::strtoul` and sends the result as u32. This confirms the signed/unsigned boundary. Whether the UI admits values greater than INT32_MAX and how the NPC script expects them remain unresolved; do not add a clamp without establishing those semantics. Cancellation remains a separate 0x0146 dialog-close packet. No discovery row is closed.
