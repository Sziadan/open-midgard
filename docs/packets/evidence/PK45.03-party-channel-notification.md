# PK45.03 — 0x017F guild-chat text notification

Date: 2026-11-04. Status: variable framing and chat-routing behavior traced; server payload semantics and replay remain open. No rows closed.

Opcode 0x017F is variable length and is routed through `HandleGuildNotification`. Its branch checks for at least four bytes, extracts a packet-bounded string beginning at offset 4, and passes it to `RecordChat` with color `0x00B4FFB4` and `kChatChannelParty`. It does not parse a sender ID or update actor chat bubbles in this branch. If the packet is shorter than four bytes it returns without recording chat.

Open work: verify the opcode's server meaning, sender/encoding semantics and empty-string behavior; compare its chat display with the 0x0109 party-chat path; replay valid, empty, malformed, multibyte and non-NUL payloads. No independent fixture or production replay was performed for this leaf.

## Selected server 0x017F guild-chat contract (2026-11-04)

The selected server defines variable-length `0x017F` as `ZC_GUILD_CHAT`, not a party-channel packet. `clif_guild_message` ignores empty messages, bounds payload length to the chat buffer (reserving a NUL terminator), writes packet length plus message and terminator, and sends through `GUILD_NOBG`. It returns without sending if no guild member session is available. This confirms the variable frame includes a two-byte length header and text, but does not include a sender AID in this opcode.

The client currently routes `0x017F` through `HandleGuildNotification` and records the extracted text as chat. The selected server source establishes guild broadcast semantics, but whether the client assigns the correct channel/sender presentation and whether packet-bounded extraction handles empty and terminator cases as intended need focused replay. Treat the “party-channel” label as a client-side classification pending review; no discovery row is closed.
