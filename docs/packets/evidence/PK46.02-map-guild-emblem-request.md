# PK46.02 — guild-emblem request 0x0151

Date: 2026-11-04. Status: two client send paths, six-byte guild-ID frame, shared per-guild throttle, selected server response and client decompression/cache path traced. Missing-emblem and visual replay remain open. No row closed.

The Qt guild-emblem resolver and GR2 emblem-texture resolver both send the same six-byte `0x0151` frame: opcode u16@0 followed by guild ID u32@2 in little-endian order. Both use `mode.m_emblemRequestTicks` and suppress another request for that guild until 5000 ms has elapsed; the timestamp is updated only after a successful socket send. The second path also logs the advertised emblem version, but the request frame itself contains only the guild ID. The shared timer means activity in either resolver suppresses the other path.

The selected registry assignment snapshot identifies length 6 and `clif_parse_GuildRequestEmblem` with the guild ID at offset 2 (`PK01.02-server-registry-assignments.txt:134`). The parser reads that guild ID and responds only when the guild is loaded; `clif_guild_emblem` also returns silently when `emblem_len <= 0`. Otherwise it sends variable-length 0x0152 with guild ID at @4, emblem ID at @8 and compressed emblem bytes at @12. The client registers 0x0152 to `HandleGuildEmblem`, requires a nonempty body after the 12-byte header, decompresses into a bounded 64 KiB buffer, validates BMP signature and 24x24 dimensions, caches the bitmap/version by guild ID, then erases the request tick. Invalid compression/BMP data returns before clearing the throttle entry. Server `emblem_id` is the value occupying the client handler's `version` field; the serialized field positions match.

No-response cases include unknown/unloaded guild and guilds without an emblem. These do not clear the client throttle timer; the normal retry path is therefore delayed by the shared 5000 ms cooldown. The request routine performs no authorization check, and the server returns emblem data for any existing guild ID. Whether this is intended public data is a policy question, not resolved by packet framing. UI cache invalidation/refresh remains separate: the server source itself notes that guild emblem-area updates do not force all emblem-bearing UI components to refresh.

Replay cache hit/miss, failed send, both call paths within the throttle interval, unknown guild, empty emblem, malformed compressed data, guild-ID changes, response arrival/cache replacement and visible refresh before closure. Primary ownership remains PK50; no production replay and no row closed.
