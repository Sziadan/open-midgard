# PK45.03 — authoritative actor position updates

Date: 2026-11-04. Status: client handlers and both selected-server correction variants traced; movement/interpolation replay remains open. No rows closed.

## Receive path

The current receive profile exposes basic actor set-position 0x0088 and high-jump 0x01FF; the packet-size table assigns 10 bytes to both. Both register to `HandleActorSetPosition`. The handler verifies the packet ID is active and requires at least 10 bytes, then reads GID u32@2 and signed X/Y values from u16 fields at offsets 6 and 8. It ensures a runtime actor, records the actor/tick/position, updates the local player position and chase source when the GID is local, clears the local pending move-ack flag, and calls `ApplyRuntimeActorFixPosition` to replace the actor's path position.

The source comment identifies 0x0088 as the Ref `ZC_STOPMOVE` case and describes it as authoritative even when the coordinate matches the current/previous path cell. This prevents the prior walk from continuing when a stop correction arrives before another action. The current profile labels 0x01FF high-jump and routes it through the same position correction handler.

## Selected 0x01FF high-jump emitter (2026-11-04)

The pinned 20080910 server defines `PACKET_ZC_HIGHJUMP` as 10 bytes: packet type u16@0, source ID u32@2, x u16@6, y u16@8, opcode 0x01FF (`src/map/packets.hpp:1193–1199`). `clif_slide` assigns these fields and sends the packet to `AREA`; for disguised actors it follows with a `SELF` copy using `disguised_bl_id` (`src/map/clif.cpp:10100–10115`). Its comment describes an instant visual move even when the destination cell is not walkable, while a sitting actor remains sitting.

`clif_blown` sends `clif_slide` first and `clif_fixpos` second (`src/map/clif.cpp:2190–2196`). The 0x0088 stop-move packet then carries the authoritative actor ID and coordinates to `AREA`, with the same disguised-actor SELF-copy pattern (`clif.cpp:2199–2217`). It enforces walkability and stands a sitting actor. This order explains why the client routes both packets to the same position handler: 0x01FF supplies the visual slide, then 0x0088 supplies the final authoritative correction.

## Additional correction behavior from the shared handler

The active basic 0x0088 and high-jump 0x01FF IDs both register to HandleActorSetPosition, which validates the active packet ID and 10-byte minimum, reads GID u32@2 and signed x/y u16@6/8, and calls the same ApplyRuntimeActorFixPosition path (src/gamemode/GameModePacket.cpp:8297-8336, 8787-8788). The handler treats the correction as authoritative even when it targets the current/previous path cell; for the local player it resets move-request timing/destination and clears the waiting-move-ack flag before applying the position. The fix path makes the actor visible, unregisters its old spatial position, sets source and destination to the corrected tile, collapses movement start/end times, clears moving state, updates world position, resets actor state, re-registers the position, and reapplies concealment (GameModePacket.cpp:7024-7054). This source evidence establishes common packet handling and stop/correction semantics. It does not establish visual interpolation timing or all repeated/cross-packet orderings; those remain replay/runtime checks.
