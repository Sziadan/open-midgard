# PK46.02 — open-vending request 0x01B2

Date: 2026-11-05. Status: open-shop serializer, selected parser, server item/skill validation, success-list response and local pending state traced. The empty flag-0 close action resets pre-vend state without opening a shop. Cross-layer response/rejection lifecycle needs stronger review and replay. No row closed.

The explicit `openVend` action rejects active/pending shops, an empty draft, empty title or title longer than 79 bytes. It builds `85 + 8 * itemCount` bytes: opcode u16@0, total length u16@2, title bytes @4 in an 80-byte field, flag byte @84 set to 1, and each offer record at @85+8k with item index u16, amount u16 and price u32. Each item must still exist in cart state with nonzero amount not exceeding stock and nonzero price. Only a successful send sets `vendingPending`, saves the shop title and shows the waiting status; it does not optimistically set `vendingActive`.

There is a second `0x01B2` send in `Commerce::Action(close)` when the shop is not active: it sends exactly 85 zero-initialized bytes with only the length field set to 85, then clears the draft/pending state and hides the window. That branch has no title, no open flag and does not set `vendingPending`; its intent is unclear and should not be treated as equivalent to `openVend` without review. When a shop is active the close action instead sends 0x012E.

The selected final registry assigns variable-length `0x01B2` to `clif_parse_OpenVending` with positions `2,4,84,85,0` (`PK01.02-server-registry-final.csv:171`). The parser derives offer data length from total length minus the 85-byte prefix. For this 0x01B2 branch, flag 0 clears `prevend` and the work-in-progress state; an empty title then returns before `vending_openvending`, so the client's 85-byte empty frame is a server-side preparation cancel/reset, not an open request. This removes the earlier intent ambiguity.

For a nonempty title, server map/chat restrictions can return before a vending result. `vending_openvending` rejects dead players, missing pre-vend state and trading; requires the vending skill and cart; bounds item count by `MAX_VENDING` and skill level; then filters every cart offer by index/quantity, identification, broken/expired/bound/tradeable status. Prices are capped at `vending_max_value` and aggregate seller-zeny overflow is checked. Any invalid/offending list or other visible validation failure clears prep/work-in-progress and sends failure effects/results. Success sets `state.vending`, assigns seller UID, persists listing data, emits the seller's 0x0136 `ZC_PC_PURCHASE_MYITEMLIST`, and shows the vending board.

The client 0x0136 receive path parses the selected 22-byte entries and marks vending active/pending=false, so this is the selected 20080910 success response. The server's `clif_openvending_ack` body is compiled only for `PACKETVER >= 20141022`; it therefore emits no newer open-store result in the selected build. Some parser/map early returns also send no explicit failure response, so client `vendingPending` can remain set until another state transition. The client's 0x0138 handler does not establish an acknowledgement from this selected server branch.

Replay valid/invalid drafts, title byte boundaries, skill/cart/count limits, invalid cart offers, seller-zeny overflow, map/chat restrictions, 0x0136 success, modern-vs-selected result packet behavior, silent failure/pending cleanup, send failure, and flag-0 empty-frame cancel. Stronger review gate: independently reconcile the 20080910 `0x01B2` parser and `0x0136` response with the client’s two send forms, especially whether every selected-server rejection or lost response can leave local pending state stuck. Exercise flag-0 draft reset and flag-1 open through the real production path before changing completion status; do not infer that a newer result packet applies to this profile. Primary ownership remains PK37; no production replay and no row closed.
