## Follow-up auth-token semantic check — 0x0069 to 0x0065

The prior field-name caveat is resolved for the selected rAthena path. For `PACKETVER 20080910`, `PACKET_AC_ACCEPT_LOGIN` carries `login_id2` at offset 12 (`src/common/packets.hpp:220-240`); `loginclif_auth_ok` writes `sd->login_id2` there (`src/login/loginclif.cpp:114-125`), and the login session obtains that token from `rnd_value(1u, UINT32_MAX)` (`src/login/login.cpp:414`). The client reads bytes 12-15 into `m_userLevel` (`LoginMode.cpp:2374`) and forwards the same value at offset 10 in `0x0065` (`LoginMode.cpp:1795`; `Packet.h:278-285`). The character server reads it as `login_id2`, then the login server compares it with the outstanding auth node (`char_clif.cpp:827,866-884`; `loginchrif.cpp:76-92`). Therefore the client’s `UserLevel`/`m_userLevel` label is stale naming for the second auth token in this profile; byte and token semantics align. Response ordering, timeout/disconnect cleanup, and client send-failure recovery remain open.
