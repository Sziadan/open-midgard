# PK45.03 — recovery notification

Date: 2026-11-04. Status: client framing, vitals update and visual effects traced; selected server wire contract traced; AP reachability and replay remain open. No rows closed.

The router maps 0x013D to `HandleRecovery`; the size table fixes it at 6 bytes. The handler requires a data pointer and 6 bytes, reads status type u16@2 and amount u16@4, and ignores zero amounts. HP is type 5 and SP is type 7. With a live world player, current/max vitals come from the player; otherwise, when a character is selected, they come from session character vitals. For HP/SP it adds the amount, caps at max when max is nonzero, and calls `ApplySelfStatusUpdate` for that type. When max is zero it does not cap the addition.

With a live player actor, it emits a recovery number for every nonzero amount, with SP color only for type 7 and HP color for every other type. It launches a recovery effect only for HP (effect ID from the HP recovery constant) or SP (SP effect); other types yield no effect. This means an unknown status type can show an HP-colored number without changing HP/SP. The handler always logs the recovery tuple after those branches.

Open work: establish whether HP/SP amounts are deltas and how zero/max values behave; determine whether unknown types should produce a number; verify the unpinned AP caller against the selected source; replay HP/SP, zero, over-range, and AP cases with absent actors.

## Selected server recovery contract (2026-11-04)

Pinned `clif_heal` confirms `0x013D` carries type u16 and amount u16 to SELF. Its documented types are 5=HP and 7=SP; unknown types are described as ignored. The emitter caps the uint32 input amount to the packet field's maximum before serialization, so large heals are truncated to the u16 wire ceiling. This confirms the client's HP/SP type IDs and that the packet amount is an effect notification, not a serialized absolute stat snapshot. Whether each caller also emits a separate stat-value update depends on the healing path.
