# PK46.02 — guild-invitation reply request 0x016B

Date: 2026-11-05. Status: client prompt dispatch, answer encoding, selected server reply checks and result routing are source-traced. Asynchronous membership/update ordering and stale-prompt replay remain open. No row closed.

`Commerce::Action` handles `prompt` only for a recognized pending prompt kind. For `promptKind == "guild"`, it sends a 10-byte `0x016B` frame with prompt ID u32@2 and answer u32@6 (`1` when accepted and `0` when declined). A failed send preserves the prompt state; successful send clears `promptKind`. Alliance and friend prompts use different opcodes/layouts and are outside this leaf.

The selected final registry assigns length 10 to `clif_parse_GuildReplyInvite` (`PK01.02-server-registry-final.csv:130`). The parser forwards guild ID@2 and answer@6 to `guild_reply_invite` (`src/map/clif.cpp:14546-14553`). The server compares that guild ID with the recipient's current `sd.guild_invite`; a later invite can replace it, and a stale/mismatched reply returns without mutation (`src/map/guild.cpp:1002-1010`). Decline clears pending guild/account IDs and sends inviter result 1 only if the inviter is online. Acceptance is forced to decline if the recipient is already guilded; otherwise the handler rechecks guild existence, instance invitation policy and free capacity. Missing/blocked guilds clear pending fields and return without an inviter result; a full guild clears them and sends result 3 to an online inviter. An accepted reply calls `intif_guild_addmember` rather than changing the recipient's guild ID optimistically; membership arrives asynchronously (`guild.cpp:1012-1054`). Client `0x0169` handling maps these result bytes to a system message and does not itself update guild membership (`Commerce.cpp:84`). The prompt origin and replacement fields are cross-linked in `PK46.02-map-guild-invite-request.md`.
