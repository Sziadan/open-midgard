## 2026-11-04 — selected server and client response continuation

The selected parser rejects requests while the requester has an active NPC dialog, then reads the target block ID from the configured offset and calls `vending_vendinglistreq`. That routine silently returns if the target is absent or not vending. It also checks `pc_can_give_items` for both parties and emits the GM-trade restriction message if either side is blocked. On acceptance it stores the seller's vending UID in `sd->vended_id` and emits the shop list. This request routine itself does not check distance/map visibility; the later purchase routine independently enforces same-map/view distance except for an active remote-search result.

For the selected 20080910 server packet structs, the list response is 0x0133 with an 8-byte header (opcode, total length, seller AID) followed by 22-byte item entries. The server fills price, amount, client item index, type/ID, identify/damage/refine and card slots; entries with no item database record are skipped. An empty shop therefore produces an 8-byte list packet. The production client routes 0x0133 into `Commerce::Receive`, requires the body after the 8-byte header to be an exact multiple of 22, then reads amount at entry+4 and item index at entry+6, matching this selected server struct. The response opens/updates the local shop list; no local purchase occurs at this stage.
