# PK46.02 — NPC shop purchase-list request 0x00C8

Date: 2026-11-05. Status: purchase confirmation, row guards, wire contract, selected server transaction and 0x00CA result path are source-traced. A duplicate-row limited-stock partial-transaction risk is source-confirmed; safe repair and production replay need stronger review. No discovery row is closed.

## User action to sender

`UIItemPurchaseWnd` sends `GameMsg_RequestShopBuyList` when Buy Confirm is activated. `RequestNpcShopPurchaseList` requires buy mode and at least one deal row, computes a variable frame length of 4 header bytes plus 4 bytes per row, and rejects lengths above 65535. It writes the legacy shop purchase opcode and frame length, then serializes each row as quantity u16 followed by item ID u16. Quantity is clamped to 0..65535; item ID is narrowed to 16 bits. It sends the completed buffer and returns the transport result.

## Client layout and profile

`PACKET_CZ_PC_PURCHASE_ITEMLIST` has opcode `0x00C8` and frame length in its 4-byte header. Each repeated row is `{amount:u16, itemId:u16}`; total length is `4 + 4 * rowCount`. The sender uses `LegacyNpcShopSend::kPurchaseItemList` (`0x00C8`).

## Selected registry comparison

`PK01.02-server-registry-final.csv` maps opcode `00c8` to variable length and `clif_parse_NpcBuyListSend`. The selected parser computes row count by flooring `(packetLength - 4) / 4`, copies each u16 item ID and amount, then returns a purchase result. If trading or no server-side NPC shop is selected, it returns the money-failure result. It clears `npc_shopid` and sends a fixed 0x00CA result packet on every path that reaches the end of the parser.

`npc_buylist` rechecks that the remembered shop NPC still exists, is nearby and is a shop/market-shop, then rejects an empty list. Every row must match an item offered by that shop (including configured view-ID replacements) and still exist in the item database. Nonstackable items requested above one are clamped to one. For normal shops it aggregates cost, weight and required inventory slots, applies discount, checks zeny/weight/capacity, then deducts zeny and grants the items. Script-controlled shops instead populate `@bought_nameid`/`@bought_quantity`, invoke the configured on-buy event and return success for script handling. Selected 20080910 does not compile the newer market-stock branch.

The server emits 0x00CA with the purchase result byte; the client handler maps result 0/1/2/3 to success/money/weight/capacity messages, releases the NPC conversation lock, closes shop windows and clears shop state. This result path is source-traced, while actual item/currency UI update ordering remains dependent on the separate inventory/zeny packets.

The parser snippet has no explicit row-remainder validation or zero-quantity rejection before `npc_buylist`; those cases need targeted tests/review. Client narrows item IDs to 16 bits and quantities to u16, so IDs outside that domain cannot be assumed compatible. Existing `PK45.03-npc-shop-lists-results.md` remains the source for shop-list prompt/result contracts.

## Remaining evidence and ownership

### Duplicate limited-stock purchase risk

For normal shops, `npc_buylist` first validates each row independently against the current shop stock (`src/map/npc.cpp:2822-2839`), then checks aggregate zeny/weight/slots and charges zeny (`src/map/npc.cpp:2887-2895`). A later loop decrements stock per row; if a later duplicate row exceeds the now-reduced stock, it returns `PURCHASE_FAIL_COUNT` after payment and any earlier row-side stock/item mutation (`src/map/npc.cpp:2897-2928`). Thus duplicate rows can individually pass prevalidation while their combined amount exceeds limited stock, producing a failure result after a partial purchase. Script-controlled shops take a separate `npc_buylist_sub` branch and are not included in this specific finding.

Stronger review and production-path regression are required before repair: reproduce duplicate rows against limited stock, then design atomic validation/mutation that preserves script-shop behavior. Also replay zero quantities, max quantities, unknown/narrowed item IDs, malformed trailing bytes, full inventory, insufficient zeny, overweight, stale/far shop, send failure and response/inventory/currency ordering before closure. Preserve existing primary ownership; no production replay and no discovery row is closed.
