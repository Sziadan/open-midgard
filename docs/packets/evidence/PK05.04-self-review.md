# PK05.04 — receive-framing self-review

Date: 2026-11-04. Status: implementation self-review complete; independent PK48 review pending.

## Source and branch audit

- `CRagConnection::RecvPacket` looks up the leading two-byte ID in the active `GetPacketSize` table. Size zero sets `ReceiveError::UnknownOpcode`, logs that it is disconnecting, closes, clears queues, and returns false. No two-byte removal or rescan remains.
- For the recognized variable sentinel, the receive path waits for the complete four-byte header; lengths outside 4–`0x7FFF` set `InvalidVariableLength`, log the disconnect, close/clear, and return false. Partial headers remain buffered.
- Recognized fixed and valid variable packets still wait for full table/declared length and pop exactly one frame. Existing fixture splits and concatenation tests cover that preserved behavior.
- `CConnection::Disconnect` clears the socket and all queues. The typed receive error is set before this transition; `OnClose` intentionally retains it for the caller. `OnConnect` resets it to `None`.
- `CLoginMode::OnUpdate` consumes the retained error after `PollNetwork` and picks distinct unknown-opcode and malformed-length status/dialog text. Ordinary EOF follows the prior generic disconnect path.
- The map packet loop treats a false receive as drained and the transport emits a first-seen diagnostic; this review does not claim the full `CGameMode::OnUpdate` lifecycle or a visible map-mode notification was exercised.
- Self-review found stale “dropping” wording in the unknown/invalid logs after PK05.02 changed behavior. Both log strings now say “disconnecting”; the updated build and replay passed.
