# PK46.02 — zone-entry request profile family

Date: 2026-11-04. Status: current zone-connect sender and selected registration lengths traced; full effective-profile resolution and legacy branches require stronger review. No discovery row is closed.

## Current client path

When `LoginMode` enters zone connection after the character-server transition, it connects to the stored zone endpoint. On connection failure it disconnects, reports the error and returns to login. On success it calls `BuildActiveWantToConnectionPacket` with session AID, GID, auth code, current tick and sex, then sends the returned byte frame. A build or send failure now disconnects, clears `m_isConnected`, reports the failure, shows the zone-connection dialog and returns to login.

## Profile families and selected registrations

`MapSendProfile` selects a `ZonePacketProfile` separately from the map gameplay send profile and supports multiple opcode/layout families. The PacketVer22 map profile uses `0x009B` with a 26-byte legacy layout; the PacketVer23 profile uses `0x0436` with a 19-byte compact layout. The selected registry maps both opcodes to `clif_parse_WantToConnection` at those lengths. Additional legacy-0x0072 profiles and compact/padded layouts also exist in the client code, but the selected registry maps `0x0072` to 25-byte `clif_parse_UseSkillToId`, not a want-to-connection parser. Keep these request identities distinct.

## Exact client layouts and effective default

`ResolveConfiguredProfile` defaults `Packets.MapSendProfile` to `packetver23`. `ResolveConfiguredZoneProfile` defaults `Packets.ZoneConnectProfile` to `inherit`, which returns the base profile's zone layout. Thus the source default is PacketVer23 compact layout and `0x0436` unless settings override it (`src/network/MapSendProfile.cpp:56-74,319-329,332-342`). This records source defaults; deployed settings still need confirmation.

With packed `Packet.h` structs and the profile builders, the current client variants are:

- PacketVer23 compact `0x0436`, 19 bytes: opcode u16 @0, AID u32 @2, GID u32 @6, auth code u32 @10, client tick u32 @14, sex u8 @18 (`PACKET_CZ_ENTER2`, `Packet.h:334-341`).
- PacketVer22 legacy `0x009B`, 26 bytes: opcode u16 @0, padding[2] @2, AID u32 @4, padding u8 @8, GID u32 @9, padding[4] @13, auth code u32 @17, client tick u32 @21, sex u8 @25 (`PACKET_CZ_ENTER_PACKETVER22`, `Packet.h:343-353`).
- Legacy `0x0072` compact reuses the 19-byte field layout; `legacy0072padded22` uses 22 bytes: opcode @0, padding[3] @2, AID u32 @5, GID u32 @9, auth code u32 @13, tick u32 @17, sex u8 @21 (`PACKET_CZ_ENTER_PADDED22`, `Packet.h:355-363`). Builders fill the explicit padding according to `FillPacketPadding` (`MapSendProfile.cpp:748-785`).

The zone endpoint/map are sourced from the character-server notification: handler `OnNotifyZonesvr` parses map bytes @6..21, IP @22..25 and port @26..27, then schedules `LoginSubMode_ZoneConnect` (`LoginMode.cpp:2752-2787`). The zone connect path uses session AID/GID/auth/sex plus `timeGetTime()` (`LoginMode.cpp:1917-1927`). Both packet-build and `SendPacket` failure now disconnect, clear connected state, show a failure dialog and schedule return to login (`:1927-1944`); successful send proceeds to the zone-server wait status.

The selected final registry has `0x0436` fixed length 19 and `0x009B` fixed length 26 as `clif_parse_WantToConnection`; `0x0072` is instead the 25-byte `clif_parse_UseSkillToId`. Therefore only the source-default layout has an unambiguous selected-registry tuple. The 0x0072 variants remain a concrete profile/registry mismatch until the deployed profile is established. Registry framing does not establish the parser's field semantics or validation.
