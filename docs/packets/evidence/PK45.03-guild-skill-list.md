# PK45.03 — guild skill information list

Date: 2026-11-04. Status: variable framing, record parsing and session/UI effects traced; field schema and boundary behavior remain open. No rows closed.

The size table marks 0x0162 variable length and the router maps it to `HandleGuildSkillInfo`. The handler requires at least six bytes, clears the pending guild-skill-upgrade flag and existing guild-skill items, then computes `recordCount = (signed16(packetLength) - 6) / 37`. Records begin at offset 6 and advance by 37 bytes. Each record reads SKID u16@0, type u32@2, signed level u16@6, signed SP cost u16@8, and upgradable byte@36; bytes 10–35 are not consumed. Only SKIDs 10000–10015 are named and stored. It reads signed guild skill points u16@4 and invalidates session UI after parsing.

Trailing partial record bytes are silently ignored after the old list has been cleared. The signed-16 conversion of total packet length also makes behavior for lengths above 32767 a boundary risk: record count may become negative while the handler still updates points/UI. No upper bound or malformed-record rejection appears here.

Open work: validate 37-byte schema and accepted SKID range against the selected server; resolve the unparsed record bytes and signedness of level/cost/points; test 0,1,16,17 records, partial tails, malformed lengths and >32767-byte packets; verify upgrade request/response state and UI refresh. No independent fixture or production replay was performed for this leaf.

## Selected server guild-skill emitter follow-up (2026-11-04)

The pinned `clif_guild_skillinfo` emitter confirms the client’s six-byte header and 37-byte record stride. It includes the guild skill-point value, then emits only skills with a positive ID whose requirements pass `guild_check_skill_require`. Each record supplies skill ID, skill info/type, level, SP cost, range, name, and upgradable flag; the client consumes ID/type/level/SP/upgradable and skips range/name. The upgradable flag is 1 only when the skill is below its maximum and the receiving session pointer is the session stored for guild member slot 0 (the leader). If the session has no guild, the emitter sends nothing; a guild with no qualifying skills still sends its header and points.

This validates selected-profile framing, filtering, field mapping, and leader gating from pinned source. Whether the client's clear-then-rebuild behavior and pending-upgrade reset match every server transition, plus partial-tail and large-length boundary cases, remain open for fixture/replay. No discovery row is closed.
