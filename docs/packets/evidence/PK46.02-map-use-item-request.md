# PK46.02 — inventory use-item request

Date: 2026-11-05. Status: user path, profile serializers, selected parser gates and basic/extended client acknowledgement effects are source-traced; explicit legacy profile conflicts with selected server. Early-return and target/recovery replay remain open. No discovery row is closed.

`UIItemWnd` sends `GameMsg_RequestUseInventoryItem` for an inventory item accepted by the double-click use gate. `RequestUseInventoryItem` rejects index zero or an item absent from the current inventory. Equip-tab items route to the equip request, and card items route to the composition-list request; the remaining item-use path calls `BuildActiveUseItemPacket` with the selected item index and the session AID. A successful send records the item index as awaiting its use acknowledgement.

The active map send profile selects these use-item forms:

- PacketVer22: opcode `0x009F`, 14-byte packet, item index u16@4 and target AID u32@10 (padding occupies the other fields). The selected 20080910 registry has `0x009F`, length 14, `clif_parse_UseItem`, with those positions.
- PacketVer23: opcode `0x0439`, 8-byte packet, item index u16@2 and target AID u32@4. The selected registry has `0x0439`, length 8, `clif_parse_UseItem`, with those positions.
- Explicit Legacy map profile: opcode `0x00A2`, using the same compact eight-byte struct. The selected 20080910 registry instead identifies `0x00A2` as a 15-byte `clif_parse_SolveCharName` request. This legacy use-item path conflicts with the selected server and must remain unresolved for that server.

The selected `clif_parse_UseItem` reads the inventory index from the first registered field and subtracts two before calling `pc_useitem`; it does not consume the target-AID field in this branch. It rejects dead players and blocked states before using the item, and sends an empty use acknowledgement when `pc_useitem` fails so the client does not remain waiting. This follows the parser path, not the deeper item-effect, target, or UI result lifecycle. No independent byte fixture or production replay was run, so no discovery row is closed.


## Selected-server parser and item-use gates — PACKETVER 20080910

The final selected registry confirms `0x009F` is a 14-byte `clif_parse_UseItem` packet with index at offset 4, and `0x0439` is 8 bytes with index at offset 2; both registered forms match the PacketVer22/PacketVer23 serializers. `clif_parse_UseItem` reads only the first registered field and subtracts 2 from the client index; the PacketVer23 target-AID field at offset 4 is not consumed by this handler. The explicit Legacy profile's 8-byte `0x00A2` is incompatible: the selected final registry maps `0x00A2` to a 15-byte `clif_parse_SolveCharName` packet with its field at offset 11. Do not use that legacy serializer with this server profile.

Before reading the index, the selected parser rejects dead players (clear-dead-unit update, no use ack) and busy states: trade without an NPC, chat-room membership, or `PCBLOCK_USEITEM` (busy message, no use ack). It updates configured idle timers, subtracts 2 from the registered index, and returns silently if the resulting slot is out of range. For an in-range slot, a false `pc_useitem` result receives an empty `clif_useitemack` so the client does not remain pending.

`pc_useitem` additionally rejects mail-writing state; may cancel an active NPC progress bar on the first item attempt; enforces NPC item/progress restrictions; requires a present item with positive count and `pc_isUseitem` permission; and applies status-effect, delayed-consume, skill-timer, cooldown, and map no-equip gates. Delayed-consume items have a distinct acknowledgement/consumption sequence, while other usable items acknowledge and consume through the ordinary path. These source paths do not prove script-specific item behavior, exact client recovery after every early silent return, or item-target semantics; those remain replay/review work. No row closed.

## Client use-acknowledgement follow-up

The basic use acknowledgement is fixed seven-byte `0x00A8`; the extended variant is 13-byte `0x01C8` (`src/network/GronPacket.cpp:89,290`, `src/network/MapSendProfile.cpp:224-225`). The basic handler reads item index u16@2, remaining amount u16@4 and success byte @6; it clears `m_waitingUseItemAck` for either result, sets the pending card index only on successful card use, and on success consumes the difference between cached count and acknowledged remaining count (`GameModePacket.cpp:1302-1334`). The extended handler reads item ID @4, actor ID @6, amount @10 and success @12; it clears pending/card state and consumes inventory only when the actor ID resolves as local, but invokes `MakePotionEffect` on any successful response (`GameModePacket.cpp:1254-1300`). These paths expose variant-specific pending-state behavior: a nonlocal extended acknowledgement does not clear the local pending item index. This is source behavior, not proof of selected-server variant use or recovery after silent parser returns. Keep profile, stale/mismatched ack, early-return and visible effect replay open.
