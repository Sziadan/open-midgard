# PK45.03 — vending shop listings and lifecycle

Date: 2026-11-04. Status: client list parsing and UI/state transitions traced; server schema and status meanings remain provisional. No rows closed.

Opcodes 0x0133 and 0x0136 share a variable-length offer-list parser. It requires at least eight bytes and an exact multiple of 22 bytes after the header. Each row reads a four-byte price, a two-byte amount and two-byte client item index (the amount/index order is reversed between the two opcodes), then item type, item ID, identified/damaged/refine bytes, and four two-byte slot values. The parsed amount becomes the offer item's quantity. For 0x0136 the new list replaces the local draft, marks vending active, clears pending, shows the vending window, and posts “Shop is open.” For 0x0133 it replaces the displayed shop items, reads seller ID at byte 4, shows the shop window, and posts the item-selection prompt.

Opcode 0x0137 requires six bytes and subtracts the four-byte amount at byte 4 from the draft offer matching the item index at byte 2; an amount at least as large removes that offer. Opcode 0x0135 requires seven bytes. On zero status at byte 6 it subtracts the amount at byte 4 from the matching displayed shop item (index at byte 2), clamping at zero; either status posts a purchase-confirmed/failure message. Opcode 0x0138 requires three bytes and clears `vendingPending`; a nonzero status deactivates vending and posts a shop-open failure, while zero leaves state otherwise unchanged.

Opcodes 0x0131 and 0x0132 update the local vending-board map: 0x0131 requires 86 bytes and stores the 80-byte text beginning at byte 6, keyed by the four-byte ID at byte 2; 0x0132 requires six bytes and erases that ID, additionally clearing local vending active/pending flags when it matches the session account ID. These handlers do not set or clear the map based on a separate result code.

The parser establishes the client's offsets and state transitions, not authoritative server semantics. Confirm the 0x0133/0x0136 amount/index field distinction, 0x0135 polarity and board-ID interpretation against a selected server profile or captures. The UI uses a fixed failure message for purchases and does not correlate a result with a pending request. No independent fixture or production replay was performed; no rows are closed.

## Selected server vending emitters (2026-11-04)

Pinned `clif_vendinglist` confirms the buyer-facing `0x0133` variable frame: header length, seller AID, then 22-byte offer rows. It filters entries whose item metadata lookup fails and serializes price, amount, cart index, type/ID, identify/damage/refine and cards; it sends the list to the requesting buyer. `clif_openvending` emits the seller's `0x0136` list with the seller ID and 22-byte rows, then invokes an open-store acknowledgment that is compiled only for PACKETVER >= 20141022, so the selected 20080910 profile does not send that newer acknowledgment. Board show/remove are `0x0131` (AID plus fixed 80-byte message) and `0x0132` (actor ID); absent explicit target they broadcast around the actor excluding the source.

The `0x0135` purchase result meanings documented by the pinned source include 0 success, 1 insufficient zeny, 2 overweight, 4 out of stock, 5 trade conflict, 6 incorrect shop information, and 7 no sales information. `0x0137` reports the sold cart index and amount to the seller. These layouts and meanings align with the client list/update handlers. Exact state behavior for omitted result 3, purchase transaction ordering, invalid item metadata filtering, message-board lifecycle, and production replay remain open. No discovery row is closed.


## Legacy 0x0138 vending-open result cross-check (2026-11-04)

The current client fixes 0x0138 at three bytes and routes it to the commerce receiver. That receiver clears the local vending-pending flag; a nonzero status also clears the active flag and reports that the server could not open the shop. This establishes the client receive direction and local effect only.

The pinned server packet headers inspected here define ZC_OPENSTORE at 0x012D and ZC_ACK_OPENSTORE2 at 0x0A28; no 0x0138 definition or matching emitter was found in the inspected clif.cpp/packets.hpp sources. Treat 0x0138 as a legacy or profile-specific client path until its historical server contract is sourced. Do not infer success/failure polarity beyond the client behavior. Stronger profile/source review and replay remain required.
