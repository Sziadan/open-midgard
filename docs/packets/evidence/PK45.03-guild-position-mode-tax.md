# PK45.03 — guild position mode and tax lists

Date: 2026-11-04. Status: framing and position-map mutation traced; selected-server semantics and replay remain open. No rows closed.

Opcodes 0x0160 and 0x0174 are variable-length guild-window packets. `ReadWindowPacket` selects 16-byte rows for 0x0160 and 40-byte rows for 0x0174. It requires the four-byte packet header and rejects the packet before mutation unless the remaining payload is an exact multiple of that opcode's stride.

Both row forms read position ID u32@0, mode u32@4 and tax u32@12. Opcode 0x0174 additionally reads name[24]@16; 0x0160 does not touch the existing name. Bytes 8–11 are unused by this parser. Rows update `state.positions[id]`; neither branch clears the map, and entries not otherwise assigned retain their prior/default fields. The outer guild-window handler recomputes local position-derived permissions/title after successful parsing when the local member has a matching position.

Open work: confirm the packet sizes, field meanings, and full-list versus delta semantics against the selected server; determine treatment of duplicate/unknown IDs and stale positions; replay empty, aligned and malformed variants and verify UI/permission consequences. No independent fixture or production replay was performed for this leaf.

## Selected server position-info emitters (2026-11-04)

The pinned `clif_guild_positioninfolist` emits `0x0160` as a 324-byte frame: four-byte header plus 20 rows of 16 bytes. Each row is position ID, rights/mode, ranking, and pay rate. IDs are emitted in slot order; ranking is currently set equal to the slot index. The `0x0174` update emitter sends a single 40-byte row containing ID, rights, ranking, pay rate, and name[24] to GUILD recipients; its source comment says the intended update should be batched after a commit, but the current implementation sends one packet per position. Both emitters assign the pay-rate field from `guild_position.exp_mode`; the client stores that field as `tax` and presents “experience tax.” The server-side business field is outside the pinned source set, so treat the exact percentage/range semantics as a provenance gap until that implementation is tied to the intended revision.

The pinned `0x0174` contract labels rights bit 0x01 as invite and 0x10 as expel, while ranking is explicitly TODO. This establishes wire assignment and current update recipient behavior, but leave ranking meaning, tax units, and batching/UI refresh for stronger source review and replay. No discovery row is closed.
