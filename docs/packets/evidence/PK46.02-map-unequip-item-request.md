# PK46.02 — unequip inventory item request

Date: 2026-11-04. Status: UI sender, selected parser, and selected server acknowledgement semantics traced; index-zero correlation and runtime UI/replay remain open. No discovery row is closed.

`UIItemWnd` sends `GameMsg_RequestUnequipInventoryItem` for an equipped item on its equipment tab action. `RequestUnequipInventoryItem` rejects item index zero, fills `PACKET_CZ_REQ_TAKEOFF_EQUIP`, sends it, and records the item index as awaiting an unequip acknowledgement if the send succeeds.

The request is fixed-size 4 bytes: opcode u16@0 and item index u16@2. Each configured map gameplay profile selects `0x00AB`. The selected 20080910 registry registers `0x00AB`, length 4, with `clif_parse_UnequipItem` and item index at offset 2. The server rejects dead players and prohibited NPC/block-action states, allows the storage/status exceptions shown in the parser, reads the registered index and subtracts 2, then calls `pc_unequipitem(sd,index,1)`.

The sender and selected parser agree on framing and field offset. The request does not locally remove the equipment; the client waits for the server's inventory/equipment updates. Ack correlation, returned inventory/equipment list ordering, and visible UI restoration were not replayed or independently captured. No discovery row is closed.


## Selected server acknowledgement follow-up (2026-11-04)

At PACKETVER=20080910, `clif_unequipitemack` uses the pre-20110824 `0x00AC` packet with index u16@2, wear location u16@4, and one-byte `flag` at @6; the server copies the `success` boolean without inversion (`src/map/clif.cpp:4336-4349`, `src/map/packets.hpp:1015-1022`). The client reads that result byte, clears pending state only when the returned index matches, leaves equipment state unchanged on failure, and clears wear location/rebuilds appearance on success (`src/gamemode/GameModePacket.cpp:2767-2795`).

`pc_unequipitem` returns an indexed failure ack for an already-unequipped item or a prohibited unequip. Its invalid server-index branch instead sends failure with index zero (`src/map/pc.cpp:12389-12407`). The client will not match that zero to a normal nonzero pending item index, so the pending marker may remain set for a malformed/stale request. The current `pc.cpp` SHA-256 is `E94AF5E1B173CC442EE0B14F69EBD402F5703DEEA1D51FCA36DF8F9A69244A4E`; PK01.02 does not pin this file and the server checkout has no Git revision metadata. Stronger review should decide whether the index-zero branch is reachable through normal UI state and what correlation behavior is safe. No discovery row is closed.
