# PK45.03 — commerce trade invitation and exchange lifecycle

Date: 2026-11-04. Status: client receive branches and state transitions traced; protocol status/actor meanings remain provisional. No rows closed.

The client accepts trade invitations on 0x00E5 (minimum 26 bytes) and 0x01F4 (minimum 32). Both reset the current trade state, read a 24-byte player name at byte 2, set the incoming-invitation flag, show the trade window, and post a prompt to review the name. The 0x01F4 form additionally reads partner ID at byte 26; 0x00E5 sets partner ID to zero.

Opcodes 0x00E7 and 0x01F5 require three bytes. Status byte 2 equal to 3 resets trade state and opens the active trade window; the window is resized to 660×420 and 0x01F5 reads partner ID at byte 3 when at least nine bytes are present. Other statuses reset trade state, hide the window, and map status values 0–5 to the client messages for distance, unavailable partner, generic failure, empty string, declined/canceled, and busy; out-of-range values use generic failure.

Opcode 0x00E9 requires 19 bytes and an active trade. It reads a four-byte amount at byte 2 and item ID at byte 6. A zero ID replaces `remoteZeny`; otherwise it appends a remote offer with amount, item ID, identified/damaged/refine bytes at 8–10, and four slot values starting at byte 11. It does not read an item index. Opcode 0x00EA requires five bytes and acts only when a trade-item addition is pending and the index at byte 2 matches the pending item. Status zero adds the pending offer or increments an existing local offer with the same index; nonzero posts rejection text. A matching response clears `tradeAddPending`; a nonmatching response is ignored.

Opcode 0x00EC requires an active trade and three bytes. Status zero marks the local side locked and clears `lockPending`; nonzero marks the remote side locked. Opcode 0x00EE resets trade state, hides the window, and posts a cancellation notice. Opcode 0x00F0 requires three bytes, resets trade state and hides the window, then reports completed for zero status or failed otherwise. Opcode 0x00F1 clears only the local offer, local zeny and local lock/pending-lock flags; it does not call the full reset helper.

The shared reset clears active/incoming/waiting and lock/add/commit flags, both offer lists and both zeny values, and restores the default trade-window size. Status-to-actor mapping for 0x00EC, whether the 0x00E9 remote offer is a full snapshot or a sequence of additions, and the server meanings of the invitation/status variants need selected-server or capture confirmation. No independent fixture or production replay was performed; no rows are closed.

## Selected server trade lifecycle emitters (2026-11-04)

The pinned `clif.cpp` comments and emitters establish the principal result meanings and recipient scope. Trade invitation `0x00E5` carries the inviter name; `0x01F4` adds target ID and base level when the extended PACKETVER branch is used. Response `0x00E7`/`0x01F5` flags are 0=too far, 1=character missing, 2=trade failed, 3=accept, 4=cancel, 5=busy. The client’s status-3 open path and non-3 reset path are consistent with this table. Adding a remote item uses `0x00E9`; item index zero produces an otherwise empty item record with amount populated, matching the client’s item-ID-zero zeny interpretation. `0x00EC` explicitly defines who=0 self and who=1 other player, matching the local/remote lock mapping. `0x00EE` is cancellation. The success emitter sends `0x00F0` result 0; the meaning of a received failure result 1 is documented, but its selected emitter path was not established here.

The selected source therefore resolves the core status polarity and several actor meanings. Invitation expiry, request correlation, offer snapshot-versus-delta behavior, failure-result emitter, undo semantics, call ordering, and runtime replay remain open. No discovery row is closed.
