## Machine-readable manifest schema

Create `docs/packets/evidence/PK02.02-contract-manifest.json` with top-level `schema_version` (integer 1), `baseline` (client commit, server root/revision, server snapshot state, effective define map, deployed provenance status), `source_sha256` (repository-relative path to lowercase SHA-256), `contracts` (array keyed by unique `contract_id`), and `generator` (tool path/hash, exact command, compiler identity/version, exit code). Each contract record contains: `contract_id`, `discovery_parents`, `stage`, `direction`, `server_packetver`, `client_profile` or null, `opcode` or null for raw handshake/state-machine contracts, `layout_variant`, `applicability_status`, `registration` (guard, source path/line, accepted length, parser/emitter, evaluated final assignment order), `fields` (ordered entries with name, offset, width_bytes, signed, endian, semantic type/units, source path/line, guard, validity/range or explicit unresolved), and `probe` (translation unit/source hash, compiler command, exit code, measured sizeof/offsetof or explicit not_applicable). Preserve JSON array order for wire order; do not omit padding or unknown fields—record them as `padding`/`unresolved`. No credentials or live account data.

Manifest determinism: sort `contracts` by `contract_id`, source hash keys lexically, and define keys lexically; preserve field wire order and assignment order. UTF-8 JSON, two-space indentation, LF line endings, final newline. Hash each compiler input and generated probe source; record compiler/toolchain version. A null Git revision is valid only with `server_snapshot_state: unversioned` and complete relevant file hashes.

## Independent byte-oracle schema

PK02.03 creates `PK02.03-fixtures.json` plus separate `.hex` files. Top-level `schema_version`, `manifest_sha256`, `fixtures`; each fixture has unique `fixture_id`, `contract_id`, `provenance` (server source symbol/path/line or registration + exact field facts), `direction`, `stage`, `profile`, `expected_length`, `hex_file`, `sha256`, and ordered `fields` entries (`name`, `offset`, `width_bytes`, `expected_hex`, `decoded_value`, `source_basis`). Fixtures must be derived manually or by a separate generator from the server registration/parser or emitter/packed layout; never import client serializer output or client structs. Requests 0x0190, 0x007E and 0x0437 use final server parser offsets and accepted lengths. Outbound 0x01F2/0x01A2 use server packed emit layout and guards. Handshake fixture is a four-byte raw prefix parameterized with a synthetic account ID, explicitly marked as no opcode. Add minimum/maximum/sentinel/rejection cases only where server source establishes semantics; preserve unknowns. Each fixture includes a synthetic-data flag and contains no real credentials.

Schema validation rejects duplicate IDs, missing contract links, duplicate/out-of-bounds fields, non-hex or wrong-length bytes, mismatched fixture/field slices, missing hashes, unresolved values represented as guessed bytes, and client-derived provenance. A fixture can establish byte expectations only; it does not establish active reachability or complete UI behavior.

No runtime changes, builds, live sessions, deployment, or account transactions are part of PK02.01.
