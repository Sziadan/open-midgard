# PK46.02 — card composition-list request 0x017A

Date: 2026-11-04. Status: inventory-use branch, four-byte card-index frame, selected server validation/list response and client composition handlers traced. Production replay and request-response correlation remain open. No row closed.

`RequestUseInventoryItem` first resolves the inventory row and rejects missing items or item index zero. Equipment-capable items with a location route to equip handling. A card item instead sends `PACKET_CZ_ITEM_COMPOSITION_LIST`: fixed 4-byte opcode `0x017A` with card inventory index u16@2. On successful send the client clears `m_waitingUseItemAck` and stores the selected index in `m_lastCardItemIndex`; a failed send leaves those fields unchanged.

The selected final registry assigns length 4 to `clif_parse_UseCard` (`PK01.02-server-registry-final.csv:138`). The selected server parser ignores requests while trading, converts the client item index, bounds-checks it, and calls `clif_use_card`. That routine requires a valid inventory item of type `IT_CARD`, then enumerates identified, unequipped weapon/armor items with compatible equip masks, an empty card slot and no special first-card marker. It emits variable-length 0x017B with a 4-byte header and the eligible item indexes. If the item is invalid/not a card, or no compatible target exists, it returns without a response.

The client 0x017B handler validates the 4-byte header and even-sized index tail, removes zero entries and opens the composition window. It does not correlate the response with a stored request token. The selected card index is stored after the 0x017A send and is consumed by the later composition request; an empty server result has no 0x017B response to clear it. A later ordinary item-use send clears that stored card index, and the 0x017D composition acknowledgement also clears it. This leaves no explicit timeout/cancel cleanup for a card request that receives no list response.

The follow-on 0x017C parser rejects while trading, converts and bounds-checks both indexes, then `pc_insert_card` independently validates the card and equipment types, item quantities, identification, slot capacity, equip compatibility and unequipped state before consuming the card. On successful consumption it inserts the card ID and emits the composition result. This source trace covers eligibility and mutation gates, not end-to-end replay or rendered UI behavior.
