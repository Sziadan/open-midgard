# PK46.02 — NPC dialog close request 0x0146

Date: 2026-11-05. Status: dialog close actions, client pre-send effects, fixed serialization, selected parser/script-state behavior, and client close-output handling are source-traced. Source confirms local quest/dialog state is cleared before send with no rollback; production send/order replay remains open. No discovery row is closed.

## User action to sender

`UISayDialogWnd` sends `GameMsg_RequestNpcCloseDialog` when the player closes the NPC conversation; `UINpcInputWnd` also sends it when the input dialog is dismissed. Both UI paths close NPC dialog windows before sending the message. `GameMode` dispatches to `RequestNpcCloseDialog`, which clears the current game mode's quest/dialog identifiers before validating the supplied NPC ID, then sends the close packet. A zero ID or send failure returns false after those local side effects; there is no rollback in this helper.

## Client layout and profile

`Packet.h` defines `PACKET_CZ_NPC_CLOSE_DIALOG` with opcode `0x0146` at offset 0 (2 bytes) and NPC ID at offset 2 (4 bytes). The sender uses `PacketProfile::LegacyNpcScriptSend::kCloseDialog` (`0x0146`) and sends the six-byte struct size.

## Selected registry comparison

`PK01.02-server-registry-final.csv` maps opcode `0146` to fixed length 6 and `clif_parse_NpcCloseClicked`. Client opcode and total length agree with the selected final registry. The server returns immediately if no NPC dialog is active; otherwise it calls `npc_scriptcont` with the packet NPC ID and `closing=true`. The continuation requires that ID to match `sd->npc_id`, checks that the NPC remains in range/visible (apart from the item-script fake NPC), and can return without progressing for a progressbar or absent script state. Closing bypasses the secure NPC idle-timeout check used for ordinary menu/next continuation.

On a `CLOSE` script state the server moves the script to `END` and clears its cutin if requested. On `STOP` it resumes the script (`RUN`); unexpected states are forced to `END` and logged. `run_script_main` then owns the next script output/cleanup. There is no generic close acknowledgement. This means the client's pre-send window/quest-ID cleanup can precede server acceptance; zero ID, failed send, mismatched/stale NPC, out-of-range NPC, progressbar, or missing script state can leave client/server dialog state temporarily divergent.

## Client close send-failure behavior

`RequestNpcCloseDialog` clears `m_isOnQuest` and `m_lastNaid` before checking whether the NPC ID is zero or sending the packet (`src/gamemode/GameMode.cpp:6281-6300`). The keyboard close route first closes NPC windows and propagates the `SendMsg` result; mouse close and input-window dismissal also close/hide windows first but ignore the result (`src/ui/UISayDialogWnd.cpp:399-406,474-480`; `src/ui/UINpcInputWnd.cpp:460-468`). There is no local restoration on a failed send in these call paths. A zero NPC ID also returns false after clearing the tracking fields.

## Client close-output receive path follow-up

The client frames server `0x00B6` output as six bytes and routes it to `HandleNpcDialogClose` (`src/network/GronPacket.cpp:100`, `src/gamemode/GameModePacket.cpp:8880`). The handler reads NPC ID at offset 2, remembers the conversation, and hides menu/input windows. If the say dialog remains visible it changes that dialog to a Close action; otherwise it releases the NPC conversation lock and closes all NPC dialog windows (`GameModePacket.cpp:3455-3477`). This is subsequent server output handling, not a generic request acknowledgement, and does not undo local cleanup when the request send fails or the server silently rejects a stale ID. Replay the ordering and dialog-lock lifecycle before closure.
