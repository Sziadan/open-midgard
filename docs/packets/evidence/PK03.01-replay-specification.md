# PK03.01 — Production replay and harness specification

Date: 2026-11-03
Status: specification approved; no harness code or packet behavior is certified by this leaf.

## Bounded scope and production entry points

The harness exercises production code offline against synthetic fixtures only. No deployed game client, live account, server process, network service, or `Ref` writes are permitted. Server-derived expected bytes come exclusively from PK02.02 manifest and PK02.03 fixtures; no test oracle may be generated by the client serializer under test. Record each contract’s independent strong approval before a runtime feature test relies on its semantics.

Primary receive/framing path: `CRagConnection::RecvPacket(std::vector<u8>&)` in `src/network/Connection.cpp`, fed by a local loopback peer; verify `CPacketQueue` accumulation/removal and `ro::net::GetPacketSize` routing in `PacketQueue.cpp` / `GronPacket.cpp`. Relevant connection reset path is `Disconnect()` and reconnect/`OnConnect`. Test raw handshake mode separately through its owning login/character state machine; the generic map packet decoder must not consume the four-byte raw prefix as an opcode. Production receive dispatch is `GameMode`/`GameModePacket` and the active map router; trace exact current symbols before adding assertions.

Outbound path: production action/skill entry points through `MapSendProfile.cpp`, `GameModePacket.cpp`, and `CRagConnection::SendPacket`; capture bytes at a local socket peer. The existing `BuildActiveUseSkillToPosInfoPacket` helper alone is supplemental, not proof that a user action reaches the builder. Session and UI transitions for later feature replays use production `Session`, actor/network callbacks, and Qt adapters with `QT_QPA_PLATFORM=offscreen` where supported.

## Harness layout and output schema

Add an opt-in `RO_BUILD_PACKET_REPLAY_TESTS` CMake option (default OFF), separate from `RO_BUILD_SKILL_REPLAY_TESTS`, and a `packet_stream_replay_checks` executable under `tools/tests/replay/`. It links production `ro_network`/`ro_core` for framing; feature-specific runtime replays may link the relevant existing libraries but remain separately named and scoped. Test transport is a loopback socket pair with deterministic chunk writes and timeouts. Where a platform cannot use the same socket setup, record the platform-specific harness path rather than replacing production `RecvPacket` with a test clone.

Each JSONL replay record includes: `case_id`, `contract_id`, `fixture_id` and fixture SHA, client baseline commit, `production_entry`, `stage/profile`, ordered input chunks (hex references, never credentials), invocation count, expected returned packet bytes or no-packet result, expected connection state, expected queue remainder, expected send bytes, observable Session/UI assertions when applicable, command/build preset, exit code, and outcome. Every assertion maps to a production source branch and a source-approved contract field or explicitly structural framing property. Preserve failing input and actual byte/state output for diagnosis.

## Required cases

PK03.02 receive/framing cases: split each relevant fixed packet at every byte boundary; split raw handshake prefix separately; one-byte/two-byte opcode fragments; incomplete valid fixed frame waits without consuming; coalesced known frames yield exactly one frame per call then preserve the next; variable-length frame header/body fragmentation and adjacent frame; unknown opcode followed by a valid frame; malformed variable lengths below minimum and above max followed by a known frame; EOF with empty, partial header, and partial body; disconnect/reconnect reset; wrong stage/profile; output buffer safety for the legacy `RecvPacket(char*)` wrapper. Use a loopback peer and timeout every case. If a candidate scenario depends on protocol semantics not specified by PK02, keep the assertion to framing/queue invariants.

PK03.03 outbound/runtime cases: send each approved fixture through its actual production action entry point; capture exact bytes and compare against server-derived fixture, include short/exact/overlong text boundaries only when source contract establishes them, builder failure must not emit a prefix, and pending Session/Qt state must clear on reject/cancel/disconnect. Replays must include unrelated action requests where a shared profile/router is touched. UI tests assert visible controls/actions and state lifetime, not only helper return values.

## Commands and build boundary

Use the documented deploy-off preset; verify both cache values before compiling or running: `RO_ENABLE_DEV_DEPLOY:BOOL=OFF` and `RO_BUILD_PACKET_REPLAY_TESTS:BOOL=ON`. Initial proposed commands (PK03.02 adds the opt-in option/target):

```text
cmake --preset mingw-qt-x64-ci -DRO_ENABLE_DEV_DEPLOY=OFF -DRO_BUILD_PACKET_REPLAY_TESTS=ON
cmake --build build-mingw-preset --target packet_stream_replay_checks --parallel
ctest --test-dir build-mingw-preset -R "^packet_stream_replay_checks$" --output-on-failure
```

The existing `tools/tests/UseSkillToPosInfoPacketTests.cpp` expects profile 23 to emit 0x0190 with length 90 and coordinates/text beginning at client-layout offsets. The server-derived active 0x0190 is a 19-byte ActionRequest, while 0x007E is 102 bytes; this old test cannot be accepted as an oracle and is gated for correction with PK08. A passing helper-only check or existing skill replay is not complete packet parity.

## Verification, approval, and limits

PK03.02 implements only the receive/framing harness and its structural cases. PK03.03 adds outbound and feature/UI cases incrementally under approved contracts. PK03.04 requires a different strong reviewer to inspect branch-to-assertion mapping, test fixture independence, build cache/deploy OFF, actual production entry points, and failures before replay results can close any row. Preserve command, exit code, binary hash/timestamp, test log, and source hashes for each run. Do not start feature-specific tests from applicability approval alone.
