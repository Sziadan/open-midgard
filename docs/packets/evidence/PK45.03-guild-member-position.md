# PK45.03 — guild member position update 0x0156

Date: 2026-11-04. Status: variable framing and member-map mutation traced; server semantics and replay remain open. No rows closed.

Opcode 0x0156 has variable-length framing and routes through `HandleGuildWindowPacket` to `ReadWindowPacket`. The parser selects 12-byte rows, requires a four-byte header and an exact payload multiple of the row stride before iterating. Each row contains account ID u32@0, character ID u32@4 and position ID u32@8 (row-relative). It updates `position` for every existing member matching both IDs; it does not create unknown members or clear positions on other members. The loop does not stop after a match.

After a successful parse, the outer guild-window handler recomputes local position-derived permissions/title if the local member has a matching position entry. The packet branch itself sends no reply. Coverage records the opcode as an unresolved family seed requiring source verification.

Open work: confirm field identity and whether the list is full or delta against the selected server; establish duplicate, unknown-member, stale-position and zero-position behavior; replay aligned/partial rows and verify local permission/title effects. No independent fixture or production replay was performed for this leaf.

## Selected server position-update emitter follow-up (2026-11-04)

The pinned `clif_guild_memberpositionchanged` contract confirms `0x0156` rows as account ID u32, character ID u32, and position ID u32, matching the client's 12-byte stride and pair-keyed member update. The current emitter appends only one row for the supplied member index and sends to GUILD recipients through an available guild session; if no guild session is available it returns without sending. Its source comment explicitly says the intended behavior is to update clients after committing position changes rather than send one packet per position, so the current call pattern/batching is a known implementation caveat, not a client framing mismatch.

The server field is `g.member[idx].position`, confirming the client stores the position assignment. Call-site ordering, duplicate identities, and replay/UI refresh remain open. No discovery row is closed.
