# PK37.03 trade cancellation

The selected `20080910` server uses nine-byte `01F5` for invitation responses (`src/map/packets.hpp:382–388`). The result byte is followed by the partner ID and level. `trade_tradeack` sends result 4 to both peers on decline. `clif_parse_TradeCancel` routes the two-byte `00ED` request to `trade_tradecancel`. That function sends the two-byte `00EE` response for both pending and active trades. For active trades it first sends the virtual item returns and any Zeny status update (`src/map/trade.cpp:520–578`).

The client keeps ownership of the trade after sending cancel or decline and hides its window. While cancellation is pending it rejects another local trade and keeps the window closed if acceptance crosses the request. `00EE` retires a cancel. A decline can complete on the invitation response or a server cancellation. Send failure keeps the existing trade state. Map teardown clears the pending state through `CloseTransactions`.

The loopback replay covers failed sends, exact decline and cancel requests, duplicate cancellation, crossed acceptance, and the terminal response. The packet replay and world-entry handoff checks passed. The standalone commerce protocol fixture passed after updating its test doubles and also covers distance, expiry, and decline acknowledgments. ## Offer and lock acknowledgments

The selected `trade_tradeadditem` searches for the same inventory index or a free position among ten offer slots. The client allows an existing stack to grow when all ten slots are occupied. It checks the current inventory item and available count before sending. A matching `00EA` acknowledgment merges the amount into the offered row and leaves inventory authoritative. The server maps newer add-result values to overweight on this profile, so `00EA` accepts result values 0–2. Its zero-index success before the lock does not settle an item add. `00EC` recognizes side 0 as local and side 1 as remote, matching `clif_tradedeal_lock` and the reference handler. Replay exercises the zero-index acknowledgment, an undefined result and side, a matching success, a stack increment at capacity, and the remote lock.

The selected `00E9` item delta has no inventory index. `Ref/GameModePacket.cpp::Zc_Add_Exchange_Item` passes each non-Zeny packet to `CSession::SetToOtherExchangeList`, which fills the first free position in a ten-row array. The client follows that display rule, including separate rows for repeated packets with identical item fields. A Zeny update replaces the displayed amount without using an item row. Amounts with the signed bit set and zero-quantity item records are rejected. The `00F1` undo emitter has no callers in the selected server source. Its historical variants remain open.

`trade_tradecommit` waits for both peers, sends the inventory and Zeny updates, then emits success `00F0` to both. Its cancellation branches send `00EE`. Ref recognizes `00F0` values 0 and 1. The client applies these results only to its pending commit. If cancellation is already in flight, it reports the result and keeps the cancel request pending until `00EE` arrives. Replay exercises unowned success, an unknown result during a commit, valid success, ten distinct display rows for identical incoming item records, and a separate Zeny update. Live two-peer verification remains open.
