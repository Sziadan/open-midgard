# PK45.03 — guild member online status 0x016D

Date: 2026-11-04. Status: fixed framing, member mutation and outer cache/UI-state effects traced; server semantics and replay remain open. No rows closed.

Opcode 0x016D has fixed size 14 and routes through `HandleGuildWindowPacket` to `ReadWindowPacket`. The parser requires at least 14 bytes, reads account ID u32@2, character ID u32@6 and online flag u32@10. Every member matching both IDs gets `online = (flag != 0)`. It then recalculates the guild's online count from all member entries and accepts the packet even if no member matched.

After parsing, the outer handler erases `mode.m_guildPosList[accountId]` when the flag is zero. It then recomputes local guild position-derived permissions/title from the current member/position map when a local position is found. No network reply is sent. The parser does not clear other stale member rows or position metadata in this branch.

Open work: confirm the account/character key pair, online flag values, meaning of the fixed-size tail and offline position-cache invalidation against the selected server; replay matched/unmatched, online/offline and duplicate rows, including current-local-member impacts. Coverage ownership is marked unresolved/provisional. No independent fixture or production replay was performed for this leaf.

## Selected server online-state emitter follow-up (2026-11-04)

The pinned server uses `0x016D` records with AID u32@2, GID u32@6, and online u32@10, matching the client parser and 14-byte stride. The one-record notice helper sets these from the guild member and sends to the guild with the appropriate exclusion target; it also fills appearance fields in newer structures, which do not change this selected 20080910 packet size. The login helper batches one 14-byte record for each other guild member with a nonzero account ID, excludes the entering player's own account ID, and sends the concatenated records to SELF. This explains why repeated 14-byte records form a packet sequence and why an empty batch has zero payload.

The server source confirms the status field is `member.online`; client treatment as nonzero=true is consistent. Exact UI notice timing (source comments say the first login/map-change info may not display as a message) and production replay remain open. No discovery row is closed.
