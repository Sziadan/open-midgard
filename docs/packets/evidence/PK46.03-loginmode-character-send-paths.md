# PK46.03 — character selection and creation send paths

Date: 2026-11-04. Status: current UI-to-sender paths traced for character select (`0x0066`) and create (`0x0067`), including profile resolution and selected-source request-direction evidence. Full mode lifecycle, result handling, S2C compatibility and replay remain open. No discovery row is closed.

## Character selection path

`UISelectCharWnd` clamps the selected slot, resolves it to a character-list index, and sends `LoginMsg_SelectCharacter`. `LoginMode` accepts only an index inside the current character count, stores the selected index and server slot number, updates local selected-character appearance, and defers to `LoginSubMode_SelectChar`. On the next submode pass it rechecks the list/index, reads `CharNum` from the selected character record, updates local appearance again, builds `PACKET_CZ_SELECT_CHAR`, and sends it. The packet is 3 bytes: opcode `0x0066` (2 bytes) plus slot `CharNum` (1 byte). The `SendPacket` result is ignored; the mode reports “selecting character” regardless of send success, and the local appearance update is not rolled back here.

## Character creation path

`UIMakeCharWnd` sends the selected six stats, hair color/style and name through the character-creation messages, then requests `LoginMsg_CreateCharacter`. `LoginMode` rejects this message when disconnected; otherwise it builds `PACKET_CZ_MAKE_CHAR`, copies the name into the fixed 24-byte field, narrows the six stats and selected slot to bytes, writes hair color/style as 16-bit values, and sends the 37-byte packet. The send result is ignored, after which the mode creates/shows the wait window. The create action therefore has no immediate local failure branch in this sender.

## Profile and source-contract comparison

Both packet IDs are selected through `GetActiveCharacterPacketProfile`. `MakeCharacterProfile` assigns character send IDs from the PacketVer23 login-chain constants; the selected `Packet.h` values are fixed `0x0066` for selection and `0x0067` for creation (`PACKETID_CH_MAKE_CHAR`). These correspond to the 3-byte `PACKET_CZ_SELECT_CHAR` and 37-byte `PACKET_CZ_MAKE_CHAR` layouts. `PK44.04-character-request-directions.md` records production captures and selected-source character-server C2S registration for both requests. The PK01 map-registry snapshot has no parser assigned for these character-server requests, so map registry absence is not treated as rejection.

# PK46.03 — account-server login request path and variants

Date: 2026-11-04. Status: client UI-to-send branch traced; selected-server parser parity and credential-mode review remain open.

## UI action and connection gate

`UILoginWnd::OnButtonClick` for the login action stores the remembered user ID, sends password and user ID into `CLoginMode`, then dispatches `LoginMsg_RequestConnect` (`src/ui/UILoginWnd.cpp:1034-1042`). `CLoginMode` enters `LoginSubMode_ConnectAccount`, opens the configured account endpoint (default loopback:6900), and returns to login status on connection failure (`src/gamemode/LoginMode.cpp:1703-1719`). After connect it optionally sends connect-info, always attempts executable hash check, then requests a password hash or calls `SendPlainAccountLogin` (`:1722-1730`).

## Packet selection and default plain frame

`ResolveAccountLoginPacketKind` honors `[Login] AccountLoginPacket`; recognized values select Legacy/0x0064, LoginChannel/0x02B0, PCBang/0x0277, Login3/0x01FA, or Login4/0x027C. Invalid overrides log and fall through. Without an override, service Korea or `[Login] ForceLoginChannel` selects LoginChannel; other services use Legacy (`LoginMode.cpp:568-596,610-618`). The hash-request path can be forced by settings or selected Login3; if a challenge does not arrive before the fallback delay, `SendPlainAccountLogin` is invoked (`:1454-1460,620-630`).

For the default profile, `PacketVer23LoginChain::kAccountLogin` is `PACKETID_CA_LOGIN` (`0x0064`), with client date `20080910` (`src/network/Packet.h:47-58`, `MapSendProfile.cpp:27-41`). The Legacy sender uses this profile-selected opcode, `ResolveAccountLoginVersion`, bounded C-string copies into 24-byte ID/password arrays, and `ResolveAccountClientType`; `PACKET_CA_LOGIN` is statically asserted to 55 bytes (`LoginMode.cpp:2114-2155`, `Packet.h:227-233,728`). A send failure returns before setting `m_plainAccountLoginSent`; success sets it and waits for account-server response.

The other variants dispatch to separate serializers (`SendLoginChannel`, `SendLoginPcBang`, password-hash/Login3, and Login4). This note does not claim those variant layouts or the server-side registration semantics have been independently compared. Compare each supported service/settings branch to the pinned account parser before closing PK46.03; do not infer server acceptance from the client struct or profile comment.


Account-login variant field maps are expanded in PK46.03-account-login-variant-layouts.md; those layouts are client-derived and do not close account-parser parity.

## Selected character-server comparison — select character (0x0066)

The configured character server registers `HEADER_CH_SELECT_CHAR` as fixed `sizeof(PACKET_CH_SELECT_CHAR)` and dispatches `chclif_parse_charselect` (`src/char/char_clif.cpp:1602`). The server packed request is `int16 packetType, uint8 slot` (3 bytes; `src/common/packets.hpp:136-140`), matching client `PACKET_CZ_SELECT_CHAR` (`u16 PacketType, u8 CharNum`, 3 bytes; `src/network/Packet.h:288-291,736`). The client maps the selected list entry to its stored `CharNum` and sends the populated struct (`LoginMode.cpp:1836-1845`).

The parser uses the slot to query a character belonging to the session account with `delete_date=0`; a missing/deleting or mismatched character is rejected (`char_clif.cpp:1086-1098`). If no map server is available, it returns accessible maps and leaves the client waiting; pending guild-bound retrieval, a banned character, or a character-load failure is rejected (`char_clif.cpp:1079-1084,1103-1123`). This supports the selected request layout and several server-side outcomes only; map transfer completion, client retry behavior, and broader slot-bound checks remain open. No discovery row is closed.
## Selected character-server comparison — create character (0x0067)

With the configured server `PACKETVER 20080910`, the `#else` `PACKET_CH_MAKE_CHAR` layout is active: packed opcode @0, name[24] @2, STR/AGI/VIT/INT/DEX/LUK @26-31, slot @32, hair_color u16 @33, hair_style u16 @35, total 37 bytes (`src/custom/defines_pre.hpp:12`; `src/common/packets.hpp:163-176`). The client `PACKET_CZ_MAKE_CHAR` has the same fields and 37-byte assertion (`src/network/Packet.h:304-316,740`); `LoginMode.cpp:1638-1651` fills name, six stats, selected slot, hair color/style, then sends `sizeof(pkt)`. The server registers `HEADER_CH_MAKE_CHAR` by `sizeof` and calls `chclif_parse_createnewchar` (`src/char/char_clif.cpp:1603`), which reads these fields under the same version branch, defaults job to novice and sex to the authenticated account, and passes all values to `char_make_new_char`; a negative result is sent as a refusal (`char_clif.cpp:1265-1314`).

The client ignores the `SendPacket` result before showing the create wait/status (`LoginMode.cpp:1651-1663`). This note confirms the 2008 request field map and parser handoff only; server creation rules, refusal-code parity, and transport-failure UI recovery remain open. No discovery row is closed.

## Character-create slot handoff recheck (2026-11-05)

The selector computes 9–12 local slots from its fixed extended-slot baseline and existing character `CharNum` values, clamps its selected slot to that local range, and passes the slot through `ActivateCreate`. `LoginMsg_RequestMakeCharacter` stores the supplied `wparam` without an independent range check; the later create sender narrows the slot to a byte. Treat this as a UI-to-mode invariant, not proof of a defect: verify server slot acceptance and stale/settings-derived slot behavior in lifecycle replay. No discovery row is closed.

## Character request recovery

For selected MAIN 20080910, `chclif_accessible_maps` calls `chclif_send_auth_result(fd, 1)`, which sends `0081`. The accessible-map list in the earlier trace requires PACKETVER 20100714 or later. Invalid or deleting slots, pending guild-bound retrieval, bans, and character-load failures use `006C` via `chclif_reject`. Creation sends `006D` with the new character record or `006E` with a refusal code.

The client tracks one sent selection or creation request. Selection commits the chosen character only after a matching CID arrives in `0071`. Creation requires a matching slot in `006D` and prevents a second submission while awaiting `006D` or `006E`. A failed local send or 15 seconds without a usable reply closes the character connection and returns to sign-in. A fresh character list resolves an uncertain creation result before the user attempts another create. The 15-second deadline is a client recovery policy.

The MinGW build used deployment disabled. Full packet replay verified the deadline for both actions, duplicate create suppression, immediate create send failure, matching and mismatched selection CID, and map-transition lifetime. The separate world-entry and both character-deletion profile checks passed. Live character-server and rendered UI checks remain open.

## Character slot identity validation

The selected `006B` has a 24-byte header without account slot-capacity fields. Each 108-byte record carries a 16-bit slot at offset 104. The selected `006D` uses the same record. Validate the full slot before narrowing it to the client field. Reject the entire `006B` list on an out-of-range slot, a zero character ID, or a duplicate slot or character ID. An inconsistent `006D`, including one that cannot fit in the local list, returns to sign-in to fetch the authoritative list without claiming that creation failed or that the result was added locally.

`char_make_new_char` in rAthena `src/char/char.cpp` checks the authenticated account's `char_slots`. The selected server caps this at nine in `src/common/mmo.hpp` and `src/char/char_logif.cpp`. The old list has no field for the account's actual creation limit, so the client uses its representable slot range for parsing and keeps the server's creation refusal authoritative. Later layouts and loaded character pages can use the existing client capacity of twelve. Live character selection and creation remain open.
