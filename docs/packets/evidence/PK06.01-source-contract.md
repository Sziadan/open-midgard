# PK06.01 — guild member notice source contract

Date: 2026-11-04. Status: selected-source contract complete; implementation not started.

## Source-backed identity

The effective server baseline is PACKETVER/PACKETVER_SAK_NUM 20080910, from `PK01.02`; the source snapshot has no Git metadata and deployed binary provenance is unknown. `PACKETVER` is defined in the selected config. `src/map/packets.hpp` lines 867–885 selects packed `PACKET_ZC_UPDATE_CHARSTAT`, 20 bytes, header `0x01F2` when `PACKETVER` is defined; the `#else` branch is legacy 14-byte `0x016D`. `clif.cpp` lines 8676–8710 documents and emits the 20-byte 01F2 shape for the selected configuration.

The packet registry in `clif_packetdb.hpp` is the server's accepted C2S packet/parser registry, not an outbound S2C size table. Therefore the emitter plus packed structure are the applicable server proof for 01F2; omission from that C2S registry would not negate its S2C identity.

## Emitter reachability and branch details

`guild.cpp::guild_recv_memberinfoshort` finds the matching guild member by account and character IDs, saves prior online state, updates online/level/class, updates the guild online count, refreshes the session pointer, and emits the notice only when `oldonline != online`. Its `online` argument originates at `intif.cpp::intif_parse_GuildMemberInfo` from byte offset 14 of the inter-server message. The selected notice code sets packet header, AID, CID and status from that flag. A live `sd` fills gender/hair fields and sends excluding the subject; otherwise appearance values are zero and a guild recipient is selected. Documented status values are 0 offline and 1 online.

## Client gap and scope split

Client `GronPacket.cpp` has a legacy `SetPacketSize(0x016D,14)` and no 01F2 registration. `GuildState::ReadWindowPacket` updates an existing member's online flag for 016D only; `HandleGuildWindowPacket` is registered for 016D, not 01F2. `Member` presently has no gender/hair members. The QML list consumes `Member.online`. After PK05.02, a 01F2 frame is rejected as unknown and closes the receive connection, so framing and router/state support must land in PK06.02 before UI propagation in PK06.03.

The exact selected shape is 20 bytes: opcode [0,2), account [2,6), character [6,10), status [10,14), gender [14,16), hair style [16,18), hair color [18,20). All are unsigned packed integer fields in the source; client convention is little-endian. Only status 0/1 are documented. PK06.02 should validate the full frame and update an existing account+character member atomically; a notice alone does not prove a member should be inserted.
