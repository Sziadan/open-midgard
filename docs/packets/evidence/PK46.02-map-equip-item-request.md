# PK46.02 — equip inventory item request

Date: 2026-11-05. Status: common/ammunition request paths, selected parser, and client acknowledgement/cache update are source-traced. Stale/unsolicited ack behavior and production replay remain open. No discovery row is closed.

`UIItemWnd` routes eligible equipment double-click/use actions to `GameMsg_RequestEquipInventoryItem`; `RequestUseInventoryItem` also routes items with an equip location through this sender rather than the consumable-use packet. The sender rejects zero item index or zero wear location, fills `PACKET_CZ_REQ_WEAR_EQUIP`, and records the item index as awaiting an equip acknowledgement after a successful send.

The client packet is fixed-size 6 bytes: opcode u16@0, item index u16@2 and wear location u16@4. Each map gameplay profile selects `0x00A9`. In the selected 20080910 server source, `HEADER_CZ_REQ_WEAR_EQUIP` is registered using `sizeof(PACKET_CZ_REQ_WEAR_EQUIP)` and `clif_parse_EquipItem`; the PK01.02 final registry resolves it to `0x00A9`, length 6. The server reinterprets the packet as that same struct, converts the client index through `server_index`, and passes the supplied position to `pc_equipitem` (except ammo, for which the server forces `EQP_AMMO`). Dead players are rejected; block-action/invalid/unidentified cases either return or send an equip-failure acknowledgement.

The 6-byte framing and struct field positions align. The ammunition path is also consistent at source level: normal inventory parsing assigns `m_location=0x8000` for item types 10, 16, and 17 (`GameModePacket.cpp:1833-1840`); `RequestUseInventoryItem` routes those equip-capable item types through `RequestEquipInventoryItem` with that nonzero location (`GameMode.cpp:5854-5859`), which serializes it at offset 4. The selected server explicitly ignores the supplied position for `IT_AMMO` and forces `EQP_AMMO` (`src/map/clif.cpp:12153-12158`). No discovery row is closed.

### Acknowledgement and server acceptance continuation

The server rejects dead players before index handling, clears the dead actor and sends no equip ack. It converts the client index and rejects out-of-range indexes silently. NPC/action block restrictions may send a message then return; unidentified items receive a failure ack; a missing item-data pointer returns silently. Pet armor uses its separate pet-equip path. For ordinary items, `pc_equipitem` performs its own eligibility checks and emits 0x00AA failure acks for the checked failure cases or a success ack with selected wear position. The handler permits storage/status exceptions for equip operations, checks equip block/cannot-act state, and enforces the requested slot intersects the item's actual equip position and that the item is not already equipped.

For selected 20080910, the server enum encodes success as result 1 and failure as 0; the client 0x00AA handler treats zero as failure and nonzero as success, matching the legacy branch. The client clears its pending item index only when it equals the ack's item index, but applies a nonzero-result wear-location update independently of that match. There is no explicit timeout for silent server returns. This leaves stale pending state after some rejected requests and makes unsolicited/late ack ordering a replay target; do not infer that the pending index is a correlation token.

Remaining acceptance is production replay across dead/block-action/unidentified/missing items, wrong slot, ammo, success/failure ack, mismatched/late ack, and visible equipment appearance timing. The full location-mask domain and replay remain open; no row is closed.

## Client equip acknowledgement follow-up

The client registers `0x00AA` as seven bytes (`src/network/GronPacket.cpp:91`) and routes it to `HandleEquipItemAck` (`src/gamemode/GameModePacket.cpp:8912`). It reads item index at offset 2, wear location at 4, and result at 6. A matching item index clears `m_waitingWearEquipAck`; result zero, zero index, or zero wear location returns without changing equipment. A nonzero result with usable fields updates the inventory wear-location mask, rebuilds player equipment appearance, and synchronizes it to the local actor (`GameModePacket.cpp:2698-2727`). The handler does not require the ack index to match the pending item before applying that nonzero update, consistent with the stale/unsolicited ordering risk already noted. This is source behavior only; replay and visible acceptance remain open.
