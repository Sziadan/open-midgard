# PK50.02 — snapshot model boundary

The selected snapshots now route to a character-session journal. Each has an 8-byte prefix with a 32-bit row count, followed by 5-byte quest rows or 104-byte mission rows. A valid quest snapshot replaces membership; a valid mission snapshot replaces the objective details. Either can arrive first. Membership determines which IDs belong in the journal.

Both parsers reject zero and duplicate quest IDs, count and length mismatches, and trailing or partial rows. The list accepts the two states emitted for available server quests. The mission parser accepts up to three objectives and preserves the raw 32-bit epoch seconds, current objective count, and names bounded to 24 bytes. The total required count arrives separately in `02B5`.

Production replay covers reversed arrival, independent zero-count replacement, the largest whole-row arrays accepted by the existing stream decoder, malformed arrays, and raw time and name widths. Map replay covers same-connection retention and clearing before a map-server reconnect. The journal also clears on exit from game mode to another mode. The MinGW full packet replay and the focused world-entry, corpse, and skill-choice checks passed with deployment disabled.

For PK50.03, the local `clif_quest_add` writes a single byte at `02B3` offset 7, where its comment and the reference client expect a 32-bit start time. The expiry at offset 11 and objective count at 15 use their documented widths. For `02B5`, correlate the repeated objective rows using their quest ID, order and monster ID. The local server can substitute a Poring ID for a generic objective in `02B2` while emitting the original objective ID in `02B5`. Keep `02B6` confirmation server-owned through `02B7`. Ref's `Gui/Event.cpp:2751` and `Gui/BottomBar.cpp:724` show Q and the quest button opening the journal. The reference declares `02B6` without a located UI producer.

## Earlier source review

The [second review](REVIEW-2026-11-05.md) established the snapshot model and time boundary.

The source-backed packet layout is substantially clearer after PK50.01, but the implementation still needs a typed journal model and exact target semantics:

- Ref's 0x02B1 handler clears the existing quest list before iterating 5-byte `{questID, active}` records using floor division. It does not validate the full packet length/count before clearing.
- Ref's 0x02B2 handler updates existing quest entries in place, converts start/expire fields with `localtime`, and copies up to three objective records. The available sender describes 104-byte records, but the binary reference's time conversion and objective-name copy widths need careful field-by-field adjudication before reproducing them.
- The current client has no `QuestInfo`/quest journal model or journal UI in the inspected paths. Atomic replacement, list↔mission correlation, time units, and preservation of partially updated objectives therefore need a new domain model, not just handlers.
- Newer server PACKETVER branches use 0x097A/0x09F8 and 0x08FE/0x09F9 layouts. The exact deployed 2008 profile and unsupported-variant behavior must be explicit.

The clear-before-parse behavior and presentation conversions in this earlier reference review informed the current implementation. Incremental state updates and the journal UI remain in PK50.03, with live and independent review still open.
