# PK04.04 — Raw account-ID handshake implementation self-review

Date: 2026-11-04. Status: implementation verified; independent review deferred to PK48.

## Source-to-code review

The selected server sends the account ID as four unframed bytes immediately after consuming the 17-byte `0x0065` request; no opcode value is emitted. The client arms the exact expected AID only after ConnectChar connects and before sending `0x0065`. The receive policy precedes all packet-size lookup, buffers arbitrary fragments, validates all four bytes, consumes them once, and then allows adjacent framed packets through the unchanged decoder. Mismatch closes and clears the stream. Partial EOF closes/clears it. `OnConnect` and `OnClose` clear pending state, covering reconnection. Account/map production callers do not arm the prefix. The fake size entries and no-op 8482/8483 dispatch cases are removed.

PK04.03's 19 records cover the selected ConnectChar send/echo/empty-list flow; three literal AIDs including fixed `0x006C` and variable `0x0069` low-word collisions at split positions 1–4; no premature frame, byte-exact suffix and subsequent-frame preservation; wrong full AID; EOF with zero through three bytes; and reconnect to ordinary framing. The replay has production receive framing, and the end-to-end case also passes through production `PollNetwork`/`OnAcceptChar`. The empty list's status and CharSelect transition are asserted.

## Discovery reconciliation

The numeric parents `AUDIT-0x8482` and `AUDIT-0x8483` originated from fake client receive sizes, not rAthena opcode registrations. The source permits arbitrary account IDs, so both can only describe low-word coincidences inside the same four-byte raw prefix; they are not separate server packets. Their coverage rows now classify `ALIAS` to the implemented canonical contract `PK04.RAW-AID`, retaining PK04 primary and PK01/PK02/PK47/PK48 secondary review ownership. No other raw AID value is converted to an opcode classification, and no independent PK48 acceptance is claimed.
