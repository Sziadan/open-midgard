# PK46.02 — vending purchase request 0x0134

Date: 2026-11-05. Status: client guards, selected parser layout, transaction validation and 0x0135 result layout are source-traced. A bounded production sender replay verifies one-entry serialization and local guards; server result parity and transaction behavior remain open. No row closed.

`Commerce::Action` handles `buy` when the requested item index exists in the current shop list, amount is nonzero and no greater than listed stock, and the client is not in a busy trade/vending state. It serializes a 12-byte `0x0134` frame: total length u16@2 (=12), seller ID u32@4, amount u16@8 and item index u16@10. The send result is returned without optimistic stock mutation.

The selected final registry lists `0x0134` as variable-length `clif_parse_PurchaseReq` (`PK01.02-server-registry-final.csv:100`), so this fixed 12-byte client request is a concrete branch of the variable-length parser. The client handles the related `0x0135` result when at least 7 bytes are present: result byte @6 equal to zero decrements the matching shop row by quantity u16@4 using item index u16@2 and reports success; nonzero reports a generic purchase failure without changing stock. Server validation, effects and visible failure emitters are source-traced below; no successful 0x0135 emission was found in the selected path.

Replay stale stock, zero/over-stock amount, stale seller, busy state, send failure, success/failure reply and duplicate/out-of-order results. Primary ownership remains PK38; no row closed.

## 2026-11-04 — selected server parser and transaction continuation

The selected server parser `clif_parse_PurchaseReq` casts the packet to `PACKET_CZ_PC_PURCHASE_ITEMLIST_FROMMC`, passes seller AID plus the session's previously selected `vended_id` to `vending_purchasereq`, then clears `sd->vended_id` whether the purchase succeeds or fails. This is the selected legacy branch; the newer 0x0801 parser instead accepts both AID and unique vending ID.

`vending_purchasereq` rejects missing/non-vending/self sellers and stale vending UID (sending 0x0135 `STORE_INCORRECT`), enforces same-map/view distance unless this is an active remote-search result, and rejects zero entries, more than `MAX_VENDING`, or more entries than the current stock list. Each entry reads amount and client cart index; amount must be positive, the index is adjusted by -2 and must resolve to an actual listed cart item. It checks buyer zeny/overflow, weight, cart/list synchronization, cumulative duplicate-item stock, inventory capacity and item-add limits before applying the transaction. The validation uses a copied vending list to catch duplicates within a multi-item request.

Explicit 0x0135 responses in this path cover stale shop UID, insufficient zeny, zeny overflow, overweight, and out-of-stock. Several invalid/stale/too-distant/capacity conditions return silently. The response builder sends the selected 0x0135 packet with index, amount and result. The success path found here does not call that response builder: it deducts buyer zeny, credits seller after tax, adds purchased items, decrements/deletes shop stock, removes seller cart items, reports the sale to the seller, compacts stock and optionally saves both inventories. No successful 0x0135 emit was found among the exact-symbol call sites; client success-reply behavior therefore remains unproven for this server branch.

The selected wire layouts are confirmed from `src/map/packets_struct.hpp:5609-5620` and `src/map/packets.hpp:1161-1167`: request header is 8 bytes (`packetType@0`, `packetLength@2`, seller `AID@4`); each 4-byte row is `count@0` then `index@2`, making one row a 12-byte request. Response 0x0135 is fixed 7 bytes (`index@2`, `amount@4`, `result@6`). `src/map/clif.hpp:818-826` defines results 0 success, 1 no zeny, 2 overweight, 4 out of stock, 5 trading, 6 incorrect store, 7 no sales info.

Still open: malformed/multi-entry request handling; server success/failure effects, silent-return cases, duplicate/out-of-order replies and window clearing. The existing production replay covers one valid entry, stock guard, failed-send preservation and no optimistic decrement, but does not exercise a server response.
