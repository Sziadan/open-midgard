The function requires an existing party, confirms the requester is a member and leader, rejects party-lock maps and (when configured) instance invitations, then checks that the target is online/active, has not disabled invitations or enabled `noask`, and is not already in a party or holding an invite (`src/map/party.cpp:383-404,406-424,454-471`). ## Client invitation-result receive path follow-up

The active receive profile registers basic/extended invite results as `0x00FD`/`0x02C5` and incoming invitations as `0x00FE`/`0x02C6` (`src/network/MapSendProfile.cpp:228-231`). The client frames the result variants at 27 and 30 bytes and routes both to `HandlePartyInviteAck` (`src/network/GronPacket.cpp:162-169`, `src/gamemode/GameModePacket.cpp:8925,9006`). The handler reads the inviter name at offset 2 and result at 26 as u8 for basic or u32 for extended. It maps results 0,1,2,3,4,5,7,8,9 to already-in-party, rejected, accepted, full-party, same-account, blocked, offline/nonexistent, unavailable, and map-prohibited notices (`GameModePacket.cpp:7528-7580`). Result 2 displays acceptance but does not itself add a party member; separate party member/list notifications own cached membership updates. This distinguishes invite result text from completed party state. Production result/order replay and server authorization remain open.
