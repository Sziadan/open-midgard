# PK45.03 — self status parameter updates

Date: 2026-11-04. Status: selected packet structs and SELF emitters traced; complete type mapping and signed edge remain open. No rows closed.

The size table fixes both 0x00B0 and 0x00B1 at 8 bytes; both route to `HandleSelfStatusParam`. The handler reads status type u16@2 and value u32@4, captures prior selected-character base/job level when applicable, and calls `ApplySelfStatusUpdate`. On success it logs resulting HP/SP and invalidates status windows. For base/job level increases over a positive prior value, it records the level-up tick/type and invokes the respective presentation path; in-world base level 99 also triggers a player message used by the aura path.

`ApplySelfStatusUpdate` handles speed type 0 by storing `g_session.m_speed` and retiming the current move path using 150 as the fallback speed when old/new values are zero. Cart type 99 marks local cart present and applies pending cart state. Other values first update session data: HP/max HP/SP/max SP via `UpdateCharacterVital`; base/job/next experience; combat fields through the shared status mapper; and, with selected-character state, HP/SP, levels, money, status points and skill points. With a live player it also updates HP/SP/max values, base level, base/job experience, and synchronizes where applicable. Unknown values return false unless a shared updater recognized them.

## Selected server parameter-packet contract (2026-11-04)

The pinned server packet structs confirm both `0x00B0` and `0x00B1` are eight bytes with varID u16@2 and a signed int32 value@4; their emitters send to SELF. `clif_updatestatus` routes ordinary parameter changes through `clif_par_change`, while designated long-valued fields use `clif_longpar_change`. This confirms the shared framing but not that every opcode/type pairing in the client's unified handler has been classified correctly.

The server field is signed int32, but client parsing uses u32. Current client update code has no explicit Manner case in the session/player field maps, so a negative manner value is not shown to be stored as a large unsigned value; this is not established as a defect.

## Pinned emitter and signedness boundary (2026-11-04)

The pinned `src/map/clif.cpp` source (`e00eddae72d4569f126efc91ed645cad0d99b4d0b6460790a441354e4b1afa69`) confirms `clif_updatestatus` routes `SP_MANNER` through `clif_par_change(sd, type, sd.status.manner)`. `clif_par_change` assigns its signed `int32 count` to the signed `PACKET_ZC_PAR_CHANGE.count` field and sends 0x00B0 to `SELF` (`clif.cpp:3546–3556`, `3635–3659`; packet struct `packets_struct.hpp:354–359`). The 0x00B1 long-parameter packet likewise uses signed int32 at offset 4; its designated type routes through `clif_longpar_change` (`clif.cpp:3558–3568`).

The client reads the four value bytes as u32. Its current status update mapping has no Manner field case, so the signedness mismatch alone does not prove a bad stored value. Whether negative manner values are emitted in the selected profile depends on setter/state code outside the pinned source hash set; keep that reachability question open. Do not classify this as a defect until the negative-value path and intended client semantics are source-verified or replayed.
