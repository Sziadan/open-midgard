# PK45.03 — normal and player chat notifications

Date: 2026-11-04. Status: client packet framing and UI/actor effects traced. The legacy fallback layout and selected-server text encoding remain open. No rows closed.

The size table marks both 0x008D and 0x008E variable length. `HandleNotifyChat` requires 8 bytes, reads actor AID u32@4, records the actor tick, extracts message text from offset 8, records it in the normal chat channel, and applies an actor chat bubble. `ExtractChatTextWithAid` falls back to extracting from offset 4 when offset-8 text is empty; the source comment says older traces suggest the actor-ID field may be absent, but this alternate layout was not tied to the selected server/profile. In that fallback, the same bytes are also read as the AID by the handler, so binary-prefix handling needs exact capture review.

`HandleNotifyPlayerChat` requires 5 bytes and extracts text from offset 4 into the player-chat channel with its configured green color; it does not create an actor bubble. Neither path normalizes text encoding or validates a terminal NUL beyond the bounded packet extraction helper.

Confirm `ZC_NOTIFY_CHAT` and player-chat payload boundaries for the selected source, whether offset-4 fallback is reachable/valid, and how malformed or non-NUL-terminated payloads should behave. Replay normal speech with/without actor ID, empty text, inline color codes, and multibyte text before closure. No rows are closed.

## Party chat sibling: 0x0109

The size table marks 0x0109 variable length and the router maps it to `HandleNotifyChatParty`. The handler requires 8 bytes, reads AID u32@4, records the AID tick, extracts text at offset 8, and records only nonempty text in the party channel with the configured party color. It does not apply an actor speech bubble. Server text encoding, empty payload semantics, and interaction with the 0x008D fallback were not replayed.
