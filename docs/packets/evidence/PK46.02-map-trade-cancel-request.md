## Selected-server cancel and cleanup path — PACKETVER 20080910

The selected registry accepts fixed two-byte `0x00ED` and calls `clif_parse_TradeCancel`, which delegates to `trade_tradecancel`. If the request is still pending (not accepted into trading), the server clears the partner IDs and sends `0x00EE` cancellation to the requester and, when still connected, the other peer. If a peer is missing, active-trade cleanup still runs for the requester and returns without touching a nonexistent session.

For an active trade, offered items are virtual until commit. Cancellation sends inventory-item refreshes for each side's staged quantities, refreshes zeny status when an offer exists, clears the staged item/zeny values, resets lock/trading/partner state, and sends `0x00EE` to each connected participant. The `0x00EE` packet is the server cancellation notification (`PACKET_ZC_CANCEL_EXCHANGE_ITEM`); the client handler resets trade state and hides the trade view. This differs from successful commit, whose state and responses follow the separate `0x00EF` path.

The server source path does not establish user-visible timing when the client locally closes first, simultaneous cancel/commit interleaving, or reconnect/session teardown behavior. Replay these cases, including cancellation during pending invite and after staged item/zeny offers, before closure. No row closed.
