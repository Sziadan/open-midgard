# PK05.05 deferral — production acknowledgement transition seam

> Current disposition — 2026-11-05: The transition design has now been supplied by the primary-agent review and amended PK05.05 work item. This earlier deferral is historical; implement the generation/preamble decision matrix rather than request another generic stronger review. See [second review](REVIEW-2026-11-05.md).

PK05.05 remains IN_PROGRESS. Review of the current production path found a specific correctness hazard that should be resolved before adding a terminal receive fallback. `ProcessGameModePacketLoop` dispatches an accepted return-to-character-select acknowledgement, whose handler queues a Login mode switch and disconnects; an accepted exit acknowledgement disconnects and calls `Quit`. The same loop may then call `RecvPacket` again and report a closed connection. Today `GameModePacketLoopResult` reports only `receiveDrained`, so a caller cannot tell an unexpected EOF from the expected close caused by an accepted acknowledgement. A naïve EOF-to-Login status transition could replace the accepted result or interfere with exit.

The reliable next implementation needs an explicit production-used transition signal from packet dispatch through the loop result/update caller, plus replay coverage proving that accepted return and exit acknowledgements remain authoritative, while malformed framing/ordinary EOF stop world updates and retain a specific Login status. The current replay harness has timeout/ack cases, but the existing coverage does not establish the full `CGameMode::OnUpdate` handoff boundary. This is a bounded design gap, not a claim that PK05.05 is impossible.

No runtime source changed for this deferral. Preserve PK05.05 as IN_PROGRESS; resume after the transition signal and production caller seam can be tested without broadening unrelated packet or UI work.


## Source-path recheck (2026-11-05)

`ProcessGameModePacketLoop` currently maps every `RecvPacket(false)` result to `receiveDrained`. After that loop, `CGameMode::OnUpdate` returns early only when `ApplyDisconnectTimeoutAfterPacketLoop` fires; otherwise world processing continues. The loop result has no explicit indication that a dispatched acknowledgement already accepted a return-to-select or exit request. The existing timeout path itself sets pending login status and return-to-select state before switching modes. These facts confirm the risk, but do not identify a narrow safe signal: dispatch ordering, pending-action cancellation, receive failure classes, mode teardown and the required replay matrix must be designed together.

Keep PK05.05 IN_PROGRESS and defer source changes for focused transition-signal design/review. Continue with PK46.03 as the next handoff item.
