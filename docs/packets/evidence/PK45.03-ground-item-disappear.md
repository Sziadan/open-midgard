# PK45.03 — ground-item disappearance and world synchronization

Date: 2026-11-04. Status: client removal-to-world path traced. Server reason semantics and frame-timing replay remain open. No rows closed.

The size table fixes packet 0x00A1 at 6 bytes and registers it to `HandleGroundItemDisappear`. The handler reads object ID u32@2, logs whether the ground-item state, world item, or runtime actor existed, erases the ID from `m_groundItemList`, removes it from the pending pickup list, and resets the pickup request tick when that list becomes empty. It does not directly erase `CItem` from the world list.

`SyncGroundItemsToWorld` runs in the game-mode update path. It walks `m_world->m_itemList` and deletes/erases any null or stale `CItem` whose AID no longer exists in `m_groundItemList`. Thus the disappearance packet removes the logical source immediately and the render-world item is removed on the subsequent synchronization pass. This provides the observed retry cleanup: disappearance drops the pending object and clears retry timing when no IDs remain.

The handler ignores any reason/type field because this packet is fixed to six bytes. This pass did not confirm server-side disappearance reasons, eventual UI-frame timing, repeated/unknown IDs, or interaction with generic 0x0080 actor vanish. Replay a successful pickup, another-player pickup, expiry/disappearance, and duplicate disappearance before closing lifecycle parity. No rows are closed.

## Selected server ground-item disappearance (2026-11-04)

The selected server's `clif_clearflooritem` emits `0x00A1` with only the floor-item object ID. With no target session, it broadcasts in AREA around the floor item; when a target session is supplied, it sends to that session as SELF. This matches the client's fixed six-byte packet and explains both world-wide removal and targeted cleanup without a reason byte.

The packet itself carries no cause, so pickup/despawn reason cannot be inferred from `0x00A1`. Runtime timing between logical-map removal and the client's next world synchronization, and behavior for repeated/unknown IDs, still need replay. No discovery row is closed.
