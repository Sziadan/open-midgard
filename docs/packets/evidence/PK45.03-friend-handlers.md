# PK45.03 — friend list, request, and state handlers

Date: 2026-11-04. Status: client framing, invitation UI/reply, and pinned-server reply semantics traced; list variants and replay remain open. No rows closed.

The receive router maps 0x0201 to `HandleFriendsList`, 0x0206 to `HandleFriendState`, 0x0207 to `HandleFriendRequest`, 0x0209 to `HandleFriendAdd`, and 0x020A to `HandleFriendDelete`. The packet size table declares 0x0201 variable and fixes the others at 11, 34, 36, and 10 bytes respectively.

`HandleFriendsList` requires at least four bytes, clears the current friend list, then parses `(packetLength - 4) / 32` complete entries. Each entry is AID u32@0, GID u32@4, fixed name[24]@8, with initial state 1. Any non-multiple-of-32 tail is ignored after the list has already been cleared; verify whether malformed tails should reject the whole packet and whether the four-byte header is correct for the selected profile.

`HandleFriendState` reads AID u32@2, GID u32@6, and state byte@10. It refreshes the friend UI only when `SetFriendState` reports a mutation. `HandleFriendAdd` first calls the commerce receive hook, requires 36 bytes and status u16@2 == 0, then reads AID@4, GID@8 and fixed name[24]@12; it inserts with state 0 and refreshes UI. Nonzero add status is silently ignored; establish whether this packet is a successful add notification and confirm its field semantics from selected-server evidence.

`HandleFriendDelete` reads GID u32@6 after a 10-byte minimum, deletes by GID, and refreshes UI only on successful deletion. `HandleFriendRequest` first invokes the commerce receive hook, requires 34 bytes, extracts the fixed name[24]@10 and emits a system chat message only when nonempty. Its remaining bytes are ignored by this handler.

Open work: validate all layouts and the list header against the effective server packet database and an independent captured/constructed fixture; test duplicate/unknown state changes, failed/successful add status, add/delete ordering, truncated and extra list bytes, empty/non-NUL names, UI refresh behavior, and list replacement/reset across reconnect or character changes. No independent replay or UI scenario has been run for this leaf.

## Friend invitation prompt consumer follow-up (2026-11-04)

The receive path uses `promptKind="friend"` and stores prompt ID, character ID, and fixed name text from the 34-byte request. The same production QML prompt displayed for guild alliances renders the “Friend Request” title and stored name, with Accept/Decline and Escape/close choices. Accept maps to amount 1; Decline maps to 0.

`Commerce::Dispatch` serializes the friend reply as `0x0208`, length 14, prompt ID u32@2, character ID u32@6, decision u32@10. As with alliance replies, a send failure leaves the prompt state intact and a successful send clears `promptKind`. The selected server registry records `0x0208`, length 14, parser `clif_parse_FriendsListReply`, with fields at offsets 2, 6, and 10 (`PK01.02-server-registry-final.csv`).

The client presentation and wire dispatch are traced, but server reply semantics, prompt expiry/replacement behavior, and captured/replayed acceptance evidence remain open. No discovery row is closed.

## Selected server friend-reply semantics (2026-11-04)

The pinned 20080910 packet registry selects `0x0208`, length 14, with fields at offsets 2, 6, and 10. An earlier base registration lists the legacy length 11 form, but the later `PACKETVER >= 20040705` registration is the effective form for the selected profile. The server parser reads offset 2 as the requester account ID, ignores the character-ID field at offset 6, and reads the 32-bit decision at offset 10.

The parser ignores self-adds and replies for an offline requester. It treats decision 0, or a reply without reciprocal pending-request state, as rejection and sends result 1 to the requester. For an accepted reciprocal request, it adds the accepting player's identity to the requester's friend list, sends result 0, and updates the achievement. With `friend_auto_add`, it also attempts the reverse insertion; a full reverse list returns result 2 to the accepting player, while an already-present reverse relation short-circuits. This makes the client prompt ID's account-ID role consistent with the selected server parser. Exact current `clif.cpp` bytes are pinned by PK01.02; no runtime replay has been performed.

Still open: the unpinned friend business-logic implementation that creates/clears reciprocal request state, list framing/malformed-tail semantics, reconnect/reset behavior, and acceptance/rejection replay. No discovery row is closed.
