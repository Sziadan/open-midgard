# PK45.03 — emotion request and acknowledgment loop

Date: 2026-11-04. Status: client outbound/reply path and local effect state traced. selected-server request semantics now traced; visual parity and replay remain open. No rows closed.

## Request

The chat command path resolves an explicit emotion command to an ID, rejects malformed IDs, and rate-limits requests to one per second. It sends a 3-byte 0x00BF packet containing the emotion ID at byte 2. On successful send, it records the request tick and sets `m_isReqEmotion`.

## Reply and presentation

The packet-size table fixes 0x00C0 at 7 bytes, and the router maps it to `HandleEmotion`. The handler requires 7 bytes, accepts emotion IDs 0..80 at byte 6, reads actor GID u32@2, resolves an existing skill/actor target, and sends internal actor message 21. For a local-player reply it clears `m_isReqEmotion`. Internal message 21 maps the ID through `EmotionAction`, creates the emotion sprite/action effect, and special-cases ID 34 as the red chat-prohibit effect. Unknown actor, invalid ID, and unsupported action result in no effect.

## Selected server emotion request/reply contract (2026-11-04)

The pinned 20080910 server parses 0x00BF as a three-byte request and rejects IDs at or above ET_MAX. When basic-skill checking is enabled, it requires the configured novice/basic-skill level; it also rejects the chat-prohibit emotion, enforces a one-second flood limit, honors the emotion action block, and may reroll dice under the corresponding configuration. Accepted requests call clif_emotion.

clif_emotion builds the seven-byte 0x00C0 packet with actor GID u32@2 and emotion type u8@6, then sends it to AREA. This confirms map-stage S2C ownership and the selected request-to-broadcast path. It does not settle client rendering, pending-reply timeout/reset behavior, or malformed/replayed event behavior.


## Additional pending-state timeout audit

The /emotion request writes m_reqEmotionTick and sets m_isReqEmotion only after the send succeeds (src/gamemode/GameMode.cpp:10918-10921). A focused source-wide reference search finds no reader of m_reqEmotionTick, so this stored timestamp does not currently drive a timeout. The flag is cleared by the special skill-failure case (cause==0, skillId==1, btype==1) and by a valid 0x00C0 packet only when its GID resolves to an actor identified as the local player (src/gamemode/GameModePacket.cpp:4187, 6695-6702). Thus a lost acknowledgment leaves the pending flag set; no timeout recovery is present in the inspected client source. The flag has no additional consumers in src, so its persistent state appears informational today, but the intended policy and missing-actor response need stronger review before changing behavior.
