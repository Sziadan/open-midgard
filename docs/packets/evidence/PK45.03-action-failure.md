# PK45.03 — action-failure notification

Date: 2026-11-04. Status: client packet fields, messages, and retry-state effects traced. Selected-server type mapping is traced below; repeated-delivery lifecycle and replay remain open. No rows closed.

The client packet-size table fixes 0x013B at 4 bytes and registers it to `HandleActionFailure`. The handler requires four bytes and reads a u16 type at offset 2. Types 0–2 map to ammunition/weight-limit messages. Type 3 emits a job-dependent ammunition-equipped message for recognized classes; unrecognized types or unsupported type-3 jobs are ignored. Recognized messages go to the chat UI event.

For types 0–2, the client stops retrying a server-rejected action by clearing monster/lock-on target state, attack chase hints/target, skill chase flags, and the world player's target/proceed target when present. It does not reset local movement or unrelated equipment pending indices in this handler. The client comment cites Ref `Zc_action_failure` and message-table entries 242–245, but the exact selected-server packet branch/value mapping was not independently revalidated. ## Complete client switch and repeat behavior follow-up (2026-11-04)

The prior source review omitted the full type switch; it is now traced. Defined types are 0–3. Type 0 uses the ammunition message and explicit color 255; types 1 and 2 use their separate weight-limit messages. Type 3 selects a message by player job: jobs 12, 4035, and 4013 share one message, job 24 uses another, job 25 emits no message, and other job IDs use the generic type-3 message. Unknown type values return before any retry-state mutation or chat notification.

Only types 0–2 clear the attack/skill retry state and player target/proceed-target fields. Repeating one of these failures repeats the same clears; no additional counter or retry backoff is updated in this handler. Type 3 reports (when a message is selected) without clearing that state. This is the client effect only; it does not establish whether the selected server emits each type for the same condition or whether repeated notifications are expected.

This establishes the selected emitter’s packet and documented type meanings. It does not prove every call site’s reachability, repeated-notification timing, or runtime chat rendering; no replay was run and no discovery row is closed.
