## User action to sender

`UIPartyOptionWnd` submits the entered party name and option bits through `GameMsg_RequestPartyCreate` (`src/ui/UIPartyOptionWnd.cpp:624`). `GameMode` normalizes the name, calls `RequestCreateParty`, and clears the pending name if the send fails; on success it stores the option bits for later handling. The option bits are message/local pending state, not fields in this create-request frame. `RequestCreateParty` rejects an already joined party and an empty normalized name; otherwise it zero-initializes the fixed packet, copies the normalized name, sends it, and returns the transport result (`src/gamemode/GameMode.cpp:6491-6504,6513-6531).

## Client layout and profile

`PACKET_CZ_CREATE_GROUP` is statically asserted to 26 bytes: opcode `0x00F9` at offset 0 (u16); zero-initialized `PartyName[24]` at offset 2. `NormalizePartyNameForPacket` trims leading/trailing space, tab, CR, and LF, rejects all-whitespace names, then truncates to 23 bytes before copy, leaving a NUL from packet zero-initialization. The sender selects `ActivePartySend::kCreateParty`, which resolves to the legacy party opcode `0x00F9`. `RequestCreateParty` copies the normalized `std::string` bytes directly into the zero-initialized packet and sends `sizeof(packet)` (`src/gamemode/GameMode.cpp:6513-6532`); this establishes byte truncation and NUL termination but performs no explicit character-set conversion. Compatibility of those bytes with the deployed client input encoding and server name comparison remains a replay/deployment question.

## Selected server validation and asynchronous result

The selected `0x00F9` parser rejects party-locked maps, enforces the basic-skill gate when configured, copies the fixed name field, and calls `party_create` with both option arguments set to zero (`src/map/clif.cpp:13797-13818`). `party_create` trims the name and returns on empty input; it sends result 2 for existing membership or joining/creating state, otherwise marks `party_creating` and requests character-service creation with the unchanged name and zero option values (`src/map/party.cpp:144-164`). The character-service callback clears `party_creating`; success stores the party ID and sends result 0, while name conflict sends result 1 (`src/map/party.cpp:167-195`). The 26-byte `0x00F9` request therefore has no option payload and its success response is asynchronous relative to any subsequent client option update.

## Client acknowledgement and pending options

The client handles the three-byte `0x00FA` acknowledgement in `HandlePartyCreateAck` (`src/gamemode/GameModePacket.cpp:7466-7525`). On result 0, it seeds a local leader record only if the local party cache is empty and a pending name exists, copies the pending name/options into session state, and refreshes the party UI. It opens the group window and, when pending options exist, sends `GameMsg_RequestPartyChangeOptions` with the three selected bits only when at least one bit is set. Because the selected `0x00F9` server call creates with zero option arguments, selected nonzero options are applied through this later request; all-zero options produce no follow-up update. Results 1, 2 and 3 map to duplicate name, already in party and map restriction messages. The handler clears all pending create fields after every handled acknowledgement, including unrecognized result values.

`GameMsg_RequestPartyCreate` stores the normalized pending name before sending, clears that name if the send fails, then stores the option bits and marks them pending after a successful send (`src/gamemode/GameMode.cpp:11055-11071`). This ordering assumes the acknowledgement cannot be dispatched before `RequestCreateParty` returns; the receive/dispatch scheduling and send-failure cleanup effects need focused replay or stronger review before closure. The callback can also occur after the client party cache changes, in which case local seeding is skipped but the success-path option follow-up still runs when pending options are set. No discovery row is closed.

## Client creation-result receive path follow-up

The client frames `0x00FA` as three bytes and routes it to `HandlePartyCreateAck` (`src/network/GronPacket.cpp:159`, `src/gamemode/GameModePacket.cpp:8927`). Result 0 reports success; when the local party cache is empty and a pending name exists, the handler creates a local party with the player as master, seeds cached options from pending values, adds the local member, and refreshes party UI (`GameModePacket.cpp:7466-7507`). It then sends a party-option change when the pending option mask is nonzero, but ignores that send's result; pending option/name fields are cleared afterward (`GameModePacket.cpp:7500-7525`). Results 1,2,3 display duplicate-name, already-in-party and map-prohibited messages; other values have no handled message (`GameModePacket.cpp:7508-7519`). This is client cache/dispatch ordering only: it does not prove that party creation or the follow-up option change was accepted. The option-send failure/reconciliation and server packet ordering need replay before closure.
