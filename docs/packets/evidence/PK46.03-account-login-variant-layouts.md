# PK46.03 — account-login packet variant layouts

Date: 2026-11-04. Status: client serializer variants and guards source-traced; account-server parser/profile parity remains for stronger review.

`CLoginMode::ConnectAccount` optionally sends connect-info-changed, always attempts executable hash check, then sends a password-hash request or dispatches the configured plain-login variant. `AccountLoginPacket` accepts Legacy/0x0064, LoginChannel/0x02B0, PCBang/0x0277, Login3/0x01FA, and Login4/0x027C; absent an override it selects LoginChannel for Korea or when `ForceLoginChannel` is nonzero, otherwise Legacy (`LoginMode.cpp:568-596,610-618,1722-1730`). The profile can be `packetver22` or `packetver23`; login chain constants are sourced from `PacketVer23LoginChain` in both profile constructors. Settings can alter login date/version, client type, and packet variant, so the default must not be treated as universal.

All packet structs use `#pragma pack(push, 1)` (`src/network/Packet.h:5`). Client request layouts:

- Legacy `0x0064`, 55 bytes: opcode u16 @0, version u32 @2, username `[24]` @6, password `[24]` @30, clienttype u8 @54. `PACKET_CA_LOGIN` size is statically asserted.
- LoginChannel `0x02B0`, declared packed fields total 85 bytes: opcode @0, version @2, ID @6, password @30, clienttype @54, IP `[16]` @55, MAC `[13]` @71, IsGravity u8 @84. Sender fills IP/MAC and sets IsGravity=0. No channel-size static_assert was found; runtime send length is `sizeof(pkt)`.
- PCBang `0x0277`, 84 bytes: same prefix through clienttype, then IP `[16]` @55 and MAC `[13]` @71. Size is statically asserted.
- Login4 `0x027C`, 60 bytes: opcode @0, version @2, ID @6, MD5(password) @30, clienttype @46, MAC `[13]` @47. Size is statically asserted.
- Hash flow request `0x01DB`, 2 bytes. On hash challenge, the client sends either `0x01DD` (47 bytes: opcode @0, version @2, ID @6, MD5(challenge+password) @30, clienttype @46) or `0x01FA` (48 bytes with clientinfo u8 @47) when Login3 is selected. Both sizes are statically asserted.

The relevant field assignments are in `LoginMode.cpp:2099-2111,2157-2240,2243-2313` and layouts/opcodes/assertions in `Packet.h:9-15,20-25,227-275,677-694,728-734`. Failed sends return before the corresponding sent/waiting flags are committed. The hash request path records its request tick and waits for a challenge; the configured fallback can later send plain login.

This is client-source evidence only. Resolve each supported settings/service branch against the pinned account-server parser and deployed profile, including acceptance of IP/MAC/clientinfo fields, challenge behavior, and version/client-type semantics. No PK46.03 row closed.

## Selected server comparison — Legacy account login (0x0064)

For configured `PACKETVER 20080910` (`C:/Users/sziad/source/repos/rathena-master/src/custom/defines_pre.hpp:12`), the server login packet table registers `HEADER_CA_LOGIN` with `sizeof(PACKET_CA_LOGIN)` and `logclif_parse_reqauth_raw<PACKET_CA_LOGIN>` (`src/login/loginclif.cpp:488`). The packed server struct is `int16 packetType`, `uint32 version`, `username[NAME_LENGTH]`, `password[NAME_LENGTH]`, `uint8 clienttype`; `NAME_LENGTH` is 24, yielding 55 bytes (`src/common/packets.hpp:127-134`, `src/common/mmo.hpp:154`). Its parser copies the username and password and clienttype into the login session before `login_mmo_auth`, then emits the auth success/failure response (`src/login/loginclif.cpp:266-294`).

The client’s packed `PACKET_CA_LOGIN` has matching fields and size: opcode @0, version @2, ID @6, password @30, clienttype @54, total 55 (`src/network/Packet.h:227-233,728-734`). `LoginMode.cpp:2146-2160` fills those fields, sends `sizeof(pkt)`, and sets `m_plainAccountLoginSent` only after a successful send. This corroborates only the selected Legacy request layout and server parser path. Configured service/settings variants, hash challenge flow, and full login acceptance/retry behavior remain open; no discovery row is closed.

## Selected server comparisons — PCBang and Login4 account login

The configured server registers PCBang `0x0277` at `sizeof(PACKET_CA_LOGIN_PCBANG)` to `logclif_parse_reqauth_raw` and Login4 `0x027C` at `sizeof(PACKET_CA_LOGIN4)` to `logclif_parse_reqauth_md5` (`src/login/loginclif.cpp:489,493`). For PCBang, packed client/server fields match at 84 bytes: opcode @0, version @2, ID/username @6 (24), password @30 (24), clienttype @54, IP @55 (16), MAC @71 (13). The sender fills these fields and sends the full struct (`src/network/Packet.h:677-685`; `LoginMode.cpp:2169-2195`; server struct `src/common/packets.hpp:398-407`). As with Legacy, the raw parser consumes ID, password and clienttype and does not read version, IP or MAC (`loginclif.cpp:266-294`).

For Login4, packed client/server fields match at 60 bytes: opcode @0, version @2, username/ID @6 (24), MD5 bytes @30 (16), clienttype @46, MAC @47 (13) (`src/network/Packet.h:687-694`; `src/common/packets.hpp:409-417`). The client hashes the entered password with MD5 and sends the frame (`LoginMode.cpp:2198-2223`). The registered MD5 parser consumes username, clienttype and passwordMD5, sets `PASSWORDENC`, rejects when server `use_md5_passwds` is enabled, otherwise calls `login_mmo_auth`; it does not read version or MAC (`src/login/loginclif.cpp:296-325`). Thus field layout and parser dispatch match, while deployment configuration determines whether this request path is accepted. No discovery row is closed; configured profile selection, unsupported combinations and end-to-end retry semantics remain open.

## LoginChannel raw-auth field-read recheck (2026-11-05)

The selected `logclif_parse_reqauth_raw` template reads username, clienttype, and password from the packed request. It derives the logged IP from the accepted session socket (`session[fd]->client_addr`), not the packet IP field. The transmitted version, packet IP, MAC, and Gravity flag do not enter this raw-auth path. `loginclif.cpp` SHA-256: `'$h'`. This source comparison does not prove the deployed service selects LoginChannel; profile applicability and account-server provenance remain open.

## Login3 MD5 field-read/configuration recheck (2026-11-05)

The selected `logclif_parse_reqauth_md5` template reads username, clienttype, and binary `passwordMD5`, deriving the logged IP from the socket session. The packet version and Login3 `clientinfo` fields do not enter this authentication function. It explicitly rejects the MD5 flow when `login_config.use_md5_passwds` is enabled; otherwise it authenticates the supplied digest. `loginclif.cpp` SHA-256: `'$h'`. Deployed profile/configuration applicability and challenge/retry behavior remain open.

## Login4 parser-route recheck (2026-11-05)
