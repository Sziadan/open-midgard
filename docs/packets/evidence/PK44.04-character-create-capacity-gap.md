# PK44.04 — Character-create success at client capacity

Current recovery is implemented. An inconsistent `006D` retires the character connection and returns to sign-in with a request to refresh the list. See the [PK46.03 implementation evidence](PK46.03-loginmode-character-send-paths.md#character-slot-identity-validation). The original finding follows.

Date: 2026-11-04. Status: unresolved recovery policy; no runtime change made.

## Finding

`CLoginMode::OnAcceptMakeChar` appends the server-confirmed `0x006D` character only when `m_numChar` is below `std::size(m_charInfo)`. The array has 12 entries. If the response arrives when 12 characters are already stored, the handler leaves the old list unchanged, sets “Login: character created successfully.”, and transitions to CharSelect. The server has confirmed a new character that the client cannot display, so the current branch presents a false local success state.

## Source and configuration boundary

The selected rAthena `PACKETVER=20080910` configuration sets `MAX_CHARS=9` in `src/common/mmo.hpp`; that file's SHA-256 at inspection was `AAC4F5AA4661D087F71DCB52FDF0CC515DEEE2EBD4642C084B9CBDC8B2BB140A`. This is below the client's 12-entry array, so the selected server should not reach this branch if the list is current. The client has no profile-independent proof that every peer's maximum matches this configuration, and stale or later-profile lists could differ.

## Why implementation is deferred

The packet is a success acknowledgement: rejecting it as a failed creation would misreport server truth. A safe fix must define resynchronization after server-confirmed creation when local storage is full—such as reconnecting and refetching the authoritative character list—and verify that LoginMode transition, connection teardown, deferred status, and UI actions all agree. The current replay harness can verify handler and socket state but not the full native Qt/LoginMode lifecycle. Do not merely increase the array without proving all consumers and UI bounds.

This is a bounded implementation/recovery question for PK44.04 and later independent review, not a strong-agent approval gate for unrelated packet work. No discovery row is closed. Continue with other source-backed branches while retaining this exact gap.
