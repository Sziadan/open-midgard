# PK44.04 — Convert selected legacy character records

Date: 2026-11-04. Status: selected-source production-handler conversion verified; visible character UI and other profile variants remain open.

## Source finding

Effective rAthena configuration is `PACKETVER=20080910`, `PACKETVER_SAK_NUM=20080910`; `src/custom/defines_pre.hpp` activates `PACKETVER_SAK_LEGACY_CHARINFO`. In hash-pinned `src/common/packets.hpp`, the 108-byte server record stores `int16 CharNum` at byte 104 and `int16 hairColor` at byte 106. `char_mmo_char_tobuf` populates both fields from the character slot and hair color; `0x006B` sends the record after a 24-byte prefix, and `0x006D` sends the same record immediately after its two-byte opcode.

The current client target `CHARACTER_INFO` is also 108 bytes, but its tail is `u8 CharNum`, `u8 haircolor`, `s16 bIsChangedCharName`. The old direct copies silently interpreted the high slot byte as hair color and the server hair color as the rename flag. This could display the wrong hair color in character selection and created-character state despite matching packet and struct sizes.

## Change and replay

Added an explicit packed source-layout mirror with size and terminal offset assertions. For the resolved login date before 20090225, both `OnAcceptChar`'s 24-byte-header legacy layout and `OnAcceptMakeChar` translate the selected old server tail into the current client structure; the rename flag receives the same legacy default already used by compact conversion. Other character-list layouts and later login dates retain their existing parsing paths. The populated and empty `0x006B` list fixtures now pass through `CRagConnection::RecvPacket -> CLoginMode::PollNetwork -> OnAcceptChar`; the `0x006D` creation fixture now also passes through `CRagConnection::RecvPacket -> CLoginMode::PollNetwork -> OnAcceptMakeChar`.

The selected 20080910 `0x006B` fixture now contains two independent server records: GID `0x12345678`, name `RuneA`, job 7, slot 7 and hair color 18; then GID `0x87654321`, name `RuneB`, job 8, slot 3 and hair color 7. Each selected server byte record sets the hair-color palette and terminal `hairColor` field to the same value, as `char_mmo_char_tobuf` does. Production checks verify both records are preserved and translated, index 0 is selected, and status/CharSelect transition are correct. A valid empty 24-byte `0x006B` response separately checks no-character status and transition. A malformed 133-byte response with a 24-byte header, one full record and one trailing byte is rejected as an unsupported layout, clears the character list and returns to Login. A fourth packet containing the first record tests `0x006D` creation success. All four replay records are in `PK44.04-character-record-conversion.jsonl`.
