# PK40.02 auction transactions

The client sends the selected `024D` registration from an acknowledged item reservation. It checks ordered positive prices, the signed Zeny range, and the server's one- to 48-hour duration. The server owns the configured fee, price cap, and Zeny updates. On a matching success the client retires the reservation and queries own sales. On failure it sends the staging cancellation so the server returns a still-staged item. If the char server already returned the item through normal inventory packets, the staging cancellation sees an empty server selection.

Bid, cancel, and stop use `024F`, `024E`, and the six-byte outbound `025D`. Each action rechecks the selected listing against the current page, including seller, buyer, and prices. Bid must exceed the current price. Cancel requires an own sale without a buyer, and stop requires an own sale with a buyer. Inbound `025D` still frames as four bytes.

The client serializes these transactions because `0250` and inbound `025D` have no auction ID. Registration and bid both use `0250` result 1. Cancel can reply through either `0250` or `025D`. Asynchronous win and loss notices leave pending transactions intact. The map server pushes an own-bids page after successful bid and an own-sales page after successful stop. The client expects those pages through its existing search reply owner and accepts no additional query while they are pending.

Production replay captures all four requests, rejects a stale quote and duplicate registration, and verifies the two server-pushed pages and the cancel failure through `025D`. Live registration failure and refund, the visible auction controls, and recovery from silent drops remain open. The selected protocol supplies no transaction ID for replaying a request after an ambiguous outcome.
