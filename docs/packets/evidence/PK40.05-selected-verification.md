## Auction staging on close and same-map warp

Closing the window retires its search view. The stage remains tracked if the cancellation send fails, including when the server closes the window. A late staging success can still identify that reservation. The selected search and own-list parsers release staging when a subsequent search reaches the server.

`pc_setpos` leaves auction staging on the map-server session. The packet dispatcher drops gameplay requests while the character is off-map, apart from load-end acknowledgement. The load-end handler refreshes inventory from the full server inventory, which still contains a confirmed staged unit that has not been submitted for registration. Same-map reuse now retains staging. A matching slot and item in the snapshot contributes only its unreserved count to available inventory. The subsequent search releases the reservation through an ordinary pickup frame. No pre-load cancellation is needed and ordinary pickup handling stays intact.

Registration in flight is excluded from this adjustment because the server can consume the item before sending its result. Registration overlapping a warp still needs inventory reconciliation and live verification.

Production replay sends a same-map warp, receives the load-end acknowledgement, publishes two units in `02E8`, and checks that one is available. Auction reopen sends `0251`. Its ordinary return pickup restores the count to two, then `0252` settles the search. Full packet replay, chat-notice, world-entry handoff, and the plan validator passed with deployment disabled.

An in-server map change that replaces the game mode now carries the reservation, unanswered stage or transaction, and the old search's reply ownership into the new mode. ### Registration refusal after a snapshot

In `clif_parse_Auction_register`, fee refusal `5` keeps the valid staged unit in server inventory. When a snapshot has restored the matching slot and item during registration, this refusal restores the client's reservation accounting before it sends `024B`. The server's ordinary return pickup then restores the unit once. Closing the window or selecting Unstage during registration leaves the reservation owned by the registration reply. Result `2` can mean that the staged inventory row is already invalid, so it still needs separate reconciliation.

Result `4` is shared by an immediate failure to forward registration and an asynchronous rejection from the character server. In the first branch the map server has not consumed the item. In the second it has consumed it and `intif_parse_Auction_register` sends result `4` before restoring the item through `pc_additem`. The acknowledgement lacks a discriminator. This checkpoint leaves the result `4` inventory calculation unchanged and keeps that case open.
