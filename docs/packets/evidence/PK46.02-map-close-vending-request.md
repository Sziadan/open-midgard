# PK46.02 — close vending request 0x012E

Date: 2026-11-05. Status: active-vending close guard, opcode-only frame, client local reset, selected server close path and client seller-disappearance handling are source-traced. The production sender replay now verifies close-send success/failure and local reset. Server SQL-failure and lost-broadcast behavior remain open. No row closed.

The commerce close action sends a two-byte opcode-only `0x012E` request only when `vendingActive` is true. A failed send returns before local state changes. On success the client clears `vendingActive`; the shared close path clears the vending draft and `vendingPending`, then hides the vending window. When vending is not active, this action instead sends a vending-open/update frame, so that branch is not part of the 0x012E request.

The selected registry assignment snapshot identifies length 2 and `clif_parse_CloseVending` (`PK01.02-server-registry-assignments.txt:118`). The parser unconditionally calls `vending_closevending`; that function is a no-op unless the server session is currently vending. When active, it deletes the vending item/shop SQL rows, clears `state.vending` and `vender_id`, broadcasts an actor-disappear entry for the seller, and removes the seller from the in-memory vending DB. SQL failures are logged, but the session state and disappear broadcast still proceed. No dedicated close acknowledgement is emitted in this path.

The production client replay covers close send success/failure and local reset. Still open: server no-op when not vending, pending-open race, SQL failure, lost board-close broadcast, and remote disconnect while vending. The client clears local active state after successful send, while server close is asynchronous and has no direct ack; a lost request or ordering race can leave local/server state divergent until a later state update. Primary ownership remains PK37; no row closed.

## Selected-server close and SQL-failure cross-check (2026-11-05)

The selected parser invokes `vending_closevending` for `0x012E`; the server helper is a no-op unless `sd->state.vending` is true. For an active shop it attempts to delete vending-item rows and then the vending row, logs if the SQL expression reports an error, but proceeds to clear `state.vending`, zero `vender_id`, broadcast the close, and remove the in-memory vending entry. Because the two SQL calls are joined with short-circuit `||`, a failure deleting item rows skips the vending-row delete; server memory still transitions to closed. This is a source-observed failure behavior, not a replay or live SQL result.
