# PK45.03 — guild creation acknowledgement

Date: 2026-11-04. Status: fixed framing, result messages and cache effects traced; selected-server result semantics and replay remain open. No rows closed.

The size table fixes 0x0167 at 3 bytes and the router maps it to `HandleGuildCreateAck`. The handler reads result byte@2 and records a system chat message. Results 0–3 map to created, already in a guild, duplicate guild name, and missing required item; all other values map to generic creation failure. Success is green; failure is red.

On result zero, it erases the local character's entry from `m_actorNameListByGID` and its request timer from `m_actorNameByGIDReqTimer`. The source comment states guild membership/ID arrives through 0x016C, while the name response is refreshed so self-hover can show the updated guild/rank. The ack itself does not mutate membership or guild-window records.

Open work: validate result codes/messages against the selected server and creation flow; ensure cache invalidation plus subsequent 0x016C/name reply ordering produces correct self-hover state; replay each result, unknown codes, duplicate/out-of-order membership notifications and stale pending guild data. No independent fixture or production replay was performed for this leaf.

## Server create-result correlation follow-up (2026-11-04)

The pinned `clif_guild_created` emitter sends a three-byte result packet to SELF and copies the supplied flag directly. The current external `guild.cpp` caller trace maps result 1 to already in a guild, 3 to missing required Emperium when that configuration is enabled, 2 to inter-server creation failure/same-name guild, and 0 to success after the guild-server returns a nonzero guild ID. On success, the caller first writes `sd->status.guild_id`; the client comment that the separate membership packet supplies guild ID is consistent with that ordering, while the create ack itself only clears the actor-name/request-timer cache.
