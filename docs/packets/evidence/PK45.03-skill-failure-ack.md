# PK45.03 — skill-failure acknowledgment

Date: 2026-11-04. Status: client resolver and selected server emitter audited; packet field partition and observed failure-cause values differ. Snapshot provenance for call-site files and replay remain open. No rows closed.

The client size table fixes 0x0110 at 10 bytes and routes it to `HandleSkillFailAck`. The handler delegates to the commerce receiver, requires 10 bytes, and decodes skill ID u16@2, btype u32@4, result u8@8, and cause u8@9. Nonzero result is ignored. For result 0, it clears the player's motion-freeze flag and returns selected swing/cast states (2, 5, 7, 8, 9, 12) to idle. The special `cause==0 && skillId==1 && btype==1` path clears the pending emotion request. It then resolves zero, one, or two user-facing chat notices from skill ID, btype, cause, and the `m_isSkillFail` setting.

The message resolver contains many explicit skill/type cases, including two-message results. Only a clipped portion was inspected here; exact message IDs, colors, job branches, bounds, and reference mapping need a dedicated parity review. Replay rejected skills in each major family, unknown btype/cause/result values, and failures during attack/chase/cast animation before closing this handler. No rows are closed.

## Resolver branch audit follow-up (2026-11-04)

The previous note that only a clipped resolver portion had been inspected is superseded by this bounded source audit. For `cause == 0`, `skillId == 1` maps `btype` 0–6 through the seven-message table (message IDs `0x9F`–`0xA5`), `btype == 7` produces two notices (`0x17F` and `0x518`), and `btype == 8` produces `0x518`. Other explicit cause-0 skill branches are skill ID 27 -> `0xD6`, 50 -> `0xCD`, and 52 -> `0xCF`; unmatched cause-0 cases can use generic `0xCC` only when the skill-fail notice setting is enabled. The notice container has capacity for two messages, matching the two-notice branch.

For causes 1–10, the resolver maps to message IDs respectively: `0xCA`, `0xCB`, `0x328`, `0xDB`, `0xE9`, `0xEF`, `0xF6`, `0xF7`, `0x244`, and `0x11D`. Cause 10 is suppressed when the skill-fail notice setting is disabled; unknown cause values return no notice. The receive handler requires 10 bytes, reads skill ID u16@2, btype u32@4, result byte@8, and cause byte@9, and ignores nonzero result values before resolving notices.

This completes the client-side branch and message-ID inventory for the inspected resolver. It does not prove the server's cause/btype meanings, locale/reference-string parity, or runtime color/UI behavior. No replay was run and no discovery row is closed.

## Hash-pinned selected-server field-layout comparison (2026-11-04)

The selected 20080910 rAthena `PACKET_ZC_ACK_TOUSESKILL` uses the legacy branch: opcode `0x0110`, skill ID u16@2, btype i16@4, itemId u16@6, flag u8@8, cause u8@9; packed size 10. `clif_skill_fail` assigns `skill_id`, `btype`, `itemId`, sets `flag=0` (failure), sets `cause`, and sends to `SELF`. The packet size and final two byte fields agree with the client, but the client currently reads `ReadLE32(packet.data+4)` as a single btype and does not separately read itemId.

For this server layout, the client combines the server's 16-bit btype and 16-bit itemId into one u32 value. This is a field-partition mismatch. The explicit itemId call sites found in the current external source use causes 71/72, which the client resolver drops before consulting btype; their observed client effect is therefore a missing failure notice. Other itemId-zero cause paths retain the btype value in the low half. The call-site files are not in PK01.02's original hash list; their current hashes are recorded below.

Escalate targeted call-site/itemId reachability and determine the correct profile-specific client interpretation before changing code. No discovery row is closed; production replay remains open.

## Cause enum and explicit itemId call-site follow-up (2026-11-04)

The current external server `clif.hpp` defines `USESKILL_FAIL_NEED_ITEM=71` and `USESKILL_FAIL_NEED_EQUIPMENT=72`; `clif_skill_fail` defaults `itemId` to zero but forwards the supplied cause, btype, and itemId into the packet. Unless globally disabled by `battle_config.display_skill_fail & 1`, it sends the failure packet to SELF. The client's resolver has cases only for causes 0–10 and returns no notice for unknown causes, including 71 and 72.

A bounded exact-call scan of the current `src/map/skill.cpp` found four explicit itemId calls: two `NEED_EQUIPMENT` calls (`btype=0`, item IDs from `require.eqItem[0]`/`reqeqit`) and two `NEED_ITEM` calls (`btype=1` or `require.amount[i]`, item IDs `ITEMID_POISON_BOTTLE`/`require.itemid[i]`). If these calls reach the emitter under the selected configuration, the client drops their 71/72 causes and displays no failure notice. This is a concrete protocol behavior to verify, not a confirmed production impact.

Provenance limit: `clif.cpp` and `packets_struct.hpp` match PK01.02's pinned hashes. `clif.hpp` SHA-256 is `4BE8D550C203378B4444655922927FA309E5C513BD43819B1877AD7F24C27C5D`; `skill.cpp` SHA-256 is `F9AAC46FDC14D36F9B018EB3CD52A39C790FE3B23923E657B5F3CA6C3F6F2982`. These latter files were not in the original PK01.02 hash list and the server tree has no Git metadata, so confirm their provenance before treating the call-site finding as final. A stronger review should verify the cause enum/call paths against the intended server revision and replay causes 71/72 plus nonzero itemId cases.

No discovery row is closed.
