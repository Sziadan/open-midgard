# PK46.02 — trade accept/decline request 0x00E6

Date: 2026-11-05. Status: client actions/timeouts and selected server acceptance/rejection path are source-traced. Production sender replay covers accept/decline frames and failed-accept preservation; duplicate/stale invitation replay and end-to-end result timing remain open. No row closed.

The client size table fixes `0x00E6` at 3 bytes. `Commerce.cpp` emits this frame from three incoming-trade paths: explicit reply, closing an incoming trade window, and automatic decline when `UpdateTradeContext` sees the inviter disappear or the 30-second request timer expire. The action byte is u8@2: `3` accepts and `4` declines. A successful decline resets trade state and hides the window; a successful acceptance changes `tradeIncoming` to `tradeWaiting`, updates the request tick and waits for server confirmation. Failed sends preserve the prior UI/state. An attempted acceptance first checks that the inviter remains in the local peer table and within distance 2; failure sends code 4, resets the incoming trade and reports unavailable/distant peer.

Closing or expiring an outgoing request uses `0x00ED` instead of `0x00E6`, so this leaf covers only the accept/decline packet. The selected parser reads the action byte and calls `trade_tradeack` (`src/map/clif.cpp:12529-12533`). It returns silently if already trading or no partner is recorded; otherwise it rechecks the partner is online and reciprocal. Type 4 cancels both sides, clears both partner/lock states and emits cancel results. Only type 3 accepts; other values return silently. Acceptance rechecks distance (except permitted @trade), NPC/storage/vending/buying-store/trading state for both players, then sets both trading flags, clears both offer records and sends acceptance results (`src/map/trade.cpp:108-177`). Server result codes are 0 too-far, 1 absent character, 2 failed, 3 accepted, 4 canceled and 5 busy (`trade.hpp:11-17`); the client opens the trade window only for result 3 and otherwise resets it with a message (`Commerce.cpp:74-78`). This trace does not prove timeout/close race behavior, stale partner reuse or duplicate replies; replay those sequences before closure.

The production sender replay covers accept, decline, and failed-accept preservation. Still open: auto-decline on disappearance/timeout, duplicate/stale invitation behavior, and server response/result timing. Primary ownership remains PK37; no classification is closed.
