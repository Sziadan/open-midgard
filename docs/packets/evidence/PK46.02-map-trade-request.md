Date: 2026-11-05. Status: client call path, guards, fixed frame, selected server target/permission/distance checks and invitation dispatch traced. Accept/reject/timeout replay remains open. No row closed.

## Client action and serialized request

`CGameMode` player-context dispatch obtains the target actor name and calls `ro::commerce::PlayerAction` (`src/gamemode/GameMode.cpp:11104–11107`). For `PlayerContext_RequestDeal`, `src/gamemode/Commerce.cpp:154–157` rejects zero/self targets and empty names before dispatch; `busy()` rejects active/waiting/incoming trade or active/pending vending. The trade branch requires a current `tradePeers` entry and distance at most 2. It sets `tradeRequestTick`, then serializes fixed 6-byte opcode `0x00E4` with target ID u32@2. If send fails, the request returns false before partner/waiting/UI state is updated, though the tick has already changed. On success it stores partner name/ID, sets waiting and visible trade UI state, and reports that it is waiting for acceptance.

The client size table fixes `0x00E4` at 6 bytes (`src/network/GronPacket.cpp:137`). The selected registry assignment snapshot lists length 6 and `clif_parse_TradeRequest` (`docs/packets/evidence/PK01.02-server-registry-assignments.txt:78`). The server maps the packet target ID to a session, blocks requests when the sender cannot act (except while in a chatroom), handles recipient `@noask` and mail-writing state, and checks the basic skill requirement when configured. `trade_traderequest` rejects no-trade maps, missing/self targets, targets using an NPC, configured pending invitation conflicts, already-trading targets, and either party lacking trade permission. Unless the sender may use `@trade`, it enforces same-map `TRADE_DISTANCE`. Success sets reciprocal pending partner IDs and sends a trade prompt to the target; there is no success acknowledgement to the requester in this path. Some errors return protocol responses, while noask/action/map restrictions may be silent or a chat message.

The dedicated [0x00E6 accept/decline leaf](PK46.02-map-trade-ack-request.md) now holds the selected parser/result trace and explicit duplicate/stale-invitation replay gates; the summary above is retained here because invitation completion is part of the 0x00E4 request lifecycle.

## Open verification

The 0x00E6 reply parser passes the one-byte result to `trade_tradeack`. The server ignores replies when already trading or without a pending partner; it resolves the reciprocal partner and clears the requester-side partner state on missing/mismatched peer errors. Result 4 sends cancel responses to both sides and clears both partner/deal-lock states. Result 3 rechecks distance (including the `@trade` override), then rechecks NPC/vending/buying-store/storage blockers for both sides. On success it sets both trading flags, clears both offers, and sends 0x00E7 result 3 to each player. Too-far and busy/failure paths clear both pending partner states and return status packets.

The client handles incoming 0x00E5 by resetting prior trade UI and opening the invitation state. Its accept path requires an incoming invitation and locally checks the known peer is still present and within distance; if that precheck fails, it sends result 4 and resets locally. Otherwise it sends 3/4 via 0x00E6; successful accept changes to waiting state until 0x00E7, whose result 3 opens the trade UI and non-3 result resets/closes it with a mapped message. A failed accept send leaves local incoming state unchanged. Server rechecks remain authoritative.

Still open: timeout/disconnect cancellation races, reciprocal state cleanup under simultaneous requests, delayed/duplicate responses, and the early send-failure mutation of `tradeRequestTick`. Replay just-inside/at/outside distance, @trade override, noask, mail-writing, accept/reject, send failure and disconnect. No production replay or independent fixture was performed; retain `AUDIT-0x00E4` as `UNREVIEWED`.
