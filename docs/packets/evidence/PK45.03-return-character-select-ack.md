# PK45.03 — return-to-character-select acknowledgement

The character server's `chmapif_parse_authok` sends `2B03` result 0 if it is stopping and result 1 after registering authentication. The map server forwards the byte in `00B3`. The client now treats result 0 as a refusal when character select is pending, clears the request, and reports the refusal in system chat. The production replay sends the request from the chooser, dispatches the refusal through the packet router, and verifies that a fresh chooser request can be sent on the same map connection. Live character-server shutdown and refusal presentation remain open.

Date: 2026-11-04. Status: framing, pending-action gate and teardown effects traced; char-server result origin and lifecycle replay remain open. No rows closed.

The size table fixes 0x00B3 at 3 bytes and the router maps it to `HandleDisconnectCharacterAck`. The handler reads the current pending disconnect action and packet result byte@2. It proceeds only when action is `ReturnToCharSelect` and result is 1. Otherwise it logs the packet type/action and leaves pending state and mode untouched.

On the accepted path it clears the pending action, sets `g_session.m_pendingReturnToCharSelect = 1`, then calls `ReturnToLoginMode`, which clears pending disconnect action, clears inventory and chat events, disconnects the connection, and switches to login mode. The character-select flag is intentionally set before the mode switch so the login/character flow can observe it; verify the consumer and reset lifecycle.

## Selected server character-select acknowledgement (2026-11-04)

The selected server defines `0x00B3` as `ZC_RESTART_ACK`, a three-byte packet containing a one-byte result. Its documentation assigns result 1 to “disconnect, char-select”; `clif_charselectok` copies the supplied result and sends SELF. This confirms the client's expected packet size and the success-result meaning used by its accepted disconnect path.

The emitter alone does not establish which request/callers produce each result, when the character-select mode flag is consumed, or whether teardown order is correct in every disconnect lifecycle. Those remain replay/review questions. No discovery row is closed.
