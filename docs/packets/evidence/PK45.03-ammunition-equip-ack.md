# PK45.03 — ammunition equip acknowledgement

Date: 2026-11-04. Status: client framing and inventory mutation traced; server field semantics and replay remain open. No rows closed.

The router maps 0x013C to `HandleEquipAmmo`; the size table fixes the packet at 4 bytes. The handler requires four bytes, reads an inventory item index u16@2, clears wear-location mask 0x8000 from every inventory item except that index, and sets that item's wear location to 0x8000 when the index is nonzero. Index zero therefore clears the ammo mask from all inventory items without setting another one. It also clears `m_waitingWearEquipAck` and logs the index. It does not directly refresh inventory UI, and it ignores whether `SetInventoryItemWearLocation` found a matching item.

Open work: confirm whether the field is the inventory index, how index zero is used, and whether this acknowledgement is authoritative for ammo state in the selected server version. Replay valid index, zero, unknown index, delayed/stale ack, and normal equipment coexistence; verify the 0x8000 mask and UI refresh through the production receive path. No independent fixture or runtime replay was performed for this leaf.

## Selected server ammunition emitter follow-up (2026-11-04)

The pinned `clif_arrowequip` emitter confirms `0x013C` as opcode plus u16 client inventory index (four bytes total), sourced from `sd.equip_index[EQI_AMMO]` via `client_index`, and sent to SELF. This establishes that the payload is the currently equipped ammunition slot's inventory index, not an item ID or wear mask. The server populates it from authoritative equipment state. The no-ammunition sentinel after `client_index` conversion is not established by this function and remains open, as do call-site ordering and stale-ack replay.

The packet field contract is now source-backed. Verify the sentinel conversion and coexistence with general equipment state before closing the leaf; no discovery row is closed.

## Empty-slot client-index sentinel follow-up (2026-11-04)

The pinned `client_index` conversion is `server_index + 2` returned as u16. The current unpinned server session state stores `equip_index` as int16 and initializes empty equipment slots to -1; passing the empty ammo slot through that conversion wraps to client index 1. Real cart/inventory indices are encoded starting at 2, so 1 is the no-ammunition sentinel. On the client, no inventory row has index 1; its ammo handler therefore clears the old 0x8000 wear mark without assigning it to an item. This resolves the previously open zero-index concern for the current source pairing.

Caveat: the equip_index type/initialization are from unpinned pc.hpp/pc.cpp; revalidate against the intended server revision before relying on the sentinel cross-revision. Runtime stale-ack and equipment coexistence cases remain open. No discovery row is closed.
