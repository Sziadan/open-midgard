## Identity and disposition schema

Use canonical identity `(connection stage, direction, active profile/date, opcode, layout variant)`. A numeric opcode or historical definition name is not sufficient identity. Preserve every original `AUDIT-*` discovery parent when splitting one number into multiple stage/profile/layout contracts. For catalog definitions absent from the 990-row union, assign a durable historical identifier based on the source opcode plus exact definition and guard evidence; do not describe the catalog as a multi-revision archive or invent a discovery row.

For every row reviewed, capture: input source and source row/key; primary and secondary owner; canonical identity/contract links; selected-profile status; server declaration and final registration/guard; parser/emitter/call-site evidence; Ref path when available; source hash or evidence artifact; disposition and unresolved question. Keep `coverage.csv` as the public discovery-owner ledger. The historical reconciliation output is a separate evidence CSV with columns:

`historical_id,opcode,definition_names,discovery_parent,stage,direction,profile_or_date,canonical_contract,primary_owner,selected_config_status,server_guard_or_registration,client_path,evidence,disposition,open_question`.

Disposition values follow the implementation plan only: applicable, inactive for selected source configuration, C2S-only with verified send/unavailable-server-feature evidence, alias to a verified canonical identity, or unresolved. “Registered”, “declared”, “no client handler found”, and historical absence from the configured registry are evidence observations, not dispositions by themselves. If evidence is weak, keep UNREVIEWED.
