# PK46.02 — ground-item take request

Date: 2026-11-05. Status: client pickup path, request layouts, and basic/extended pickup-ack cache effects are source-traced; the explicit legacy request still conflicts with the selected registry. Ack correlation, failure recovery and production replay remain open. No discovery row is closed.

## User action to sender

`WinMain.cpp` forwards the left-button click to `CGameMode::OnMessage`; after skill handling, `TryRequestGroundItemFromScreenPoint` can call `TryBeginGroundItemPickup` for a ground item. The pickup helper verifies that the object ID exists in the local ground-item map, records pickup intent, and sends immediately only when the item is in pickup range. Otherwise it follows the client chase/move path. The update path retries a take request for an in-range item after its retry interval, unless a move acknowledgement is pending.

## Client layouts and selected server registration

`SendTakeItemRequestPacket` rejects object ID zero and delegates to `BuildActiveTakeItemPacket`.

- PacketVer22/PacketVer23 use opcode `0x00F5`, `PACKET_CZ_TAKE_ITEM2`, eight bytes total: opcode at 0–1, padding u16 at 2–3, object AID u32 at 4–7. The builder sets the padding field to zero. The selected 20080910 final server registry lists `0x00F5`, length 8, parser `clif_parse_TakeItem`, position 4.
- The explicit legacy profile uses opcode `0x009F`, `PACKET_CZ_TAKE_ITEM_LEGACY`, six bytes total: opcode at 0–1 and object AID u32 at 2–5. In the selected 20080910 final registry, however, `0x009F` is a 14-byte `clif_parse_UseItem` packet with fields at 4 and 10. This configured legacy send therefore does not match the selected server identity/layout and must remain unresolved or be gated away for that server.

The PacketVer22/23 request length and object field position match the selected `0x00F5` registration. The registry/parser evidence establishes framing and parser identity, but not final take-item action behavior, range/security checks, failure replies, or pickup retry limits. Stronger review gate: establish which client map-send profile is actually selected for the target executable and reconcile it with the server’s effective 20080910 registration before classifying compatibility. Do not treat the Legacy `0x009F` sender as a valid take-item request under this registry or alter opcode ownership without profile/build evidence. The legacy path is a concrete mismatch under the selected server profile. No packet-specific production replay or live UI acceptance was run, and no discovery row is closed.

## Client pickup-ack receive path follow-up

The client supports basic `0x00A0` (23 bytes) and extended `0x02D4` (29 bytes) pickup acknowledgements; both route to `HandleItemPickupAck` (`src/network/MapSendProfile.cpp:209-210`, `src/network/GronPacket.cpp:84,336`, `src/gamemode/GameModePacket.cpp:8898-8899`). The handler reads result at offset 22 and returns immediately for nonzero result, leaving the pending ground-object queue and retry tick unchanged. On result zero it builds the inventory item from the acknowledgement fields, optionally reads delete-time/ownership fields in the extended form, starts local pickup animation using the first queued ground-object ID, announces/adds the item, then clears the queue and retry tick (`GameModePacket.cpp:2495-2557`). The response contains no ground-object ID used for request-token correlation; a late or unsolicited success can therefore consume the current queue-front ID for animation while still adding the returned inventory item. This is client source behavior, not proof of selected-server response identity or failure semantics. Keep profile compatibility, stale-ack behavior, retry recovery and visible replay open.
