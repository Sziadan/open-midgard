## Selected-server lock and commit path — PACKETVER 20080910

`clif_packetdb.hpp` registers fixed two-byte `0x00EB` to `clif_parse_TradeOk`, which delegates to `trade_tradeok`. The server silently ignores a lock request when trading is inactive or the sender is already locked. A missing partner cancels the trade. Otherwise it sets the sender's `deal_locked` to 1, sends source-only `0x00EA` success with index 0, then sends fixed `0x00EC` lock notifications to both sides: `who=0` for the locker and `who=1` for the peer. A duplicate lock has no response because of the already-locked guard.

The client sets `lockPending` only after a successful `0x00EB` send and rejects lock attempts while item-add ack is pending. Its `0x00EC` handler marks local lock and clears `lockPending` for `who=0`; `who=1` marks the remote side locked. The shared `0x00EA` handler only updates an item offer when `tradeAddPending` is true and the returned index matches the pending inventory item; lock status is carried separately by `0x00EC`.

Commit is separate: fixed two-byte `0x00EF` invokes `trade_tradecommit`. It requires an active trade and a locked requester, cancels if the peer is gone, changes the requester's lock state to 2, and waits until the peer also reaches state 2. Only then does it run the per-side exploit checks and aggregate `trade_check`; failure cancels the trade. Thus one side locking does not finalize or transfer the offer. Duplicate/out-of-order locks, delayed ack ordering, lock-after-item races, and client reset/retry behavior still require production replay.
