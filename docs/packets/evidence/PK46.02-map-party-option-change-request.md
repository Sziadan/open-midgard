# PK46.02 — party option change request 0x0102

The current sender uses the selected server's EXP-only layout. See the [current crosswalk](PK46.02-party-guild-crosswalk.md) for the implementation and replay.

Date: 2026-11-05. Status: UI/post-create paths, fixed serialization, selected server leader authorization and field interpretation, and the six-byte 0x0101 client handler are source-traced. The client item field is ignored by the selected 0x0102 parser and the response has no item fields; option-combination and cache/UI replay remain open. No discovery row is closed.

## Current client paths

`UIPartyOptionWnd` submits option bits through `GameMsg_RequestPartyChangeOptions` when configuring an existing party. `GameMode` decodes the experience/item-sharing bits and calls `RequestChangePartyOptions`. The sender writes both option fields and sends the packet; it contains no local party/master guard, so the UI gate and server authorization need comparison.

After a successful party creation response, `GameModePacket.cpp` seeds local party state and, when the saved pending option bits are nonzero, sends the same `GameMsg_RequestPartyChangeOptions` message. This is a second current sender path tied to the create result. Zero option bits do not trigger a follow-up packet.

## Client layout and profile

`PACKET_CZ_CHANGE_GROUP_MASTER` is six bytes: opcode `0x0102` at offset 0 (2 bytes), experience option at offset 2 (2 bytes), and item option at offset 4 (2 bytes). `ActivePartySend::kChangePartyOption` resolves to the legacy party opcode `0x0102`. The item-option bit encoding is delegated to `BuildPartyItemOption`.

## Selected registry comparison

`PK01.02-server-registry-final.csv` maps opcode `0102` to fixed length 6 and `clif_parse_PartyChangeOption`, with field positions `2,0`. Client opcode and length match the selected registration; parser permission and value semantics remain open.

## Selected server authorization and field interpretation

The selected `clif_parse_PartyChangeOption` requires a nonzero party ID, a resolvable party, the session to appear among its members, and that member to be leader (`src/map/clif.cpp:13936-13953`). It reads `RFIFOL` at the registered offset 2 into `expflag`. For command `0x0102`, it calls `party_changeoption` with that 32-bit value and the party's existing item option; the parser comment states the client cannot change the item field (`src/map/clif.cpp:13955-13958`). The request sender instead writes `ExpOption` as u16 at offset 2 and `ItemOption` as u16 at offset 4 (`src/gamemode/GameMode.cpp:6575-6585`; packet layout in `src/network/Packet.h:636-640`). Therefore the server's 32-bit EXP read includes both client fields: nonzero item-option bits make `expflag` nonzero even when the client EXP field is zero, while the requested item option is not applied by this parser. `party_changeoption` forwards the EXP and retained item values to the character service (`src/map/party.cpp:877-886`). This is a source-backed wire/handler mismatch; the downstream interpretation and user-visible effect require production replay. The selected pre-2009 server response is also a six-byte `0x0101`: `clif_party_option` writes the 32-bit EXP value at offset 2, and emits item bytes only for `PACKETVER >= 20090603` (`src/map/clif.cpp:7987-8015`). The client handler reads EXP as u32 but only reads item state when packet length is at least 8 (`src/gamemode/GameModePacket.cpp:7681-7700`); with the selected six-byte registration, that item branch is unreachable. Thus the response cannot reconcile the item state changed or retained by the server in this profile. The character-service callback stores returned EXP/item values as provided (`src/map/party.cpp:920-937`), so exact non-boolean EXP values from the u32 read may persist; verify their deployed effects in replay.

## Field values and send result

`RequestChangePartyOptions` value-initializes `PACKET_CZ_CHANGE_GROUP_MASTER`, assigns the active profile opcode, encodes `ExpOption` as u16 0/1 at offset 2, and encodes `ItemOption` at offset 4 as bit 0 = party item sharing enabled and bit 1 = shared-vs-individual item mode (`src/gamemode/GameMode.cpp:6507-6510,6575-6585`; `src/network/Packet.h:636-640,787`). The total fixed frame is 6 bytes. Send failure is returned to the caller; this request has no local option-state commit in the builder itself. The UI submit and post-create follow-up are separate call sites described above.

## Client option-update receive path follow-up

The client registers `0x0101` as fixed six bytes (`src/network/GronPacket.cpp:171`) and routes it to `HandlePartyOptionChanged` (`src/gamemode/GameModePacket.cpp:8969`). The handler reads a 32-bit EXP option at offset 2; value 2 displays a refusal message without changing the cached EXP option, while other values update it. It refreshes the party UI. The handler also contains an optional branch for item-option bytes at offsets 6 and 7, but that branch requires packet length at least 8 and is unreachable under this registered fixed six-byte framing (`GameModePacket.cpp:7681-7700`). Thus the source supports client EXP-option reconciliation, not item-option reconciliation through this packet. Verify selected-server response behavior and this framing against a production capture before closure.


## Bounded source-claim review — 0x0102 selected-version mismatch (2026-11-05)

The active client `PACKET_CZ_CHANGE_GROUP_MASTER` writes u16 `ExpOption` at offset 2 and u16 `ItemOption` at offset 4. In the selected server's `clif_parse_PartyChangeOption`, `RFIFOL(fd, info->pos[0])` reads the entire u32 at offset 2; for command 0x0102 the handler then retains the server's existing item option and ignores the incoming item field. Therefore the client item-option word contributes to the server EXP integer: item-option 1, 2 or 3 yields high words 0x0001, 0x0002 or 0x0003 (for example, EXP false + item option 1 is parsed as 65536). This is not a matching field contract. The existing client updates its local EXP/item cache when transport send succeeds, before a server result; the selected six-byte 0x0101 response reports only EXP.

The selected `src/map/clif.cpp` hash still matches PK01.02 (`E00EDDAE72D4569F126EFC91ED645CAD0D99B4D0B6460790A441354E4B1AFA69`). The current local `src/map/party.cpp` raw forwarding/assignment path has hash `5A87D5E1CE5260145AA7DC7B5DD3F0A9C878C05C2F20D8E7DB893B38A723D75F`, but that file is not listed in PK01.02's pinned hash table and the server directory has no Git metadata; treat persistence/effect claims as provisional pending source-provenance review.

Defer a code fix for stronger review: the selected server packet accepts EXP only, while the reconstructed UI sends combined EXP/item settings and has no item-option field in the response. A reliable fix needs a version-specific UI policy and authoritative-cache decision, not just a struct-width edit. Do not close the request row. Next bounded request: party leave/disband 0x0100.
