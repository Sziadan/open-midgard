# PK46.02 — NPC string-input response 0x01D5

Date: 2026-11-05. Status: NPC input submission, variable-length framing, selected parser storage and Windows ACP/byte-count behavior are source-traced. Deployed codepage compatibility, boundary effects and send-failure UI recovery remain open. No discovery row is closed.

## User action to sender

`UINpcInputWnd` snapshots the NPC ID, submit action and text into local values, then hides the input window before dispatching `GameMsg_RequestNpcInputString`. `GameMode` rejects NPC ID zero, null text and empty text; computes `8 + strlen(text) + 1` bytes and rejects lengths above 65535; then zero-initializes the frame, writes the packet ID/length/NPC ID, copies the text bytes, and sends. The zero-initialized trailing byte supplies the null terminator. The UI is already hidden if validation or transport fails; no restoration occurs in this path.

## Client layout and profile

`PACKET_CZ_NPC_INPUT_STRING` has opcode `0x01D5` at offset 0 (2 bytes), packet length at offset 2 (2 bytes), NPC ID at offset 4 (4 bytes), then a null-terminated text payload at offset 8. The sender selects `LegacyNpcScriptSend::kInputString` (`0x01D5`). The total frame is variable length and includes the terminating NUL.

## Selected registry comparison

`PK01.02-server-registry-final.csv` maps opcode `01d5` to variable length (`-1`) and `clif_parse_NpcStringInput`. The selected parser computes payload bytes as packet length minus the fixed header, returns for an empty payload, copies at most `CHATBOX_SIZE` bytes into `sd->npc_str` with bounded string copy, updates NPC-input idle time when configured, and resumes `npc_scriptcont` with the supplied NPC ID. The shared continuation requires the active NPC identity, secure timeout, proximity/visibility, no active progressbar and a valid script state; rejected/stale input has no generic reply. Detailed prompt and parser source evidence is in [PK45.03](PK45.03-npc-string-input.md).

For selected PACKETVER=20080910, the parser's newer-protocol length increment is inactive; the NUL byte is part of the packet payload. The sender measures bytes with `strlen` and relies on a zero-initialized trailing byte for the terminator. The receiver does not perform an explicit encoding validation. The parser's bounded copy establishes its storage cap, but malformed nonterminated payload behavior and exact multibyte boundary interoperability still require replay or stronger parser-boundary review.

## Text encoding and edit boundary

The Windows `WM_CHAR` handler converts each UTF-16 code unit through `WideCharToMultiByte(CP_ACP, ...)` and forwards the resulting bytes to `UIWindowMgr::OnChar` (`src/main/WinMain.cpp:663-666`). `UIEditCtrl` stores those bytes in `std::string`; its general `m_maxchar`/`SetText` truncation counts bytes, and backspace pops one byte (`src/ui/UIWindow.cpp:757-800`). NPC string mode sets `m_maxchar=0`, so no edit-control byte cap is active for this path (`src/ui/UINpcInputWnd.cpp:358`). Submission measures with `strlen` and serializes the same raw bytes without UTF-8 conversion (`src/ui/UINpcInputWnd.cpp:414-446`; `src/gamemode/GameMode.cpp:6252`). The server uses `safestrncpy` to copy at most `CHATBOX_SIZE` payload bytes into the script string buffer (`src/map/clif.cpp:13377-13395`), with no separate encoding conversion.

Thus the live client path is machine-ACP byte input, not UTF-8 normalization; multibyte/codepage sequences may be split by byte limits or backspace. Stronger review should compare deployed Windows ACP and server/script expectations before asserting non-ASCII parity.
