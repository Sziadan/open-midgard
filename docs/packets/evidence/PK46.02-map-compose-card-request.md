# PK46.02 — compose-card request

Date: 2026-11-05. Status: client selection/cancel, selected server insertion validation, 0x017D result emission and client cache update are source-traced. Silent rejection and stale-ack/runtime replay remain open. No discovery row is closed.

`UIItemCompositionWnd::SubmitSelection` sends the selected card inventory index and equipment inventory index through `GameMsg_RequestComposeCardIntoEquipment`, then closes the window. `CancelSelection` sends both values as -1; the client sender rejects negative indices and emits no packet. For a submitted request, the sender checks that both indexed inventory slots resolve and are nonzero, and that the first item is a card. It does not locally enforce that the second item is equipment. The sender serializes `PACKET_CZ_ITEM_COMPOSITION` and has no acknowledgement wait state.

The packet is six bytes: opcode `0x017C`, signed 16-bit card item index, signed 16-bit equipment item index. The configured gameplay profiles and selected packet profile use `0x017C`; the selected registry row is length 6 and dispatches to `clif_parse_InsertCard`.

The selected server handler ignores requests without a session or while trading, translates both client indices with `server_index`, rejects out-of-range inventory positions and calls `pc_insert_card` (`src/map/clif.cpp:13522-13543`). `pc_insert_card` additionally validates existing inventory rows, weapon/armor target, card type, identified/unequipped target, reserved card slots, equipment compatibility and a free slot. Those validation failures return silently. If card deletion fails, the server sends `0x017D` with failure=1; on success it inserts the card ID into the target slot and sends failure=0 (`src/map/pc.cpp:5559-5618`, `src/map/clif.cpp:7133-7142`). The selected response struct is seven bytes: opcode, equipment index, card index and result byte (`src/map/packets.hpp:1119-1125`). The successful path calls `pc_delitem` with type bit 1 set: this mutates authoritative inventory and weight but suppresses a separate `clif_delitem` notification while still sending the weight update (`src/map/pc.cpp:5607,6066-6088`). Therefore the composition ACK is the client path that applies the card/equipment record change; verify its arrival relative to weight and other inventory refreshes in replay.

## Client composition-result receive path — 2026-11-05

The client frames `0x017D` as seven bytes and registers it to `HandleItemCompositionAck` (`src/network/GronPacket.cpp:251`, `src/gamemode/GameModePacket.cpp:8917-8919`). The handler clears `m_lastCardItemIndex` without matching it to the response. On result 0, it looks up both returned inventory indexes; if both cached items exist, it locally removes one card and inserts the card ID into the first empty equipment slot, then refreshes dependent windows and reports success. Result 1 reports failure; other nonzero results clear the remembered card index without a message (`GameModePacket.cpp:1490-1530`). The handler does not reopen the selection UI when the server silently rejects validation before emitting the ack. Verify inventory-update/ack ordering, malformed or stale indexes, silent validation failure and send failure before closure; no row closed.
