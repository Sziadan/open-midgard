# PK45.03 — commerce cart deltas and cart window

Date: 2026-11-04. Status: client fields and selected-server cart-delta variants/polarity traced; transaction ordering and replay remain open. No rows closed.

The commerce receiver handles 0x0124 and 0x01C5 as cart-item additions, with minimum packet lengths of 21 and 22 bytes respectively. Both read the client item index at byte 2, a four-byte amount at byte 4, and item ID at byte 8. The 0x01C5 form includes an item-type byte at byte 10; 0x0124 assigns type zero and shifts the following fields one byte earlier. Both read identified, damaged, refine, and four slot values. The item is inserted or replaces the existing entry at that index; if the index already existed, the previous quantity is added to the incoming quantity. The handler sets `hasCart` but does not validate nonzero fields or reject trailing bytes.

Opcode 0x0125 requires at least eight bytes, reads index at byte 2 and a four-byte amount at byte 4, then calls the shared removal helper. Missing indexes are ignored; an amount at least as large as the stored quantity erases the entry, otherwise it subtracts the amount. Opcode 0x012C requires three bytes and posts a cart-transfer failure notice selected by byte 2 (zero means weight limit, nonzero means item-capacity limit); it does not mutate cart contents. Opcode 0x012D requires four bytes, clamps the advertised vending-slot count from byte 2 to 12, shows both cart and vending windows, clears the draft, resets vending active/pending flags, and posts the drag-items prompt.

The selected server follow-up below confirms the 0x01C5 layout and 0x012C status polarity for PACKETVER 20080910. The 0x0124 form remains a legacy variant outside this selected profile. The handlers use minimum-length checks rather than exact lengths, and no independent fixture or production replay was performed. No rows are closed.

## Selected server cart-delta emitters (2026-11-04)

The pinned `clif_cart_additem` emitter confirms the effective PACKETVER 20080910 variant is `0x01C5`, not legacy `0x0124`: the selected profile satisfies the `PACKETVER >= 5` branch, which adds the item-type byte for a 22-byte record. It serializes the converted client index, amount, item ID/type, identify/damage/refine flags, and cards, and returns without sending for an invalid cart slot or inactive session. `clif_cart_delitem` emits the matching `0x0125` index/amount delta to SELF. The `0x012C` add-to-cart acknowledgment uses result 0 for weight failure and 1 for count failure. These source contracts match the client's add/remove and failure paths; the 21-byte `0x0124` client branch is for an older profile.

This resolves the selected wire variant and error polarity. Cart state transaction ordering and malformed/extra-byte replay remain open; no discovery row is closed.


## Additional client delta mutation trace

The 0x0124/0x01C5 add branch checks only its minimum size (21 or 22 bytes), decodes a row, adds the incoming quantity to any existing row at the same item index, then stores the incoming row fields and marks cart state present (src/gamemode/Commerce.cpp:63). The 0x0125 remove branch checks a minimum of 8 bytes and calls
emove, which erases a row when the requested amount meets or exceeds its current amount, otherwise subtracting the amount (Commerce.cpp:33,64). Neither branch requires an exact packet length, so trailing bytes are accepted. This describes receiver mutation and its framing permissiveness; malformed trailing data, zero/large quantity boundaries, duplicate and reordered deltas, and list/delta ordering still need replay coverage before asserting transactional behavior.
