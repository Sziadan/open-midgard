# PK46.02 — global chat request 0x00F3

Date: 2026-11-05. Status: UI call paths, Qt UTF-8 cleaning, profile-selected opcode, variable frame and selected server validation/broadcast path are source-traced. Runtime profile selection and text/replay boundaries remain open. No row closed.

`SendGlobalChatMessage` rejects a null/empty player name or empty message. It builds `playerName + " : " + message`, then serializes a variable-length frame of `4 + payload.size() + 1` bytes: profile-selected opcode u16@0, total length u16@2, text bytes at @4, and a zero terminator from vector initialization. It rejects a total above 65535 and returns the socket send result. The normal chat path calls this after talk-script decoding; slash-command fallthrough also sends here and adds a local chat bubble only on successful send.

The opcode is profile-dependent: the legacy map-send profile uses 0x008C while PacketVer22 and PacketVer23 use 0x00F3 (`src/network/Packet.h:82–91, 104–117`; profile selection in `MapSendProfile.cpp:96–185`). The selected registry inventory lists variable-length `0x00F3` with `clif_parse_GlobalMessage`; the packet database also has other profile IDs routed to that parser.

The selected server parser calls `clif_process_message` before either channel or area delivery. For the selected pre-20151001 server branch, it requires the frame length to include a terminating NUL and rejects embedded NUL/trailing bytes by checking the declared message length against `strnlen()+1`; it also rejects unterminated text. The input must begin with the authenticated character name followed by the literal ` : `, otherwise the server closes the connection as a spoof/desync. The message must fit within `CHAT_SIZE_MAX-1` bytes. The parser does not perform an explicit UTF-8 validation in this path; byte sequences are copied through bounded string helpers.

Before delivery, at-command handling may consume the text; muted/chat-blocked sessions and configured minimum-chat-delay violations are rejected. Accepted channel-bound messages go to `channel_send` and return without the normal area echo. Otherwise the formatted name/message is broadcast, echoed to the sender as 0x008E, and passed to chat logging/NPC chat triggers. `clif_GlobalMessage` emits the area chat packet with the speaker GID and terminated message. This explains why a client-local bubble after a successful send is not proof of server acceptance or broadcast.
