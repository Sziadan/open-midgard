The commerce prompt action handles `promptKind == "friend"` by sending a fixed 14-byte `0x0208` frame: prompt ID u32@2, character ID u32@6 and answer u32@10 (`1` accept, `0` decline). A failed send preserves the prompt; success clears `promptKind`. The prompt ID and character ID are stored separately, unlike guild/alliance replies.

The selected final registry assigns length 14 to `clif_parse_FriendsListReply` with positions `2,6,10,0` (`PK01.02-server-registry-final.csv:235`). The current `clif.cpp`, `clif_packetdb.hpp`, and `defines_pre.hpp` hashes match the PK01.02 source snapshot; the server directory has no Git revision metadata (`PK01.02.md:4-5,10,36-47`). Under effective `PACKETVER=20080910`, the parser reads the account ID at registered offset 2 and a 32-bit reply at offset 10; it does not read the registered character ID at offset 6 (`src/map/clif.cpp:15485-15498`). It rejects self-account replies and missing online requesters. A decline or a mismatch in reciprocal pending character IDs sends rejection status 1 to the original requester. Acceptance adds the inviter to the responder's friend list and sends success status 0 to the requester; if `battle_config.friend_auto_add` is enabled, it also adds the responder to the requester's list and sends a second success status. Capacity failure in either list sends status 2 (`clif.cpp:15500-15548`). The reply parser uses the pending server-side character-ID pair as the acceptance correlation; the wire character ID field is ignored in this branch. The outgoing invitation, target prompt, and resulting acknowledgement/client cache update are source-traced below; runtime ordering and stale/duplicate behavior remain unverified.

## Matching server and client result paths

The selected server emits the target invitation as 0x0207 with account ID at 2, character ID at 6, and name at 10 (`clif_friendlist_req`, `src/map/clif.cpp:15417-15426`). The final registry assigns 0x0207 a 34-byte frame. The client registers 0x0207 to `HandleFriendRequest`; its commerce receive path stores `promptKind=friend`, account ID, character ID, and name after a 34-byte minimum check (`GameModePacket.cpp:7819-7830`, `Commerce.cpp:82`). That state is what the previously traced friend prompt action uses to form 0x0208.

The server emits 0x0209 with result type at 2 and, when a player is supplied, account ID at 4, character ID at 8, and name at 12 (`clif_friendslist_reqack`, `src/map/clif.cpp:15397-15412`). The selected final registry assigns length 36. The client routes 0x0209 to `HandleFriendAdd`; commerce records a success/failure message, and the handler adds the friend and refreshes the friend UI only for status 0 (`GameModePacket.cpp:7787-7806`, `Commerce.cpp:83`). Nonzero statuses are surfaced as the generic declined-or-failed message and do not mutate the local friend list.

With `friend_auto_add` disabled, acceptance adds the responder to the original requester's list and returns status 0 to that requester. When enabled, the server also adds the requester to the responder's list and returns a second status-0 update. These branches and the request/reply packet identities are now source-traced; selected-profile replay, live prompt timing, and stale/duplicate response behavior remain open. ## Selected-server request-field cross-check (2026-11-05)

The selected registry fixes `0x0208` at 14 bytes with fields at offsets 2, 6, and 10. `clif_parse_FriendsListReply` reads the u32 at offset 2 as the target account ID and the u32 at offset 10 as the answer for this packet version; the character-ID field at offset 6 is present in the wire contract but the current handler has its read commented out. The target account ID corresponds to the invitation's account ID from `0x0207`, while the server validates the pending mutual `friend_req` state using character IDs stored in the two sessions.

Decline or a stale/mismatched request returns a failure acknowledgement to the original requester. A missing/offline target returns without an acknowledgement. Acceptance requires a free slot in the original requester's friend list, adds the responder, and sends success; `friend_auto_add` may then add the original requester to the responder's list. The existing production replay verifies the client emits account/prompt ID, character ID, and answer values, but does not exercise these server transitions, offline behavior, slot limits, or the configured auto-add branch. Keep PK16 primary ownership and those runtime/state cases open; no row closed.
