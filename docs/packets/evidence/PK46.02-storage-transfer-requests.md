## Zero-count failure response correction (2026-11-04)

Under the PK01.02 selected PACKETVER=20080910 source, failed inventory-to-storage insertion emits `clif_storageitemremoved(*sd,index,0)` followed by a zero-count drop acknowledgement (`src/map/storage.cpp:334-358`). Failed storage-to-inventory insertion emits `clif_storageitemremoved(*sd,index,0)` plus the add-item failure result (`storage.cpp:367-383`). Successful storage removal calls `storage_delitem` with the requested positive amount, which sends that amount (`storage.cpp:305-323`). Thus zero is a failed-transfer correction, not a command to erase the storage row.

The emitter sends `PACKET_ZC_DELETE_ITEM_FROM_STORE` with index at 2 and u32 amount at 4 (`src/map/clif.cpp:4935-4943`, packed 8-byte struct at `src/map/packets.hpp:1029-1034`). The client `HandleStorageItemRemoved` decodes that count and now ignores nonpositive values before calling `RemoveStorageItem`; this prevents the session helper's `amount <= 0` erase behavior from deleting storage on a failed transfer. Current `storage.cpp` SHA-256: `FACBB35B2D02CDC1E91D09BE03940EEF80C62CFCF27F66DC27120416C394134A` (the server checkout has no Git revision metadata).

This fixes the source-confirmed local failure-state mismatch. Successful transfer ordering, duplicate/out-of-order updates, and production replay remain open; no discovery row is closed.

## Client transfer-notification cache follow-up

The client handles storage-add variants `0x00F4`/`0x01C4` through `HandleStorageItemAdded`, which builds a storage item from the packet and adds it to the session storage cache (`src/network/MapSendProfile.cpp:222-223`, `src/gamemode/GameModePacket.cpp:8922,8930,2405-2419`). The fixed eight-byte `0x00F6` removal notification reads item index u16 at offset 2 and amount u32 at 4; amounts <=0 are ignored as failure/correction and preserve the row, while positive amounts call `RemoveStorageItem` (`src/network/GronPacket.cpp:154`, `GameModePacket.cpp:8923,2421-2442`). The storage-open status handler also opens the storage state and relevant UI windows (`GameModePacket.cpp:2332-2345`). These handlers establish the client cache effects for notifications, but not which notification sequence accompanies each direction of transfer or whether inventory updates precede/follow storage updates. Keep ordering and atomicity as replay gates.
