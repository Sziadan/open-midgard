## User action to sender

`UIItemSellWnd` sends `GameMsg_RequestShopSellList` when Sell Confirm is activated. `RequestNpcShopSellList` requires sell mode and at least one deal row, computes a variable frame length of 4 header bytes plus 4 bytes per row, and rejects lengths above 65535. It writes the legacy shop sell opcode and frame length, then serializes each row as source inventory index u16 followed by quantity u16. Quantity is clamped to 0..65535; the source index is narrowed to 16 bits. It sends the completed buffer and returns the transport result.

## Client layout and profile

`PACKET_CZ_PC_SELL_ITEMLIST` has opcode `0x00C9` and frame length in its 4-byte header. Each repeated row is `{inventoryIndex:u16, amount:u16}`; total length is `4 + 4 * rowCount`. The sender uses `LegacyNpcShopSend::kSellItemList` (`0x00C9`).

## Selected registry comparison

`PK01.02-server-registry-final.csv` maps opcode `00c9` to variable length and `clif_parse_NpcSellListSend`. The parser floors row count as `(packetLength - 4) / 4`, rejects while trading or without a selected server-side NPC shop, calls `npc_selllist`, clears `npc_shopid`, then sends the one-byte 0x00CB result. `npc_selllist` rechecks shop proximity/type and each row's adjusted inventory index, nonzero item data, and quantity not exceeding the current stack. Normal shops also require the item to be sellable and compute the zeny return; script-backed shops instead populate `@sold_*` arrays and invoke the configured on-sell event.

For a normal shop, the function validates all rows first and then deletes each row in a second loop before crediting zeny. The validation compares each row independently with the original current stack; it does not aggregate duplicate indices. Thus two duplicate rows can each pass although their combined quantity exceeds the stack. If an early deletion succeeds and a later `pc_delitem` fails, the function returns failure before the zeny credit, after earlier items have already been removed. This is a transaction-atomicity concern that needs a stronger reviewer and a focused replay before any repair is proposed. The inspected code also has no explicit zero-quantity rejection (the field is u16) and no row-remainder validation in the parser; keep those as separate boundary cases.

The client uses the 0x00CB result to close/clear the shop UI; inventory and zeny changes arrive through their own state packets. `PK45.03-npc-shop-lists-results.md` contains the related list/result framing evidence.

## Remaining evidence and ownership

Selected-source duplicate-row finding: `npc_selllist` validates every row independently against the pre-mutation inventory amount, then calls `pc_delitem` in a second pass; a failing deletion returns immediately, and zeny is credited only after the deletion loop (`src/map/npc.cpp:3048-3074,3091-3119`). `pc_delitem` rejects an amount greater than the now-current stack (`src/map/pc.cpp:6066-6071`). Therefore two duplicate-index rows can each pass validation while their sum exceeds the stack: the first row removes items, the second fails, and the player receives no sale credit.

Stronger review and regression required before repair: reproduce the duplicate-row case in the production parser path, then design an atomic validation/mutation change that preserves script-backed shop behavior. Also replay zero/max quantity, stale/narrowed indices, malformed trailing bytes, unsellable items, send failure and success/failure inventory/zeny/result ordering. Preserve existing primary ownership; no production replay and no discovery row closure.y row is closed.
