# PK46.02 — NPC menu selection request 0x00B8

Date: 2026-11-05. Status: menu submission, selected server parser/continuation gates, and client menu-output/choice mapping are source-traced. Production replay and send-failure recovery remain open. No discovery row is closed.

## User action to sender

`UINpcMenuWnd` ignores a zero NPC ID or choice. For choice `0xFF` it closes all NPC dialog windows; for other choices it hides the menu. It then sends `GameMsg_RequestNpcSelectMenu`. `GameMode` dispatches to `RequestNpcMenuSelection`, which independently rejects zero NPC ID/choice, fills the packet and sends `sizeof(packet)`. Only after a successful send of choice `0xFF` does the helper clear the current mode's quest/dialog IDs. A send failure does not restore the UI windows/menu.

## Client layout and profile

`PACKET_CZ_NPC_SELECTMENU` serializes opcode `0x00B8` at offset 0 (2 bytes), NPC ID at offset 2 (4 bytes), and choice at offset 6 (1 byte), for seven bytes total. `PacketProfile::LegacyNpcScriptSend::kSelectMenu` resolves to `0x00B8`.

## Selected registry comparison

`PK01.02-server-registry-final.csv` maps opcode `00b8` to fixed length 7 and `clif_parse_NpcSelectMenu`. The client opcode and total length match the selected registry. The server reads NPC ID@2 and choice@6. Under the selected source, `0xFF` is explicitly exempt from the upper-bound check and is accepted; zero is invalid, and any other selection above `sd->npc_menu` triggers an invalid-selection warning and GM kick. An accepted choice is stored in `sd->npc_menu` and resumes `npc_scriptcont`.

`0xFF` is valid as the standard cancel sentinel: the parser exempts it from the upper-bound check, stores it in `sd->npc_menu`, and calls `npc_scriptcont` (`src/map/clif.cpp:13317-13340`). The standard script `menu` builtin recognizes `sd->npc_menu == 0xFF`, clears `menu_or_input`, and sets the script state to `END` (`src/map/script.cpp:5168-5178`). Thus standard menu cancellation ends the active menu script branch rather than selecting a numbered option.

Script continuation requires the target NPC ID to equal the active `sd->npc_id`, rechecks proximity/visibility with `npc_checknear` (apart from the item-script fake NPC), and can silently stop for secure-NPC-timeout, progressbar, missing script state or stale target. The script interpreter then consumes the selected menu value, including 0xFF. There is no generic menu-selection acknowledgement; the next script output is the observable response.

## Remaining evidence and ownership

Replay choices zero, current maximum, maximum+1, 0xFF, wrong/stale NPC ID, timeout/progressbar and send failure. Standard `menu` cancel semantics are source-confirmed; confirm the chosen script path and user-visible recovery when the client closes dialog windows before a failed send. No production replay and no discovery row is closed by this note.

## Client menu-output receive path follow-up

The client frames `0x00B7` as variable-length and routes it to `HandleNpcDialogMenu` (`src/network/GronPacket.cpp:101`, `src/gamemode/GameModePacket.cpp:8881`). The handler reads NPC ID at offset 4, extracts the menu text from offset 8, splits it into visible option labels and corresponding server choice bytes, clears the say-dialog action, hides NPC input, and passes both vectors to `UINpcMenuWnd::SetMenu` (`GameModePacket.cpp:3479-3513`). The menu defaults to the first visible row; `GetSelectedChoice` submits its stored server choice byte when available, falling back to visible index + 1 (`src/ui/UINpcMenuWnd.cpp:327-365`). `SubmitSelection` closes NPC dialog windows for choice 0xFF, otherwise hides the menu, then sends the selected value (`UINpcMenuWnd.cpp:367-380`). This is a server script-output/menu-response path, not a generic request acknowledgement. Runtime label/choice parsing and send-failure UI recovery remain open.

## Menu state when selection send fails (2026-11-05)

`UINpcMenuWnd` rejects zero NPC/choice, then closes all NPC dialog windows for choice `0xFF` or hides the menu for other choices before dispatching the request; it ignores the send result. `RequestNpcMenuSelection` returns the packet-send result and clears `m_isOnQuest`/`m_lastNaid` only when the `0xFF` send succeeds. A failed close therefore leaves those game-mode fields unchanged while the windows have already closed. This is a traced state boundary, not a confirmed defect; PK25 should review failure/retry/reopen semantics alongside the server script continuation.
