# PK45.03 — commerce cart item-list packets

Date: 2026-11-04. Status: client framing, row conversion, and replacement behavior traced; server field schema remains provisional. No rows closed.

`GronPacket.cpp` marks 0x0122, 0x0123, 0x01EF, 0x0297, 0x02D2, and 0x02E9 variable length. They route to `ro::commerce::Receive`. The receiver accepts these list packets only when the length is at least four bytes and the payload after the four-byte header is an exact multiple of the selected row stride: 10 bytes for 0x0123, 18 for 0x01EF, 22 for 0x02E9, 20 for 0x0122, 24 for 0x0297, and 26 for 0x02D2. The latter three are treated as equipment rows.

Each row begins with client item index (u16), item ID (u16), type and identified bytes. Non-equipment rows then carry amount (u16) and location (u16); strides of at least 18 add four slot values, and strides of at least 22 add a four-byte delete time. Equipment rows use amount one, followed by location, damaged byte, refine byte and four slot values; stride 24 or greater adds a four-byte delete time. For the 26-byte equipment stride, the helper consumes only the first 24 bytes; the final two bytes are not read by this conversion. The receiver copies the existing cart map, removes rows whose item-type classification matches the packet's equipment/non-equipment category, parses the incoming rows, and inserts only entries with nonzero index, item ID, and amount. It then replaces `state.cartItems` and sets `state.hasCart`. Thus each accepted list replaces one category while preserving the other, and malformed lengths return before mutation. Duplicate indexes within one packet overwrite earlier rows in the copied map.

The source establishes the client byte offsets and local effects, but does not establish the server's intended field names, location bit meanings, category distinction, delete-time units, or whether duplicate/zero-valued rows have protocol significance. Confirm those against a selected server implementation and representative captures. No independent fixture or production replay was performed for this leaf; no rows are closed.

## Selected server cart-list emitter follow-up (2026-11-04)

The pinned PACKETVER 20080910 tables select `0x02E9` for normal cart rows and `0x02D2` for equipment rows; the older `0x0123`/`0x0122` and intermediate `0x01EF`/`0x0297` values are other profile branches. `clif_cartlist` walks the cart once, classifies each item by server-side stackability, and emits one frame per nonempty category to SELF. It sends no empty category frame. The selected normal record is 22 bytes: index, item ID, type, identified, count, wear-state/equip mask, four slots, and hire-expiration time. The selected equipment record is 26 bytes: index, item ID, type, identified, location, wear state, damaged, refine, four slots, hire expiration, and bind-on-equip type. The client consumes the first 24 equipment bytes and ignores the final bind-on-equip u16. This confirms the two selected profile strides and that separately received normal/equipment frames are category snapshots rather than a single all-cart snapshot.

The client replaces only the matching category while preserving the other category, consistent with the server's omission of empty category packets. Server-side category selection uses `itemdb_isstackable2`, while client replacement classifies by item-type values; equivalence across all item definitions still needs data-backed validation. Duplicate rows, empty-category stale state, delete-time units, and replay remain open. No discovery row is closed.


## Additional client receiver replacement semantics


o::commerce::Receive maps the cart-list opcodes to 10/18/22-byte normal rows or 20/24/26-byte equipment rows, requires a 4-byte packet header and an integral row count, then copies the current cart map and erases only rows matching the incoming category before parsing replacements (src/gamemode/Commerce.cpp:54-58). Rows are inserted only when item index, item ID, and quantity are nonzero; the new map is then committed and hasCart is set. A header-only four-byte category packet therefore clears that category while preserving the other one; malformed partial rows are rejected before the copied map is committed. This documents local parser/update semantics, not whether the selected server actually emits empty category lists or whether 20080910 row field meanings match every accepted client profile. Those emitter/profile questions and replay behavior remain open.


## Equipment and session-inventory boundary

Commerce.cpp::item decodes equipment rows with m_num=1, location u16@6, damaged byte@10, refine byte@11, four u16 slots@12..19, and optional expiry u32@20 when row size is at least 24 (src/gamemode/Commerce.cpp:27-31). A 26-byte equipment row is accepted by the table but the last two bytes are not consumed by this decoder; their meaning is not established here. Normal rows use quantity u16@6, location u16@8, optional slots from offset 10 for rows >=18, and optional expiry u32@18 for rows >=22. The list receiver commits to
o::commerce::state.cartItems; this path does not directly mutate g_session inventory. Cart/inventory transfer consistency therefore depends on separate ack/list packets and ordering, which remains open for replay/source review.
