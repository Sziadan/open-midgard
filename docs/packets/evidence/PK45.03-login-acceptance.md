# PK45.03 — login acceptance

Date: 2026-11-04. Status: variable framing and session fields traced; selected login-profile semantics and handoff remain open. No rows closed.

The size table treats 0x0069 (`AC_ACCEPT_LOGIN`) as variable length and the router maps it to `HandleLoginAccept`. The handler requires at least 39 bytes, then reads auth code u32@4, account ID u32@8, and sex byte@38 into session state. It does not inspect the packet's declared length at @2 or any bytes after offset 38.

Open work: validate declared-length handling and field offsets/widths against the selected login protocol; determine expected sex values and how these fields drive subsequent character-server authentication; replay minimal, extra-payload and malformed-length accepts, checking stale session values and transition behavior. No independent fixture or production replay was performed for this leaf.

## Selected server login-acceptance layout cross-check (2026-11-04)

The selected server's pre-2017 `AC_ACCEPT_LOGIN` definition uses variable `0x0069`: packet ID and length at 0/2, login ID 1 at 4, account ID at 8, login ID 2 at 12, last IP at 16, last-login text[26] at 20, sex at 46, and variable character-server records starting at 47. The login emitter fills both auth IDs/account ID, writes zero for legacy last-IP and an empty last-login string, and fills sex from account state before appending active character-server records and updating packet length.

This conflicts with the inspected client handler trace, which requires only 39 bytes and reads sex at offset 38. The client also appears not to inspect the declared packet length. Treat the client/server pairing or handler offset as a high-priority stronger-review item; resolve using the exact client binary/profile and a captured `0x0069` packet before trusting session sex or character-server handoff. No discovery row is closed.
