### Active legacy exchange

- `0x0066` C2S `CH_SELECT_CHAR`: fixed 3-byte packet (`u16 opcode@0`, `u8 slot@2`). Registered unconditionally in `CharPacketDatabase`; client currently sends it after selecting a character. The server checks for an available map server, verifies the selected account/slot character is present and not scheduled for deletion, checks pending guild-bound item work and ban state, then loads the character. Under PACKETVER < 20100714, an unavailable last-point map falls back to a configured accessible major city. Missing map servers, bad slot/state/load, or invalid map server cause rejection/operational refusal. A successful selection emits `0x0071` then creates a temporary map-auth record.
- `0x006B` S2C `HC_ACCEPT_ENTER`: variable packet, `packetLength` at offset 2. In selected pre-20100413 layout, fixed prefix is opcode 2 + length 2 + `extension[20]` (24 bytes), then packed `CHARACTER_INFO` records. Under selected `PACKETVER_SAK_LEGACY_CHARINFO`, each record is 108 bytes and ends with `int16 CharNum` at offset 104 and `int16 hairColor` at offset 106. The server calculates record bytes using `char_mmo_chars_fromsql`, and sends on authentication via `chclif_mmo_send006b`. No active `total/premium_start/premium_end` bytes exist before PACKETVER 20100413. The current client's same-size target struct instead places `u8 CharNum`, `u8 haircolor`, and `s16 bIsChangedCharName` at offsets 104–107. A raw `memcpy` was therefore semantically wrong for the selected 20080910 source even though the record size matched.
- When the selected server has no characters, `char_mmo_chars_fromsql` appends no records and `chclif_mmo_send006b` emits only the valid 24-byte prefix. PK44.04 separately replays this zero-record path and checks the client's empty-list status/CharSelect transition.
- `0x006C` S2C `HC_REFUSE_ENTER`: fixed 3 bytes (`u16 opcode@0`, `u8 error@2`); `chclif_reject` sends zero-initialized result codes, ordinarily 0 for forged/invalid character selection or server-side rejection. Client displays a generic refusal and disconnects to Login. It is a character-server refusal, distinct from login-server `0x006A`.
- `0x0071` S2C `HC_NOTIFY_ZONESVR`: selected pre-20170315 fixed 28 bytes: opcode `u16@0`, CID `u32@2`, map name `[16]@6`, IP `u32@22`, port `u16@26`. The server writes the chosen character ID, extended map name, selected map-server IP and port. The client parses the fields, strips a map extension, resets local guild/window state, disconnects from char server, and transitions to zone connection. Wire IP/port order follows the source's `htonl`/`ntows(htons(...))` helpers. PK44.04 now has a source-byte fixture through the production handler for CID, map extension, IP, port, state reset and teardown; visible zone transition and the later map connection remain unverified.

The client now converts the selected old server's 108-byte record into the current character-selection structure when the resolved account login date is before 20090225. The conversion preserves common fields and maps the final 16-bit slot/hair-color values to the current 8-bit fields; it supplies the legacy rename-flag default. The same conversion is used by `0x006D` character creation success, whose sender calls the same `char_mmo_char_tobuf`. A separate production-handler replay uses distinct sentinel slot/hair-color values for both responses. Later profile shapes and deployed-server provenance remain unverified; the conversion does not certify the heuristic across other historical profiles. The `0x0069` offset-12 value is preserved as `login_id2`; see `PK44.LOGIN-REPLIES.md`.

## Later and paged variants

- `0x082D` S2C second character-list header has a 29-byte structure (opcode, length, five slot counts, 20-byte extension) and is called only from the `PACKETVER >= 20130000` character-list sender branch. Inactive for selected 20080910 source configuration.
- `0x0840` S2C accessible-map list and `0x0841` C2S selected accessible map are both guarded by `PACKETVER >= 20100714`. The request is 4 bytes (`opcode`, slot, map index); the S2C response is variable (`opcode`, length, repeated `int32 status` + extended map name). The guarded path is inactive for selected configuration. For older versions, unavailable maps use the major-city fallback instead.
- `0x09A0` S2C char-list notification is sent only by the `PACKETVER >= 20130000` branch, after `0x082D` and `0x006B`; inactive at selected date. Its base packed structure is 6 bytes (`opcode`, `u32 total`) with an additional RE-only slots field for a later range.
- `0x09A1` C2S char-list request is registered without a date guard and triggers `0x099D`; handler ignores payload beyond the opcode. `0x099D` is variable (`opcode`, total length, `CHARACTER_INFO` records) and the sender appends an empty final packet when the first page count is exactly three. This server-side request/response path is compiled under selected config, but client sender/reachability is not confirmed. Current client has no `0x09A1` send path or receive-size registration for `0x099D`; neither row is certified supported or inactive.
