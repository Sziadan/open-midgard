## Legacy immediate deletion

The PacketVer23 sender now uses the selected layout and confirms the character before sending. The discrepancy below records the original baseline. [Current implementation and replay](../evidence/PK46.03-character-delete-selected-replay.md)

### C2S `0x01FB` CH_DELETE_CHAR

For `PACKETVER >= 20040419` (including selected 20080910), packed fixed size is 56 bytes: `u16 opcode@0`, `u32 CID@2`, `char key[50]@6`. Older versions use opcode `0x0068` and a 40-byte key. The character server registers the selected symbol/size unconditionally, parses CID and key, checks the configured email/birthdate deletion policy, then calls `char_delete`.

Server `char_delete` result mapping: success emits empty fixed `0x006F`; key mismatch emits `0x0070` result 0; not found emits 1; guild/party restriction emits 2; database, base-level, or deletion-time restriction maps to result 0. The source documents `0x0070` result 0 as wrong email, 1 invalid slot, 2 party/guild restriction. The server's `chclif_delchar_check` accepts exact configured email/birthdate, and also permits empty key when the configured email is the default `a@a.com`.

Selected active current-client profile discrepancy: `PacketVer23LoginChain::kDeleteCharacter` resolves to `PACKETID_CH_DELETE_CHAR=0x0068` (`src/network/Packet.h:18,62`), and `LoginSubMode_DeleteChar` sends `sizeof(PACKET_CH_DELETE_CHAR)` (`src/gamemode/LoginMode.cpp:1868-1873`). The local struct is 46 bytes with `key[40]` (`src/network/Packet.h:318-322,741`), not 56 bytes. The selected server's 20080910 registration is `0x01FB`, 56 bytes with `key[50]`; therefore opcode, packet length, and key width disagree. The server parser copies the selected packet key into a 40-byte email buffer and checks it as the account email (`src/char/char_clif.cpp:1356-1365`).

### S2C `0x006F`/`0x0070`

`0x006F` is fixed 2-byte opcode-only success. It carries no CID, so the client uses its pending-delete state (GID and slot) to remove one matching local character and returns to character selection. `0x0070` is fixed 3 bytes with one-byte error at offset 2; client clears pending state and shows a dialog. Client mappings for codes 0–2 align in broad category with the documented source meaning, but generic failure codes and UI outcomes are not runtime-verified.

## Scheduled deletion / cancellation family

The login-mode transport and framing are implemented and replayed. The character-selection controls remain open. [Current transport evidence](../evidence/PK46.03-scheduled-deletion-wire.md)

These declarations and receive registrations are unconditional in the selected server's `CharPacketDatabase`; client negotiation/reachability is unknown. The selected date is outside `PACKETVER_CHAR_DELETEDATE` (that macro is true only for later ranges), so `0x0828.date` is sent as the absolute deletion timestamp, not remaining seconds.

| Identity | Direction, fixed size, fields | Source behavior |
|---|---|---|
| `0x0827` | C2S 6: opcode `u16@0`, CID `u32@2` | Queue deletion. Rejects unknown CID or DB error with `0x0828` result 3; already queued -> result 0; guild/party policy -> result 4/5; success stores `now + char_del_delay` and returns result 1 plus deletion date. |
| `0x0828` | S2C 14: opcode, CID `u32@2`, result `i32@6`, date `u32@10` | Reservation reply. Source result 0 means already queued; 1 newly queued; 3 DB/not found; 4 guild; 5 party. |
| `0x0829` | C2S 12: opcode, CID `u32@2`, birth date `[6]@6` | Confirm queued deletion after YYMMDD validation, then calls `char_delete`. |
| `0x082A` | S2C 10: opcode, CID, result `i32@6` | Confirmation result: 1 success; 2 restrictions; 3 DB/not found; 4 delay not elapsed; 5 birthdate mismatch; additional documented values include name/email failures. On newer PACKETVER >=20130000, successful confirmation also resends character list before this reply; selected source does not. |
| `0x082B` | C2S 6: opcode, CID | Cancel queued deletion; source updates delete_date to 0 for any found character, without checking that a deletion was queued. |
| `0x082C` | S2C 10: opcode, CID, result `i32@6` | Cancel result 1 success; 2 DB failure or character not found. |

`char_del_delay`, restriction configuration, database state and policy determine whether each branch is reachable. These forms are compiled/registered in the selected source but no client send or receive handling was found in the current runtime; current `GronPacket.cpp` only registers legacy `0x006F/0x0070`. Do not infer compatibility from server registrations alone.
