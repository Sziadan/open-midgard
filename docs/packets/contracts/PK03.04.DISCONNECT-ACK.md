# Contract PK03.04.DISCONNECT-ACK

Status: **APPROVED for implementation (revision 4)** by an independent strong review against the local rAthena source. See the non-blocking implementation notes below. Owner: PK03.04. This contract covers the missing receive/dispatch and pending-action behavior for map-server `0x018B`; it does not certify other packet rows.

## Exact wire contract

1. `0x018B` acknowledgement header: opcode `uint16` at byte 0, little-endian; fixed total size 4.
2. Result: `uint16` at byte 2, little-endian. rAthena's `clif_disconnect_ack` writes the opcode to `WFIFOW(fd,0)` and result to `WFIFOW(fd,2)`.
3. Result `0`: accepted quit/disconnect for request `0x018A`; the server flushes the reply and may close the socket.
4. Result `1`: disconnect refused. The server emits this for a restricted `0x018A` request and for a restricted `0x00B2` type-1 return-to-character request.
5. rAthena does not emit result `0` from the successful `0x00B2` type-1 path: that branch calls `chrif_charselectreq`; refusal calls `clif_disconnect_ack(sd,1)`. Therefore response meaning must be combined with the pending client action.
6. The server comment says results other than `0` and `1` are ignored. The client will likewise log and ignore unknown results without clearing the current pending action; the bounded timeout below is the recovery path.

Server sources:

- `src/char/char_mapif.cpp::chmapif_parse_authok` sends result 0 when the character server is stopping, and result 1 after creating character-select authentication. The map server forwards either result as `00B3`. A pending character-select action clears on result 0, reports refusal in system chat, and remains on the map. Result 1 still owns the transition.

- `src/map/clif.cpp:11427-11462`: `clif_disconnect_ack` and `clif_parse_QuitGame`; server result meanings and allow/deny branches.
- `src/map/clif.cpp:11837-11854`: `clif_parse_Restart`; type 1 is return-to-character, and only its restricted branch emits result 1.
- `src/map/chrif.cpp:775-791`: `chrif_charselectreq` sends the character-select request to the character server on the successful return path.
- `src/map/chrif.cpp:775-781`: `chrif_charselectreq` can return `-1` without sending any acknowledgement when the character-server link is absent or `login_id1` is unavailable.
- `src/map/clif.cpp:842-856` and `src/map/packets.hpp:590-594`: `0x00B3` is `ZC_RESTART_ACK`; rAthena documents type 1 as disconnect-to-character-select and `?` as no action.
- `src/map/chrif.cpp:1774`: the character-server's `0x2b03` reply forwards its `ok` byte to `clif_charselectok`; do not claim that only type 1 can arrive.
- `sizeof(PACKET_ZC_RESTART_ACK)` is 3 from its packed `int16` opcode and `uint8` type fields. The rebuilt client's `GronPacket.cpp:97` also registers `0x00B3` as length 3; rAthena has no map packet registry entry for this server-to-client acknowledgement.

Independent source-derived acknowledgement bytes:

- result 0: `8b 01 00 00`
- result 1: `8b 01 01 00`

The client requests already built by `GameMode.cpp` are `0x00B2` type 1 (`b2 00 01`) and `0x018A` type 0 (`8a 01 00 00`). These expected bytes are literal fixtures derived from packet IDs, field offsets, values, and fixed lengths above, not from client packet structs.

## Approved behavioral contract (revision 4)

Pending actions are `None`, `ReturnToCharSelect`, and `ExitToWindows`. The state is currently file-global in `GameModePacket.cpp`; every map-mode teardown must clear it. Capture the start tick only after the send path accepts a request. A non-`None` action, not a nonzero timestamp, indicates that the timer is active because `GetTickCount()` may be zero. Compute elapsed time with unsigned tick subtraction, `static_cast<DWORD>(nowTick - startTick)`, so tick wraparound is safe. The production timeout helper receives `nowTick` as an explicit parameter; production passes `GetTickCount()` and replay passes deterministic ticks.

- `ReturnToCharSelect` is set before sending `0x00B2` type 1; `ExitToWindows` is set before sending `0x018A` type 0. Failed sends clear pending state, keep the current mode, and report the send failure. A second request while either action is pending is rejected without sending. The chooser closes only after a request send succeeds; failed or duplicate requests leave it open.
- An accepted `0x018A` request waits for `0x018B`. It must not disconnect or quit before result `0` is dispatched. Result `0` with `ExitToWindows` disconnects and quits, matching Ref. Result `1` with either pending action clears the action, remains in the map session, and displays a local English chat event: `The server refused the disconnect request.` The wording intentionally makes no claim about a fixed restriction duration; Ref uses `MSI_CANT_EXIT_NOW` in its red chat channel.
- A `0x018B` result with no pending action is logged and ignored. Result `0` paired with `ReturnToCharSelect` is logged as an unexpected pairing and ignored while retaining the action. This deliberately differs from Ref/dhxj, which handles result 0 by disconnecting and quitting without checking the pending request context; rAthena's successful `0x00B2` type-1 path does not send result 0, so a return-to-character action must not become an exit-to-Windows action. Unknown result values are logged and ignored without clearing the action, matching the server's stated behavior. No unexpected result disconnects, quits, or changes modes.
- Permit at most one request at a time. The protocol has no request ID; a duplicate/late `0x018B` received while no action is pending is ignored, but one arriving after a later request has become pending is indistinguishable from that request's reply. Current server source emits one acknowledgement per request; the client cannot disambiguate a protocol-violating delayed duplicate without changing the protocol. This residual limitation must be documented and tested as far as the available wire context permits.
- A request with no corresponding server response must not leave the UI action pending forever. `CGameMode::OnUpdate` evaluates expiry only after its receive loop has ended because `RecvPacket` returned `false`; exhausting the per-frame packet budget is not a drained queue and must not trigger expiry. Set an explicit receive-drained flag only on the false return, dispatch every returned complete packet, then check `static_cast<DWORD>(nowTick() - startTick) >= 15000`. Perform the check before the map-loading early return; if expiry switches modes, return from `OnUpdate` immediately. On expiry, clear the action, disconnect the map socket, and switch to login mode with the exact status `Login: disconnect timed out.` For `ReturnToCharSelect`, set `g_session.m_pendingReturnToCharSelect` so login mode can attempt character-server selection when available; for `ExitToWindows`, explicitly leave that flag clear and do not quit the process. Consume and clear `m_pendingReturnToCharSelect` on every `CLoginMode::OnInit` path, including when `CanReturnToCharacterSelect()` is false or the subsequent connection fails, to prevent stale retries. Carry the timeout notice through a one-shot pending-login-status string owned by `LoginMode.cpp`, copy it into login-mode state during `OnInit`, and retain it until a stable destination UI is ready. Transient status writes during `ConnectChar` and `PollNetwork` do not consume or replace the notice. In a direct return to the plain login screen, apply the notice after the normal `Login: ready.` or server-selection status is written. On successful automatic character-server selection, replace the `CharSelect` state's normal empty status with the notice and consume it there. If no character-server endpoint is available, retain the existing no-endpoint flow without inventing a connection-failure dialog; if an attempted connection fails, preserve the existing failure dialog. In either fallback path, once the client returns to the plain login screen, apply the notice after the normal login status and consume it. This defines precedence over `Login: ready.`, `Login: select a server before connecting.`, `Login: no char server to connect to.`, `Login: char server connection failed.`, and `PollNetwork` status writes without suppressing the existing connection-failure dialog. This timeout and fallback are client-side recovery policy, not server-protocol values. Closing the socket resets the uncorrelated reply context before another request can be sent.
- A socket EOF or hard receive error before a complete acknowledgement must never cause a quit-to-Windows transition. If no acknowledgement was dispatched, keep the pending action until the same 15-second timeout and then apply the login fallback; EOF alone does not clear the action or bypass the timer. Clear the action on explicit disconnect and map-mode teardown. The buffered-frame drain is owned by PK03.04, with no PK05 dependency: `CRagConnection::RecvPacket` must extract and return any complete frame already in `m_recvQueue` before `FlushSendQueue()` or `recv()` can observe an error and call `Disconnect()`. Preserve the existing unknown-opcode and invalid-variable-length discard behavior and incomplete-trailing-byte behavior.
- The existing `0x00B3` route remains the separate successful return-to-character acknowledgement, not a synonym for `0x018B`. Its documented meaningful value is type 1; it may transition only when `ReturnToCharSelect` is pending and the result is 1. In that case, clear the action, set `g_session.m_pendingReturnToCharSelect`, and use the existing login-mode transition. If no return action is pending (including while `ExitToWindows` is pending), log and ignore the `0x00B3` without clearing another action or changing modes. Log and ignore other type values without clearing pending state, leaving the timeout as recovery; do not claim that rAthena emits no other values.
- On map-mode teardown, clear the file-global pending action and its timer. This is required both for normal mode changes and for unexpected transport/session teardown.

Ref evidence:

- `Ref/dhxj/GameModePacket_2.cpp:912-914` routes `HEADER_ZC_ACK_REQ_DISCONNECT`.
- `Ref/dhxj/GameModePacket.cpp:5746-5761` handles result 0 by disconnecting/quitting and result 1 by sending `MSI_CANT_EXIT_NOW` to the red chat channel. The rebuilt client has no matching resource ID; the English refusal text above is a deliberate user-facing equivalent, not a translation of the original localized resource string.
- In the authoritative rAthena source, `clif_parse_QuitGame` queues result 0, calls `flush_fifo(fd)`, and only then optionally closes the socket (`src/map/clif.cpp:11454-11457`). This source order supports the result-0-before-EOF test, but the deployed server binary's source/version is unknown; do not claim that it matches this checkout. If the deployed server does not deliver the acknowledgement, the client will take the 15-second login fallback instead of quitting Windows.

Non-blocking implementation notes from the approving review:

- Preserve source-hash provenance for `chrif.cpp` in the PK03.04 evidence alongside the contract's pinned hash.

The replay must exercise the same production receive/dispatch loop used by `CGameMode::OnUpdate` (the global router, or a factored helper called by `OnUpdate`), not only a local router. Assert handler effects for the pending-action/result matrix and keep an unrelated registered packet dispatching after concatenation. Outbound mock-peer captures must match the independent `0x00B2` and `0x018A` fixture bytes. Include every split boundary for `0x018B`, coalesced packets where the acknowledgement follows an unrelated complete frame, peer EOF after those frames, request send failure, duplicate request, result `0`/`1`, unexpected pairing/value, no pending action, deterministic clock-controlled 15-second expiry, late replies, `0x00B3` while `ExitToWindows` is pending, and teardown. Verify buffered-frame extraction occurs before flush/receive can observe connection failure, unknown-opcode and invalid-variable-length behavior is unchanged, and incomplete trailing bytes are handled as before. In `OnUpdate`, verify expiry is not run when the per-frame packet budget is exhausted and is run after the receive loop drains, before map-loading early return; verify it returns immediately after a timeout-driven mode switch. Verify EOF/hard error with a pending action and no acknowledgement retains the timer and applies the same timeout fallback. UI assertions must verify both request menu options close only after a successful send, the refusal event is visible without leaving the map session, and timeout returns to login with `Login: disconnect timed out.` without claiming that the server restriction lasts 15 seconds. Verify each status precedence rule, including the successful `CharSelect` status clear and the failure-dialog path.

No discovery row closes merely from adding framing or dispatch registration. No server-runtime or live UI claim is allowed from an offline mock-peer replay. The wire and behavioral decisions above are approved for implementation; PK03.04 remains open until the production dispatch/lifecycle replay and independent completion review pass.
