## Parser behavior and configuration limits

- Raw-password requests copy the fixed input username/password/clienttype, set `passwdenc=0`, optionally MD5 the password when `login_config.use_md5_passwds` is enabled, then call `login_mmo_auth`. Success and rejection emit the separate login response opcodes owned by PK44.03.002.
- MD5 requests convert the 16-byte digest to hexadecimal and set `passwdenc=PASSWORDENC`. If `use_md5_passwds` is enabled, the parser rejects with result 3 and returns false; otherwise it calls `login_mmo_auth`. Exact password-verification policy and secure migration behavior are outside this request-applicability contract.
- SSO copies the token into the login password field (the source comment says this is temporary), optionally applies the configured password MD5, and then calls `login_mmo_auth`.
- `0x0200` is accepted as an ignored keepalive; `0x0204` updates session hash state. Neither parser itself sends a same-opcode reply.
- The Ref client demonstrably sends `0x0064` from its connected login flow and `0x0200` in the non-debug command-account path. It has an `Ac_Ack_Hash` handler which constructs `0x01DD`, `0x01FA`, or `0x027C` by service type, but no `HEADER_CA_REQ_HASH` send call was found to establish the request that reaches that handler. The `0x0204` send is commented out. No active Ref send call was found for `0x0277`, `0x02B0`, or `0x0825`; packet declarations/length entries alone do not prove a live path. Keep those families open and do not infer 2008 client support from the unconditional server registration.
- In the Ref `0x027C` sender branch, `PACKET_CA_LOGIN4 p` is not value-initialized and its declared 13-byte `macData` field is not assigned before the full packet is sent. Whether surrounding build/runtime code initializes it is unproven; treat exact client bytes and any security implications as an open review item.

## Exact unresolved security review

The dynamic 0x0825 path requires a separate security review before client implementation. `PacketDatabase::handle` checks that the input has at least the 92-byte minimum and that `remaining < p->packetLength` is false, but the declared length is signed `int16` and this trace found no explicit lower-bound check `packetLength >= sizeof(PACKET_CA_SSO_LOGIN_REQ)`. The handler computes `size_t token_length = p->packetLength - sizeof(*p)` before copying. A negative/small declared length can therefore reach signed-to-unsigned arithmetic if the database path is entered with a full minimum prefix. This source trace does not prove exploitability or the precise out-of-bounds behavior; do not implement or claim secure SSO framing from this evidence. PK48 should review the minimum-length check, token copy bounds, and malformed-length tests against the production parser before any SSO implementation.
