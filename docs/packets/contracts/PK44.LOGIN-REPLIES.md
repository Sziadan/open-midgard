## Source layouts and behavior

### `0x0069` AC_ACCEPT_LOGIN, S2C login stage

At `src/common/packets.hpp`, the selected pre-20170315 variant is packed. Offsets are little-endian host fields as serialized on this x86 packet protocol:

1. `packetType`: offset 0, 2 bytes, value `0x0069`.
2. `packetLength`: offset 2, 2 bytes, total frame length.
3. `login_id1`: offset 4, 4 bytes.
4. `AID`: offset 8, 4 bytes.
5. `login_id2`: offset 12, 4 bytes.
6. `last_ip`: offset 16, 4 bytes; set to zero as obsolete.
7. `last_login`: offset 20, 26 bytes; set to empty string.
8. `sex`: offset 46, 1 byte.
9. Character-server records start at offset 47, each 32 bytes in this selected layout: IP 4, port 2, name 20, users 2, type 2, new flag 2. Count is derived from packetLength; source increments packetLength by each record size.

`logclif_auth_ok` sends this only after runtime/group checks, a connected character server check, and online-session checks. Rejections at this stage use `0x0081` result 1 (server closed) or result 8 (account still recognized online); otherwise it populates credentials and server list, sends `0x0069`, then creates temporary auth and online records. The 2017+ layout adds a token and 128-byte record extension and uses another opcode; it is outside the selected registration.

The current client parser in `src/gamemode/LoginMode.cpp::OnAcceptLogin` consumes the 47-byte fixed prefix and names the four bytes at offset 12 `m_userLevel`. On character connect it copies that value unchanged into `PACKET_CA_ENTER.UserLevel` at packet offset 10; the selected server reads those same four bytes at offset 10 as `login_id2`. This is a naming mismatch, not a wire-value mismatch. Preserve the bytes; optionally rename the local semantic field when a bounded implementation change is made.

### `0x006A` AC_REFUSE_LOGIN, S2C login stage

Selected packed layout is exactly 23 bytes: opcode `u16` at 0; error `u8` at 2; unblock-time text `[20]` at 3. `logclif_auth_failed` zero-initializes the struct and writes opcode and result. Although it accepts an unblock-time argument, this source snapshot currently copies an empty string into the field, including for result 6. Login-auth results documented by the source include 0 unregistered, 1 bad password, 2 expired, 3 rejected, 4 blocked by GM, 5 outdated executable, 6 blocked until date, 7 jammed, 8 company limit, 9-15 regional/group outcomes, 99 erased, and 100-104 additional account states; other values are unknown. The wrapper logs the corresponding configured message and applies dynamic password-failure IP-ban logging for results 0/1.

Current `OnRefuseLogin` maps codes differently for the initial values: client code 0 says account suspended vs server unregistered; 1 says ID not found vs server incorrect password; 2 says wrong password vs server expired; 3 says already logged in vs server rejected; 4 says not approved vs server blocked by GM. This established code-map mismatch must be resolved before changing user-visible result handling. Client dialog/disconnect returns to login mode. No result branch is certified correct by this contract.

### `0x0081` SC_NOTIFY_BAN, S2C login stage

Packed fixed size 3: opcode `u16` at 0, result `u8` at 2. `logclif_auth_ok` uses result 1 when the server is not running, connection group policy refuses access, or no character server is online; result 8 means a prior session is still recognized. These are operational login rejection branches, distinct from credential errors in `0x006A`. The current client displays a generic disconnect dialog with the numeric result and disconnects.

### `0x01DC` AC_ACK_HASH, S2C login stage

Packed variable packet: opcode `u16` at 0, total packet length `u16` at 2, salt bytes from offset 4. `login_session_data::md5key` has capacity 20; `logclif_parse_reqkey` sets `md5keylen` to that capacity, generates salt, and `logclif_reqkey_result` sets total length to `sizeof(header)+md5keylen` and copies those salt bytes. The selected sender therefore emits 24 bytes, including all 20 salt bytes. The 2-byte `0x01DB` C2S request parser and subsequent hash request are documented in `PK44.LOGIN-REQUESTS.md`.

Current `OnAckHash` accepts payload lengths from the declared length when it falls between 4 and received size, otherwise falls back to all received bytes after the header, then sends the configured hash-login request. Exact compatibility with the server's 20-byte salt and the `g_passwordEncrypt2` concatenation order is not certified here.

## Client handling and limits

Current dispatch routes these opcodes to `OnAcceptLogin`, `OnRefuseLogin`, `OnDisconnectMsg`, and `OnAckHash`. For 0x0069 the client selects the first server automatically and transitions to ConnectChar; for failures it resets the account-login handshake and returns to Login; 0x01DC triggers hash-login construction. This is a code-path inventory, not a production replay or UX acceptance.

No independent Ref send/receive evidence is asserted in this contract. The maintained Ref tree has no obvious source-level handling for these legacy login packets in searched locations; proprietary/client binary behavior and deployed-server provenance remain unresolved. Coverage classifications remain UNREVIEWED. PK48 should independently verify the `0x006A` code mapping and validate the 01DC path before implementation decisions. These issues do not block the independent next-step raw account-ID handshake trace.
