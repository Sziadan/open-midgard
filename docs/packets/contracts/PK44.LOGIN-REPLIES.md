## Source layouts and behavior

### `0x0069` AC_ACCEPT_LOGIN, S2C login stage

At `src/common/packets.hpp`, the selected pre-20170315 variant is packed. Offsets are little-endian host fields as serialized on this x86 packet protocol:

1. `packetType`: offset 0, 2 bytes, value `0x0069`.
2. `packetLength`: offset 2, 2 bytes, total frame length.
3. `login_id1`: offset 4, 4 bytes.
4. `AID`: offset 8, 4 bytes.
5. `login_id2`: offset 12, 4 bytes.
6. `last_ip`: offset 16, 4 bytes; set to zero as obsolete.
7. `last_login`: offset 20, 26 bytes; set to empty string.
8. `sex`: offset 46, 1 byte.
9. Character-server records start at offset 47, each 32 bytes in this selected layout: IP 4, port 2, name 20, users 2, type 2, new flag 2. Count is derived from packetLength; source increments packetLength by each record size.

`logclif_auth_ok` sends this only after runtime/group checks, a connected character server check, and online-session checks. Rejections at this stage use `0x0081` result 1 (server closed) or result 8 (account still recognized online); otherwise it populates credentials and server list, sends `0x0069`, then creates temporary auth and online records. The 2017+ layout adds a token and 128-byte record extension and uses another opcode; it is outside the selected registration.

PK44.04's current-client replay now covers two consecutive 32-byte server records in the variable response. `OnAcceptLogin` retains both parsed endpoints, auto-selects index 0, and transitions to ConnectChar. The synthetic second endpoint verifies array/count handling only; the subsequent socket connection and visible server chooser are not exercised. Evidence: `evidence/PK44.04-login-accept-reply.md` and `.jsonl`.

The handler now validates that the declared frame length equals the received frame length, includes the full 47-byte prefix, and has a record-array remainder divisible by the selected 32-byte `SERVER_ADDR` size. An 80-byte frame with one complete record and one trailing byte is rejected before credentials are overwritten; server-list state is cleared, the account handshake is reset, and Login status is restored. This is malformed-input boundary coverage, not a claim that the selected server emits partial records. The same evidence file records the production-framing replay.

The client stores at most 100 server records. The prior parser silently truncated larger integral arrays; it now rejects 101 records with a clear login error, clears the list, resets handshake state, and preserves accepted session credentials. This establishes the client storage bound, not a selected-server protocol maximum. The production-framed fixture is recorded alongside the partial-record case in `evidence/PK44.04-login-accept-reply.jsonl`.

The current client parser in `src/gamemode/LoginMode.cpp::OnAcceptLogin` consumes the 47-byte fixed prefix and names the four bytes at offset 12 `m_userLevel`. On character connect it copies that value unchanged into `PACKET_CA_ENTER.UserLevel` at packet offset 10; the selected server reads those same four bytes at offset 10 as `login_id2`. This is a naming mismatch, not a wire-value mismatch. Preserve the bytes; optionally rename the local semantic field when a bounded implementation change is made.

### `0x006A` AC_REFUSE_LOGIN, S2C login stage

Selected packed layout is exactly 23 bytes: opcode `u16` at 0; error `u8` at 2; unblock-time text `[20]` at 3. `logclif_auth_failed` zero-initializes the struct and writes opcode and result. Although it accepts an unblock-time argument, this source snapshot currently copies an empty string into the field, including for result 6. Login-auth results documented by the source include 0 unregistered, 1 bad password, 2 expired, 3 rejected, 4 blocked by GM, 5 outdated executable, 6 blocked until date, 7 jammed, 8 company limit, 9-15 regional/group outcomes, 99 erased, and 100-104 additional account states; other values are unknown. The wrapper logs the corresponding configured message and applies dynamic password-failure IP-ban logging for results 0/1.

Before PK44.04, `OnRefuseLogin` mapped the initial values incorrectly: code 0 said account suspended, 1 said ID not found, 2 said wrong password, 3 said already logged in, and 4 said not approved. PK44.04 now displays source-derived messages for codes 0–15 and 99–104. Meanings for 0–8 and 99–104 follow selected `loginclif.cpp`; 9–15 use named MSI refusal results and the default labels in `conf/msg_conf/login_msg.conf`. The production handler uses `FormatLoginRefusalMessage`; replay checks its output for 23-byte selected-layout packets with each result at byte offset 2, and invokes the full handler for code 1 to verify status, handshake reset, Login transition, and connection close. Code 5's client-version message and code 6's block-date/fallback handling remain unchanged; codes 16–98 and 105–255 preserve their numeric result because no refusal meaning is assigned to those values in the selected source. Custom server message configuration may differ from the repository default. Visible modal rendering remains unverified. The correction does not alter discovery classification.

### `0x0081` SC_NOTIFY_BAN, S2C login stage

Packed fixed size 3: opcode `u16` at 0, result `u8` at 2. `logclif_auth_ok` uses result 1 when the server is not running, connection group policy refuses access, or no character server is online; result 8 means a prior session is still recognized. These are operational login rejection branches, distinct from credential errors in `0x006A`. `OnDisconnectMsg` now uses `FormatLoginDisconnectMessage`; the production-handler replay checks the two result values emitted by the selected source, login status, handshake reset, stable Login transition, and connection close. The source comment also documents result 2, but no call site emits it in this source snapshot, so it retains numeric fallback pending a sender trace. Visible modal rendering remains unverified because the replay uses the headless application stub.

### `0x01DC` AC_ACK_HASH, S2C login stage

Packed variable packet: opcode `u16` at 0, total packet length `u16` at 2, salt bytes from offset 4. `login_session_data::md5key` has capacity 20; `logclif_parse_reqkey` sets `md5keylen` to that capacity, generates salt, and `logclif_reqkey_result` sets total length to `sizeof(header)+md5keylen` and copies those salt bytes. The selected sender therefore emits 24 bytes, including all 20 salt bytes. The 2-byte `0x01DB` C2S request parser and subsequent hash request are documented in `PK44.LOGIN-REQUESTS.md`.

Current `SendPasswordHashRequest` emits the two-byte `0x01DB` request when the `ShouldRequestPasswordHashOnConnect` gate permits it. The production replay captures those bytes, then feeds a 24-byte `0x01DC` fixture with a 20-byte salt through `OnAckHash` and captures the resulting 47-byte request for both `g_passwordEncrypt2` values. The digest orders match Ref `Ac_Ack_Hash`: salt+password when the flag is 0, password+salt when it is 1. Production `CRagConnection::RecvPacket` frames variable packets using the declared length and rejects lengths below four bytes, so the handler's received packet length follows that frame. The replay directly invokes the sender helper and handler; it does not establish that the deployed 2008 profile passes the `passwordencrypt` request gate or which `<passwordencrypt2>` option its external clientinfo uses. No applicable clientinfo XML or Ref request send site was found.

For discovery classification, `AUDIT-0x01DC` is applicable and fully implemented/verified against the selected source and current client: the exact 24-byte S2C frame is dispatched, both salt/password digest branches match independent expected values, and the generated `0x01DD` request bytes are captured. Whether a deployed profile enables this negotiation is a separate reachability/configuration question and does not change this response's verified behavior. PK48 review remains pending and separate.

## Client handling and limits

Current dispatch routes these opcodes to `OnAcceptLogin`, `OnRefuseLogin`, `OnDisconnectMsg`, and `OnAckHash`. For 0x0069 the client selects the first server automatically and transitions to ConnectChar; for failures it resets the account-login handshake and returns to Login. PK44.04 invokes `OnAcceptLogin` directly with an independent 79-byte fixture and checks the prefix values, sex normalization, server record, handshake reset, status, and transition. It does not exercise production framing/routing, the subsequent socket connect, or visible UI acceptance. PK44.04 also replays the `OnAckHash` helper through outbound capture for a synthetic `0x01DC` packet but does not prove live `0x01DB` negotiation.

No independent Ref send/receive evidence is asserted in this contract. The maintained Ref tree has no obvious source-level handling for these legacy login packets in searched locations; proprietary/client binary behavior and deployed-server provenance remain unresolved. Coverage classifications remain UNREVIEWED. PK48 may independently review the `0x006A` result correction and should assess the 0x01DC path; review is a later checkpoint, not an implementation gate. These issues do not block the independent raw account-ID handshake trace.
