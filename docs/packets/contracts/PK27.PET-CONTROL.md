Status: partial implementation; PK27 and PK09.21 remain open. [Request evidence and continuation](../evidence/PK27-pet-control-requests.md) records the current senders. Existing [selected pet-status contract](PK07.PET-STATUS.md) remains authoritative for the35-byte 01A2 profile.

## Source and selected server

Source `CGameMode::SendMsg`5833A0 message158 builds CZ_RENAME_PET01A5/26 bytes: opcode followed by24 raw name bytes. A source name of24 or more bytes is copied then field byte23 is overwritten with NUL. Shorter names include their NUL; remaining source stack bytes are undefined. The port defines those bytes as zero. No charset conversion, UTF-8 repair, name validation or optimistic state mutation belongs to this sender. Null source pointer is outside defined source behavior and is rejected in the port.

Message163 builds CZ_COMMAND_PET01A1/3 bytes, with the low byte of its argument at offset2. It does not clamp or reject unknown action values. Source callers own confirmation, local state and window lifetime. Failed immediate sends report failure without changing caller state.

Pinned server `clif_packetdb.hpp`190/192 and `clif.cpp`14712/14768 agree with these lengths and offsets. Hashes of the current local `clif.cpp` and `pet.cpp` match the selected baseline. `pet_menu`1422 requires an extant pet with nonzero pet ID, positive intimacy and non-incubated state. Actions0/1/2/3/4 request status/feed/performance/return egg/unequip accessory. `pet_change_name`1460 requires pet data and respects the rename flag unless the server override allows another rename, rejects control bytes/DEL, then forwards to inter-server rename. These are server decisions; the request sender must not duplicate or guess them. This source inspection is not a live server test.

## Required caller and owner integration

Command-window value74 is the sentinel10000 Alt+J path: if the basic owner exists, delete actual pet-info88 or create it if absent; return1 even without a basic owner. It sends no request0. Source factory88 requires `m_petJob != -1`, then creates280x160/restores `PetInfoWndInfo`. A previously received valid status snapshot is insufficient proof of current pet presence.

The source pet-info menu inserts Feeding, Performance, Accessory Off, Return Egg in that order. Its message39 indices0/1/2/3 send mode163 arguments1/2/4/3. Feed requires confirmation121. Return Egg also clears the matching inventory egg's damaged flag, sets egg index/job to-1, invalidates inventory and deletes the actual pet-info owner. These caller actions occur independently of immediate send success in the source; do not move them into the generic sender or silently add rollback semantics.

Rename button118 checks fewer than24 source bytes, confirms the once-only notice, sends158, then marks the local name modified, updates the raw name and hides the edit/button. Source default/cancel117 are inert. Preserve safe text copying in place of the decompiled format-string vulnerability. Actual edit/menu/modal input, native/passive Qt views and source position/close/capture behavior still need implementation and validation.

The other pet callers in `Ref/GameMode2.cpp`3842–3880 are inside mode-message26's `m_menuIdList` switch. Menu IDs29..33 are not TALKTYPE29..33, which are emotions. Menu33 sends action0 before toggling the pet owner. Keep this distinction when wiring actual menus.

Pet job/actor identity is acquired through01A4/11-byte source status changes and actor lookup; egg index is acquired from the selected identified/damaged pet-egg inventory path. Current `ro::pet::Status` models the35-byte01A2 snapshot only. It has no job/GID/egg ownership or full reset/lifetime synchronization; creating factory88 from `Status::valid` would invent a different contract.
