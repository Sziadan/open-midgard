# PK09.ITEM-NAME-CONTEXT — ordinary item names and quantity consumers

Owner PK09, bounded implementation leaf PK09.07. Selected profile 20080910. Status IMPLEMENTED_PENDING_REVIEW after the linked checkpoint validation; independent PK48 remains open.

Primary `Ref/ItemInfo.cpp::ITEM_INFO::GetItemName` (2132–2427) uses the unidentified display name directly for unidentified items. Identified ordinary equipment-like types 4/5/8/9/11–15/19 compose refinement and card affixes; other ordinary types use plain identified names. The primary functions `GetIdDisplayName`/`GetUnidDisplayName` copy metadata names without computing a socket-count suffix. `GetSocketNumber` is separate (3774–3839), explicitly called by particular list consumers, such as the sale-list construction at `Ref/UIItemWnd.cpp:5916–5960`.

The inventory help path at `Ref/UIItemWnd.cpp:11460–11464` calls `GetItemName`, then formats quantity with `MSI_EA2`; it does not append `GetSocketNumber`. Thus a source-derived Knife with three sockets and refinement seven has ordinary identified hover `+7 Knife: 1 ea`, while the unidentified item has `Dagger: 1 ea`. Socket metadata remains available to list contexts. Quantities come from the received item rows, independently of slot counts and cart status counters.

The shared name helper now distinguishes list labels and hover composition. Optional socket-suffix arguments preserve existing list behavior while shared item hovers request the raw metadata name. Qt commerce row names use the shared identified/type predicate; they no longer unconditionally compose refinement/card fields for unidentified items. Type 19 joins the primary source's composition type set.
