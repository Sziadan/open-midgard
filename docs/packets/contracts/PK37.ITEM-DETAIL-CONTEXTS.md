## Resolution and ownership

Resolve the context the UI actually rendered:

- Inventory and cart use their respective item-index owners and retain PK33.05 live detail binding.
- Vending uses the matching nonempty draft/own-listing offer, rather than a coincident cart item.
- Seller shop uses its own matching nonempty offer.
- Local trade uses its local offered item index. Remote trade uses the rendered offer ordinal, because two remote rows can both have default index zero.
- Viewed equipment uses the remote snapshot's own item index.

Offer/remote descriptions are copied snapshots. Clearing the originating source or removing a same-index local item must not retarget or invalidate that copied detail. Do not turn remote indices or row ordinals into local inventory lookups. Transaction contexts must still be visible/active when resolving a callback. Unknown sources, absent rows, nonpositive offer amounts, invalid remote ordinals and missing/mismatched expected item IDs open nothing; an invalid callback does not erase an already displayed snapshot. The expected ID guards queued callbacks after a different-ID row replacement, not arbitrary transaction-generation identity.

Actual Qt merchant, trade and viewed-equipment icons now expose the primary right-click detail entry. This is a separate action from buying, offering, dragging or committing a transaction. The tooltip alone uses the root overlay layer; hovering an item must not lift every commerce panel over a detail window. PK33.05 popup scale and scrolling remain in force. Commerce preferred coordinates are converted from root pixels to native logical coordinates; stored placement/window creation policy is separate and not accepted by this leaf.

## Limits

The UI regression injects literal selected-format snapshots through production framing/router/receive handlers. A local offer and index collisions also use explicitly synthetic state fixtures. This does not certify all transaction requests, inventory rollback, trade/vending state machines, permissions or historical profiles. It does not close all PK09.04 detail acceptance. In particular, MakeWindow currently shows a newly created detail before SetItemInfo checks whether preferred placement applies; the broader placement policy needs a distinct review. Locale/art and deployed provenance remain unverified. No discovery classification is closed from this context leaf.
