# PK32.LEGACY-MAIL-STATE — selected records and transaction decisions

Strong source/design review, 2026-11-05. Selected 20080910 uses legacy mail, not RODEX. MAIL_MAX_INBOX=30, TITLE=40, BODY=200 (199 text bytes plus NUL), MAX_ITEM=1. There is no selected network pagination; paginate the complete inbox locally if useful. A compose window and pending send state already exist in Commerce; extend them without replacing unrelated commerce behavior. ## Wire records

All integers below are little endian. Validate the complete record before atomic state mutation; use bounded protocol text decoding, not an assumed UTF-8 string or unbounded C string.

- 0x0240 list: u16 length@2, u32 count@4; exactly 8+73*count, count<=30. Each row: u32 ID@0, title[40]@4, read u8@44 (`status != MAIL_UNREAD`), sender[24]@45, epoch-seconds u32@69. Fixed title may fill all 40 bytes.
- 0x0242 read: u16 length@2, u32 ID@4, title[40]@8, sender[24]@48, reserved u32@72, zeny u32@76, amount u32@80, itemID u16@84, itemtype u16@86, identified/damaged/refine u8@88/89/90, cards four u16@91/93/95/97, body length u8@99, body@100 plus trailing NUL. Total **101+body length**, body length<=199. No-item bytes 80..98 are zero. Empty server body becomes `(no message)`. Consume only the defined 40/24 name bytes even though the server's string-copy capacity overlaps the next field before overwriting it.
- 0x024A notification: 70 bytes, ID u32@2, title[40]@6, sender[24]@46. ID zero is a real unread-refresh signal sent after reading mail; do not insert inbox entry zero or reject it as a globally invalid mail ID.
- 0x0255 stage attachment ack: 5 bytes, inventory index u16@2, result u8@4 (0 success, 1 failure).
- 0x0245 claim ack: 3 bytes, result u8@2 (0 success, 1 failure, 2 capacity). It has **no mail ID and no component discriminator**.
- 0x0249 send ack: 3 bytes, result byte@2. The selected sender collapses every non-success to 1; do not invent a precise recipient-error meaning.
- 0x0257 delete / 0x0274 return ack: 8 bytes, ID u32@2, result/fail u16@6 (0 success). A missing-ID **read** also receives 0x0274 failure, so request context matters.
- 0x0260 mail window: 6 bytes, type u32@2 (0 open, 1 close).

Legacy requests include 0x023F refresh (2 bytes), 0x0241 read (ID u32@2, 6 bytes), 0x0244 claim (ID u32@2, 6 bytes). Source handlers also enforce town/service eligibility; an unavailable service can leave a request unanswered. Do not invent a guaranteed reply for every request.

## Transaction decisions

Maintain a session-generation-scoped inbox keyed by ID, read-detail cache, selection, and explicit pending operations containing the requested ID. Selection changes must never retarget a pending transaction. Serialize ambiguous claims; do not overlap a return with a read if a 0x0274 failure would become ambiguous. Reset pending state on real session/world departure according to the existing session lifecycle, not on a harmless UI redraw. A timeout means uncertain outcome and requires reconciliation, not an automatic duplicate transfer.

One successful claim can produce **two identical 0x0245 success packets**: `mail_getattachment` calls `clif_mail_getattachment` once for item delivery and separately for zeny delivery. Inventory and zeny arrive through their authoritative updates before each corresponding acknowledgement. Never credit resources from 0x0245 or assume the first success settles every component. Retain the original claim ID through the bounded response sequence, tolerate the second acknowledgement, and reconcile the attachment display from a subsequent read of that ID. Gate the next transfer until reconciliation; do not derive it from whichever mail is currently selected. Failure/partial delivery must retain an uncertain/dirty state until readback, without guessing consumed components from the ack byte alone.

The readback is a UI reconciliation of server inbox state, not proof that every asynchronous delivery has completed. A refreshed inbox/read may already show attachments reserved while delivery is pending. Keep actual inventory/zeny authoritative and handle late acknowledgements without applying them to a new claim. Add a conservative pending-transfer phase for unresolved deliveries; if the implementation cannot determine a safe boundary from the outstanding request's expected item/zeny outcomes, keep transfers disabled and expose refresh/reopen rather than guessing.

Reading an unread message can emit 0x0242, refreshed 0x0240, then 0x024A ID-zero. Refresh can request the char service asynchronously. **Refresh clears staged compose item/zeny** (`clif_parse_Mail_refreshinbox` calls mail removal helpers). Coordinate refresh/read/claim reconciliation with the existing composer: prevent or explicitly resolve staged composition before a request that triggers refresh; never background-refresh a staged send silently. Send ack must resolve the existing pending send once; do not duplicate escrow or add inventory optimistically.

## Required acceptance and split

First implement a bounded list/read/notification model and production decoding, then compose/claim/delete/return pending-operation coordination, then wire the actual inbox UI. Preserve other mail work-item ownership; this contract does not complete all 18 related identities. Cover 0/1/30 rows; full-length title; malformed counts/truncation/NUL/body lengths; read-before-list and refreshed list after read; ID-zero notification; missing-read 0x0274; selection changes; two-success claim and partial delivery; late ack after session exit; service refusal/timeout; refresh with staged composition; and authoritative inventory/zeny updates. Fixture parsing alone does not certify escrow, rendered UI or actual production routing.
