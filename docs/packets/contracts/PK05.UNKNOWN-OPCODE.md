# Contract PK05.UNKNOWN-OPCODE — unknown and malformed receive boundaries

Status: **SOURCE_BACKED_BASELINE; RECOVERY POLICY OPEN**. Owner: PK05.01. Complexity: S (describes risk; no model assignment or prior approval gate). PK48 review: pending.

## Identity and scope

This is a transport receive contract spanning framed login, character, and map traffic after any stage-specific raw prefix has been consumed. It covers only the generic client receive table's unknown opcode and invalid variable-length header branches. Known fixed/variable packet layouts and their handlers remain owned by their feature contracts. The selected client profile is packet profile 23; profile 22 is a separately compiled table. PK04 owns the raw character-server AID prefix and must complete before this generic framed state applies.

## Observed client baseline

In `src/network/Connection.cpp::CRagConnection::RecvPacket` (current source around lines 512–595):

- The first two queued bytes are interpreted as a little-endian opcode and looked up with `ro::net::GetPacketSize`.
- A size-table result of zero is treated as unknown: the client logs, removes exactly two bytes, then rescans the remaining stream from the next byte pair.
- For `kVariablePacketSize`, the client waits for four bytes, reads the little-endian length at offsets 2–3, and accepts lengths 4 through `0x7FFF` inclusive. A length outside that range logs, removes exactly two bytes, and rescans.
- For recognized fixed packets and valid variable packets, incomplete data remains queued; a complete packet is popped exactly at its declared/table length.
- The receive pump drains queued frames before socket I/O. Socket EOF disconnects and clears the receive queue; ordinary disconnect/reconnect state is covered by PK03.02.

These are observations, not approved recovery behavior. Two-byte rescan can reinterpret payload or a malformed header as a new opcode; the resulting accidental frame can be delivered to normal dispatch. The stream contains no general marker that can establish the next boundary after an unknown or invalid-length frame.

## Authority and unresolved decision

The selected rAthena snapshot is configured for `PACKETVER=20080910`, but its packet registry describes recognized packet lengths and handlers, not a client-side recovery rule for unknown bytes. TCP preserves byte order, not application packet boundaries. No server-side evidence found so far authorizes scanning payload for a plausible opcode or supplies a universal length for unknown IDs. Therefore PK05.01 records the baseline and constraints without claiming a server-mandated recovery policy. The safe implementation decision and user-visible error/cleanup behavior remain explicit PK05.02/03 work; until resolved, do not silently classify unknown bytes as ignored or feature-complete.

## Implementation constraints and acceptance boundary

- Preserve exact stream alignment for recognized valid concatenated frames and every fragmentation boundary.
- Never scan unknown payload bytes for a plausible opcode or fabricate a length from payload values.
- Distinguish a recognized packet whose handler is absent from an unknown table entry; handler gaps remain feature work.
- Define unknown-opcode, malformed variable-length, truncated-frame, EOF, and reconnect behavior separately and test the production receive path.
- PK05.02 owns the framing decision and byte/buffer transition. PK05.03 owns explicit error propagation, connection cleanup, and reporting. No packet discovery rows close from this transport contract alone.
