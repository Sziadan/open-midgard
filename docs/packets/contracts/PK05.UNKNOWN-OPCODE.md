# Contract PK05.UNKNOWN-OPCODE — unknown and malformed receive boundaries

Status: **IMPLEMENTED_PENDING_PK48_REVIEW**. Owner: PK05.01–PK05.04. Complexity: S (describes risk; no model assignment or prior approval gate). PK48 review: pending.

## Identity and scope

This is a transport receive contract spanning framed login, character, and map traffic after any stage-specific raw prefix has been consumed. It covers only the generic client receive table's unknown opcode and invalid variable-length header branches. Known fixed/variable packet layouts and their handlers remain owned by their feature contracts. The selected client profile is packet profile 23; profile 22 is a separately compiled table. PK04 owns the raw character-server AID prefix and must complete before this generic framed state applies.

## Observed client baseline

In `src/network/Connection.cpp::CRagConnection::RecvPacket` (current source around lines 512–595):

- The first two queued bytes are interpreted as a little-endian opcode and looked up with `ro::net::GetPacketSize`.
- A size-table result of zero was treated as unknown in the baseline; PK05.02 now logs and disconnects without rescanning.
- For `kVariablePacketSize`, the client waits for four bytes and reads the little-endian length at offsets 2–3. Lengths 4 through `0x7FFF` are accepted; a length outside that range logs and disconnects without rescanning.
- For recognized fixed packets and valid variable packets, incomplete data remains queued; a complete packet is popped exactly at its declared/table length.
- The receive pump drains queued frames before socket I/O. Socket EOF disconnects and clears the receive queue; ordinary disconnect/reconnect state is covered by PK03.02.

The previous two-byte rescan could reinterpret payload or a malformed header as a new opcode; the resulting accidental frame could be delivered to normal dispatch. The stream contains no general marker that can establish the next boundary after an unknown or invalid-length frame.

## Authority and unresolved decision

The selected rAthena snapshot is configured for `PACKETVER=20080910`, but its packet registry describes recognized packet lengths and handlers, not a client-side recovery rule for unknown bytes. TCP preserves byte order, not application packet boundaries. No server-side evidence authorizes scanning payload for a plausible opcode or supplies a universal length for unknown IDs. The bounded policy implemented in PK05.02 is therefore fail-closed: an opcode absent from the active profile table, or an invalid length on a table-known variable packet, closes the transport and clears its queues rather than guessing a boundary. This is a conservative client policy derived from the inability to establish a safe next boundary; it is not presented as a server-mandated response. PK05.03 exposes the receive error and routes it to explicit LoginMode status text.

## Implementation constraints and acceptance boundary

- Preserve exact stream alignment for recognized valid concatenated frames and every fragmentation boundary.
- Never scan unknown payload bytes for a plausible opcode or fabricate a length from payload values.
- Distinguish a recognized packet whose handler is absent from an unknown table entry; handler gaps remain feature work.
- Define unknown-opcode, malformed variable-length, truncated-frame, EOF, and reconnect behavior separately and test the production receive path.
- PK05.02 owns the framing decision and byte/buffer transition, including the existing `Disconnect` queue clear. PK05.03 owns typed error propagation and explicit reporting semantics. No packet discovery rows close from this transport contract alone.
- Production replay: `docs/packets/evidence/PK05.02-replay.jsonl` covers coalesced and fragmented invalid boundaries followed by a valid frame; every case asserts no packet delivery, closed connection, and an empty receive queue.
- PK05.03 exposes `CRagConnection::ReceiveError::{UnknownOpcode,InvalidVariableLength}` and preserves the reason through close for LoginMode's disconnect status; `OnConnect` resets it. Transport enum/reset behavior is replayed in `docs/packets/evidence/PK05.03-protocol-error-replay.jsonl`. Visible modal rendering and the full `CLoginMode::OnUpdate` lifecycle remain outside the replay harness.
