# Contract PK01.P02.FRAMING — receive framing state machine

Status: **APPROVED_FOR_APPLICABILITY_BOUNDARY_ONLY**. Owner: PK05. Strong reviewer: `/root/pk01_p0_review`; approval checkpoint subject: `packet(PK01.03): approve P0 applicability identities`.

## Identity and boundary

This is a cross-stage connection receive-state contract, not an opcode contract. It covers stage/profile selection, handoff from the raw P01 character prefix, header and variable-length accumulation, exact frame extraction, unknown or malformed boundary failure, EOF/truncated-frame handling, and disconnect/reconnect reset. Packet-specific decoding, state mutations, and UI remain in their own contracts. It does not create a fictitious packet identity for an unknown opcode.

## Source-backed client behavior

`src/network/Connection.cpp::CRagConnection::RecvPacket` uses a global packet-size lookup (around line 484). Unknown opcodes remove two bytes and continue (around lines 533–538); invalid variable lengths do the same (around lines 550–553). Valid incomplete fixed packets and incomplete variable headers/bodies are retained. Variable lengths currently accept 4–32767. The receive method pumps the socket before draining buffered frames; EOF disconnect clears queued bytes. `RecvPacket(char*)` has no capacity parameter. These are facts to address, not approved recovery semantics.

## Remaining implementation gates

The PK05 implementation contract must specify state ownership and error policy, exact socket/buffer transitions, reset semantics, and tests across fragmentation, concatenation, unknown IDs, malformed variable length, truncation, EOF and reconnect. Complexity labels do not set a required model or pre-approval gate; independent review is deferred to PK48. Packet decoders tested with already-complete frames do not close this cross-cutting contract.
