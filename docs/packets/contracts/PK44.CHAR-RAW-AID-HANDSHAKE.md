# Contract: PK44.CHAR-RAW-AID-HANDSHAKE

Status: SOURCE_BACKED (research only; no discovery row closed). Owner step: PK44.03.003. This is a non-opcode handshake sub-contract linked to primary discovery owner PK04 and applicability contract `PK01.P01.HANDSHAKE`; it does not replace or complete PK04 implementation evidence. Independent review is deferred to PK48.

## Server exchange

The source snapshot and effective config are the PK01.02 hash-pinned local rAthena source (`PACKETVER=20080910`, `PACKETVER_SAK_NUM=20080910`; no Git metadata, deployed provenance unknown).

On a fresh character-server connection, the client sends the 17-byte `CA_ENTER` / `0x0065` request: opcode `u16` at offset 0, account ID `u32` at 2, login ID 1 `u32` at 6, login ID 2 `u32` at 10, unused `u16` at 14, sex `u8` at 16. The server's `chclif_parse_reqtoconnect` waits until 17 bytes are present, consumes them, initializes the session, then unconditionally writes the 4-byte account ID back at offset 0 (little-endian server wire representation) before checking whether the server is running or validating the auth tuple. The echo therefore precedes either successful character-list output or the rejection response. It is raw bytes, not a framed packet and has no opcode.

The server does not validate the account ID's numeric value before echoing it. Authentication then compares account ID and both login IDs against the auth node; on failure it asks the login server to authenticate or rejects if that connection is unavailable. An already-authenticated session's repeat request is discarded after the initial 4-byte echo.

## Client receive behavior and gap

Current `CRagConnection::RecvPacket(std::vector<u8>&)` always interprets the first two bytes as an opcode and consults the packet-size table. `GronPacket.cpp` marks fake IDs `0x8482` and `0x8483` as four-byte packets; `LoginMode::PollNetwork` silently ignores those IDs. There is no raw account-ID comparison or stateful prefix consumer in the inspected receive path. Thus only account IDs whose first two little-endian bytes happen to equal those fake IDs are consumed as a four-byte item; for other account IDs the generic path treats the raw prefix as an unknown packet header and drops two bytes, corrupting stream alignment. Even the fake-ID branch ignores the returned account value rather than comparing it to the account ID sent.

This is a concrete client protocol gap. The later ordinary packet stream cannot safely be interpreted until exactly four raw bytes have been consumed and checked against the expected account ID. Implementing that behavior requires a connection-stage receive state that handles arbitrary fragmentation, the raw prefix plus coalesced following packet bytes, mismatch, EOF, reconnect, and transition to framed parsing. Those implementation/replay requirements remain owned by PK04; this step only establishes the source identity and interaction with the current client pipeline.
