Owner step: PK44.03.008. This is source-config applicability only; no runtime implementation or deployed-server parity is claimed. Independent review is deferred to PK48.

## Applicability proof

Authoritative source is the PK01.02 hash-pinned local rAthena snapshot (`C:/Users/sziad/source/repos/rathena-master`), effective `PACKETVER=20080910` / `PACKETVER_SAK_NUM=20080910`, no RE/ZERO profile. `src/config/packets.hpp` defines `PACKETVER_SUPPORTS_PINCODE` as `PACKETVER >= 20110309`. The selected date therefore sets it false. The server's PIN handlers, their `CharPacketDatabase` registration, and the pre-dispatch PIN gate are all inside `#if PACKETVER_SUPPORTS_PINCODE`; no assigned PIN transaction runs under the selected source build, regardless of runtime `pincode_enabled` configuration. This is direct compile-time applicability evidence, not a date-only guess.

The packed declarations remain visible in common headers, identifying the family as character-server PIN/security traffic:

| Opcode | Direction | Declared fixed size and fields | Guarded source meaning |
|---|---|---|---|
| `0x08B8` | C2S | 10: opcode `u16@0`, AID `u32@2`, encoded PIN `[4]@6` | Verify PIN challenge; successful compare marks `pincode_correct` and replies state 7 on pre-20180124 profiles. |
| `0x08B9` | S2C | 12: opcode `u16@0`, seed `u32@2`, AID `u32@6`, state `u16@10` | PIN state challenge/result. Seed is assigned `rnd() % 0xFFFF`; it is not generated/sent in selected build. |
| `0x08BA` | C2S | 10: opcode `u16@0`, AID `u32@2`, encoded new PIN `[4]@6` | Set first PIN after validating challenge and policy. |
| `0x08BE` | C2S | 14: opcode `u16@0`, AID `u32@2`, encoded old PIN `[4]@6`, encoded new PIN `[4]@10` | Verify old PIN, validate new PIN, notify login server of update, then reply passed/illegal state. |
| `0x08C5` | C2S | 6: opcode `u16@0`, AID `u32@2` | Request PIN window/status; if enabled, server sends NEW or ASK state. |

When compiled for PIN-capable dates, the state meanings are declared in `char.hpp`: 0 OK, 1 ask, 2 not set, 3 expired, 4 new, 5 illegal, 6 reserved/unsupported KSSN, 7 passed for pre-20180124, and 8 wrong. The comment immediately above `chclif_pincode_sendstate` is stale for some enum values; the enum and call sites are the source of these codes. Wrong PIN increments `pincode_try` and can notify login server at configured max tries; decrypt rejects non-four-digit/non-digit values. These later-profile security semantics are not active in selected source config.

## Scope and limits

All five discovery rows are classified `INACTIVE_FOR_SELECTED_SOURCE_CONFIG` and linked to this contract. This does not prove the deployed server uses the selected build, nor does it close historical client reachability or certify PIN security. No runtime changes were made. Any later-profile PIN implementation requires its own profile-specific contract and security review; independent character-slot work continues.
