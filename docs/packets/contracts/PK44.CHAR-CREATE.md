## Selected request and response

### C2S `0x0067` CH_MAKE_CHAR

The selected pre-20120307 form is packed, fixed 37 bytes:

1. opcode `u16` offset 0 (value `0x0067`).
2. name `[24]` offset 2 (NAME_LENGTH=24, copied as bounded string).
3. six one-byte stats STR/AGI/VIT/INT/DEX/LUK at offsets 26–31.
4. slot `u8` offset 32.
5. hair color `u16` offset 33 and hair style `u16` offset 35.

The character-server packet database registers `HEADER_CH_MAKE_CHAR` unconditionally with the selected struct size and `chclif_parse_createnewchar`. The current client constructs the same 37-byte profile struct, fills name/stats/slot/hair fields, and sends it from `LoginMsg_CreateCharacter`; its send path is confirmed in `LoginMode.cpp`. The Ref source is not sufficient evidence for all historical client behavior and is not used as server authority.

For comparison, related request forms not among these audit parents are `0x0970` (20120307 through pre-20151001: name, slot, hair color/style) and `0x0A39` (20151001+: additionally job and sex). They are date variants of character creation, not deletion. They remain outside this assigned discovery set and are not claimed supported by the current client.

### S2C `0x006D` HC_ACCEPT_MAKECHAR

Selected source layout is fixed `2 + sizeof(CHARACTER_INFO)` bytes. Opcode is `u16` at offset 0, followed by the serialized character record. `chclif_createnewchar` zero-initializes the packet, writes the header, fills the record with `char_mmo_char_tobuf`, and sends it after successful creation. For contemporary later MAIN/RE dates, source changes the acceptance opcode to `0x0B6F`; selected 20080910 uses `0x006D`.

The client requires `sizeof(PACKET_HC_ACCEPT_MAKECHAR)` before copying the record into its character list, appends it if local capacity allows, and returns to character selection. The selected 20080910 source compiles `PACKETVER_SAK_LEGACY_CHARINFO`; its 108-byte record ends with 16-bit `CharNum` and 16-bit `hairColor`, unlike the current client's same-sized 8-bit slot/color plus rename-flag tail. PK44.04 now applies the selected legacy conversion to this response when the resolved account login date is before 20090225 and verifies the mapped slot/color through the production handler. Later server layouts remain profile-sensitive and are not certified by that replay.

### S2C `0x006E` HC_REFUSE_MAKECHAR

Fixed 3 bytes: opcode `u16` offset 0; result `u8` offset 2. Server mapping in `chclif_createnewchar_refuse`: internal name collision `-1` -> wire `0x00`; character creation disabled `-2` -> `0xFF`; underage `-3` -> `0x01`; ineligible slot `-4` -> `0x03`. The selected parser calls this for disabled creation or any negative `char_make_new_char` result.

The current client treats codes 0 as name collision and 1 as age restriction, but previously mapped 2 to deletion restriction and 11 to premium service without selected-source evidence; it also lacked an explicit 255 label. PK44.04 now maps source-emitted 255 to creation denied and preserves numeric fallback for 2 and 11. A production-handler replay checks selected emitted results 0/1/3/255 and these unassigned values. Other `char_make_new_char` error codes need source-by-source confirmation before claiming a full code map.
