## Later-profile response format

The packed header in `packets.hpp:176-183` is eight bytes: signed `int16` opcode at offset 0; signed `int16` total packet length at 2; `uint16` result at 4; and `uint16` entry count at 6. The result enum values are `SUCCESS=0`, `FINAL_SUCCESS=1`, `EMPTY=2`, and `FAILED=3` (`storage.hpp:38-41`). The database reader returns `EMPTY`, `FAILED`, or `FINAL_SUCCESS`; the sender preserves that result value. Total emitted size is `8 + count * entry_size`. `MAX_GUILD_STORAGE_LOG_PACKET` caps the entry count so the signed length does not exceed `INT16_MAX`. For non-final-success results, the sender sets count to zero and emits only the header.

Each packed entry contains these fields, in order:

| Field | Older item/card-width variant | Newer item/card-width variant |
|---|---|---|
| Log ID | `uint32`, offset 0 | `uint32`, offset 0 |
| Item ID | `uint16`, offset 4 | `uint32`, offset 4 |
| Amount | `int32`, offset 6 | `int32`, offset 8 |
| Action | `uint8`, offset 10 (`true` means put) | `uint8`, offset 12 |
| Refine | `int32`, offset 11 | `int32`, offset 13 |
| Unique item ID | `int64`, offset 15 | `int64`, offset 17 |
| Identified | `uint8`, offset 23 | `uint8`, offset 25 |
| Item type | `uint16`, offset 24 | `uint16`, offset 26 |
| Four card IDs | 4 × `uint16`, offset 26 | 4 × `uint32`, offset 28 |
| Character name | 24 bytes, offset 34 | 24 bytes, offset 44 |
| Time string | 24 bytes, offset 58 | 24 bytes, offset 68 |
| Attribute | `uint8`, offset 82 | `uint8`, offset 92 |

The older entry is 83 bytes. The wider entry is 93 bytes. The wider item ID is selected at MAIN 20181121 / RE 20180704 / ZERO 20181114; the four card IDs use the corresponding threshold in `EQUIPSLOTINFO` (`packets_struct.hpp:410-418`). At the selected MAIN 20080910 profile the older widths would apply, but the packet sender is compiled out. Packed multi-byte fields are copied as the server's packed struct representation; the source snapshot does not establish deployed-server architecture or byte order. The sender assigns the absolute logged quantity through a `uint16` conversion into the `int32` amount field, action from the sign of the stored amount, and bounded name/time strings with `safestrncpy`.

## Call path and selected-profile applicability

`storage.cpp:642-714` reads guild-storage log rows and calls `clif_guild_storage_log`; `script.cpp:10983-11000` exposes this through `guildopenstorage_log`, itself guarded at `PACKETVER >= 20140205` and otherwise returning script failure. Guild-storage add/delete operations write history to the database in `storage.cpp:615-639`, `:764-783`, and `:852-854`; that storage-side logging is not proof that the client response is emitted. The S2C emitter has its own 20140205 guard and is a no-op for older configurations. Under effective `PACKETVER=20080910`, the script entry point rejects the operation and the sender body is excluded.

`OFFICIAL_GUILD_STORAGE` is defined by `src/config/packets.hpp` only when `PACKETVER >= 20131223`; it is absent in the selected profile and affects official storage capacity/permission behavior. It is not the 0x09DA date guard: the packet and log-reader command independently require 20140205. The `0x09DA` discovery row remains PK12 primary; this checkpoint adds PK44 only as a secondary review owner. This source evidence does not establish what a separately deployed server binary emits.
