## Selected packet forms and state

- C2S `0x028D`, fixed 34 bytes: opcode `u16@0`, AID `u32@2`, CID `u32@6`, new name `[24]@10`. The server verifies AID equals session account ID, verifies CID is in `sd.found_char`, copies and normalizes the requested name, and runs `char_check_char_name`. Invalid name -> S2C `0x028E result=0`; valid name -> saves normalized name in `sd.new_name` and returns `0x028E result=1`. Unknown CID returns without a response.
- S2C `0x028E`, fixed 4 bytes: opcode `u16@0`, result `u16@2`, 0 invalid / 1 valid. Server zero-initializes the packed response.
- C2S `0x028F`, fixed 6 bytes for PACKETVER < 20111101: opcode `u16@0`, CID `u32@2`. Server checks CID against the session's found-character slots. If absent, it returns without a reply. Otherwise it calls `char_rename_char_sql(sd,cid)` using the name previously saved by `0x028D`.
- S2C `0x0290`, fixed 4 bytes: opcode `u16@0`, result `u16@2`. Source result meanings: 0 success; 1 rename already consumed; 2 no prepared name/character-load failure; 3 SQL update failure; 4 duplicate/reserved name; 5 guild restriction; 6 party restriction; 8 invalid name. Comments also list 7 length and 9 prohibited-name errors, though the shown selected `char_rename_char_sql` maps invalid name to 8. Unknown values should remain unknown.

The final rename path checks the rename counter, configured party/guild eligibility, name validity and uniqueness; on success it updates the SQL name, decrements the rename allowance, synchronizes party/guild names, clears `sd.new_name`, and optionally writes a character log. The source parser registrations for `0x028D` and `0x028F` are unconditional under selected configuration.
