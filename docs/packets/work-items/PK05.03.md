# Work item PK05.03 — report protocol framing failures

Complexity: **S** (risk classification only; no mandatory model or prior approval). Owner: current implementation agent; PK48 independently reviews after implementation.

## Goal and decision

Make framing failures distinguishable from ordinary no-data and ordinary EOF while retaining the existing boolean receive API. `CRagConnection` exposes a last receive error with distinct `UnknownOpcode` and `InvalidVariableLength` values. Set the value before disconnect so it survives `OnClose`; reset it on a new successful connection. `CLoginMode::OnUpdate` maps each type to an explicit login error message while retaining existing generic connection-loss messages for ordinary EOF. Existing logging must describe disconnect rather than a silent drop.

## Scope and acceptance

- Add the typed error and accessor in `src/network/Connection.h` and maintain it in `Connection.cpp`.
- Use the error in `src/gamemode/LoginMode.cpp` to produce the matching failure status/dialog text.
- Replay exact error type for unknown, undersized, oversized, and fragmented inputs, then verify the error clears on reconnect and ordinary framing resumes.
- Preserve PK05.02 behavior: close and clear queues; do not scan; do not emit the valid suffix.
- No packet handlers, discovery classifications, or generic EOF behavior change.
- Fresh deploy-off build and focused production replay; save exact JSONL, commands, binary hash/time.
- Visible modal delivery and full LoginMode update lifecycle are evidence limits if the harness cannot instantiate them.
- Separate commit: `packet(PK05.03): report receive framing errors`.

PK05.04 self-review and PK48 independent review remain separate checkpoints.
