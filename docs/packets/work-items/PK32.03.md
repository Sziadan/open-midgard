# PK32.03 — legacy attachment claims

## PK32.03-LEGACY-MAIL-CLAIM

The Qt inbox can send the selected six-byte `0244` for the selected detail. The client records the original ID and counts the item and Zeny components shown in the detail. It waits for each expected success or an explicit refusal, then reads that ID again. Success requires a read sent after terminal acknowledgement and a detail showing no attachments. The client never credits resources from an acknowledgement or detail. The selected server normally sends authoritative inventory and Zeny updates separately.

The selected server can clear cached Zeny before rejecting item capacity and can omit an acknowledgement if the service or final item delivery fails. A read can therefore show zero attachments while delivery remains unresolved. After 15 seconds, Check attachments reads the original message while retaining claim ownership and avoiding another transfer. An explicit refusal ends the acknowledgement phase. The readback updates the visible attachments to the server's current view, which may still need live reconciliation after a combined refusal. A same-connection warp keeps claim ownership and connection replacement clears it. Readback waits while the composer is active.

Production replay checks the wire request, two-success completion, changed selection, capacity refusal during composition, silent and partial delivery, a pre-acknowledgement readback, and map handoff. Verify actual inventory and Zeny delivery, late replies, capacity behavior, and the rendered panel against a deployed server.

## Original acceptance and remaining work

Strong source/design decision supplied in [PK32.LEGACY-MAIL-STATE](../contracts/PK32.LEGACY-MAIL-STATE.md). Implement against the existing composer and PK32.02 inbox model. A single item-plus-zeny claim can emit two identical 0x0245 successes; neither carries ID or component. Serialize ambiguous pending transfers, retain their requested ID/generation across selection changes, and derive actual resources only from authoritative inventory/zeny updates. Readback of reserved attachments alone is not delivery completion. Preserve an unresolved phase if component delivery cannot be settled; do not guess or auto-retry on timeout.

Production sequence tests must cover two successes, partial delivery, capacity failure, service refusal/no reply, selection change, staged composition during refresh, and late ack/session departure. Do not let a late reply resolve a newer pending claim. Source fixtures and the reviewed transaction design unblock implementation; actual escrow/production/UI acceptance remains open.
